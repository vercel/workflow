# Global streams: client contract notes

This SDK exposes global streams separately from run streams. The server contract leaves several decisions visible to callers and reviewers:

- **The encryption declaration is immutable.** Every chunk write declares its encryption through `X-Stream-Encryption`, the base64url encoding of canonical JSON. The first write binds the declaration to the stream; later writes are checked against it before an index is reserved or bytes are persisted. Core retains the plaintext framed write, reloads `/info`, re-encrypts, and retries once on `stream_encryption_mismatch`. Close carries no declaration because it writes no bytes.
- **The declaration scheme is an open set.** This client implements only `{"v":1,"s":"dpl","d":"dpl_…","k":"…"}`. Unknown versions or schemes fail loudly rather than being treated as unencrypted data. The complete declaration travels with the stream ID in the distinct `{ kind: 'global', id, encryption }` descriptor.
- **Readers may attach before the first write.** `/info` returns `{ tailIndex: -1, done: false, earliestIndex: 0, encryption: null, retentionDays: null }` for an unwritten ID, and a live GET waits for its first chunk. Close and delete still return 404 before the first write. The SDK preserves this wait-by-default behavior; callers that need typo detection must impose their own policy.
- **Retention races.** `earliestIndex` is advisory: a chunk may expire after `/info` or during a live read. A 410 is terminal for that read session and is exposed; reconnecting cannot recover absent bytes. Applications should persist their own cursor and handle retention expiry.
- **Minting requires a region.** Random IDs are minted by the World so world-vercel can reuse its region-tagged ULID scheme. `globalStreamIdFor({ region, name })` uses a version-2 tagged body derived from `SHA-256(projectId|environment|name)`; the server never sees the name. Worlds without the matching ID capability reject instead of minting an unroutable ID.
- **Public-key authenticity and key rotation.** Before using local deployment key material, core derives its X25519 public key and compares it with declaration field `k`. It uses the symmetric shortcut only on a match; on mismatch, writers seal to `k` like any off-anchor writer. Readers force the run-key API for declaration field `d` and verify the fetched key, which keeps BYOK rotation from silently selecting stale local material.
- **Run-key API terminology and controls.** Cross-deployment global-stream readers use the existing run-key endpoint with a `gstr_` ID. Its rate limits, auditing, and errors may refer to a “run”; server/API owners should confirm that this use is supported and observable without misleading operators.
- **SDK layering.** `@workflow/world-vercel` cannot derive X25519 keys because core depends on it. Core therefore constructs and validates the encryption declaration while the World adapter canonicalizes and transports it. This keeps package dependencies acyclic and makes alternate encryption schemes a core concern rather than a Vercel transport concern.
