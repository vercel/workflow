The Local World is bundled with `workflow` and used automatically during local development. It requires no installation or configuration.

To explicitly use the Local World in any environment, set this environment variable:

```bash
WORKFLOW_TARGET_WORLD=local
```

## Observability

The Workflow CLI uses the Local World by default. Run these commands inside your workflow project to view your local development workflows:

```bash
# List recent workflow runs
npx workflow inspect runs

# Launch the web UI
npx workflow web
```

Learn more in the [Observability](/docs/observability) documentation.

## Configuration

The Local World requires no configuration, but you can customize its behavior through environment variables or programmatically through `createWorld()`.

### `WORKFLOW_LOCAL_DATA_DIR`

Directory for the workflow database, `world.db` (SQLite). Default: `.workflow-data/`

### `PORT`

The application dev server port. Used to deliver workflow queue messages to the combined flow route. Default: auto-detected

### `WORKFLOW_LOCAL_BASE_URL`

Full base URL override for HTTPS or custom hostnames. Default: `http://localhost:{port}`

Port resolution priority: `baseUrl` > `port` > `PORT` > auto-detected

### `WORKFLOW_LOCAL_QUEUE_CONCURRENCY`

Maximum number of concurrent queue message handlers. Default: `1000`

### `WORKFLOW_LOCAL_QUEUE_MAX_VISIBILITY`

Maximum number of seconds a local queue message can stay hidden before the handler rechecks the run. Default: unlimited.

### `WORKFLOW_LOCAL_RUN_STATUS_POLL_INTERVAL_MS`

How often a wait for a terminal run status re-reads the run, in milliseconds. Default: `100`.

`await run.returnValue` asks the World to wait for the run to finish. When the run and the caller share a process (the usual development server case), an in-process signal resolves the wait as soon as the run ends, and this interval never comes into play. The interval covers activity the signal cannot detect, primarily a second process awaiting a run over the same data directory, so it is set far below Workflow's own polling interval.

### `WORKFLOW_LOCAL_HEADERS_TIMEOUT_MS`

Maximum time in milliseconds to wait for a local queue handler to begin responding before redelivering the durable message. Default: `0` (no deadline).

A delivery executes inline steps before the handler responds, so a deadline shorter than your longest step redelivers a healthy delivery while it is still running and executes the same step again. Set this only if you would rather a hung handler be redelivered, and set it above the longest inline work you expect.

### `WORKFLOW_LOCAL_BODY_TIMEOUT_MS`

Maximum gap in milliseconds between response body chunks from a local queue handler before redelivering the durable message. Default: `0` (no deadline). The same caution as `WORKFLOW_LOCAL_HEADERS_TIMEOUT_MS` applies.

### `WORKFLOW_NODE_HTTP`

Whether queue deliveries go out through Node's built-in `node:http` and `node:https` modules instead of the HTTP client library this World normally uses. Default: disabled. Set to `1` to switch to Node's modules. Socket pooling, keep-alive, and both timeouts above apply either way. See [`WORKFLOW_NODE_HTTP`](/docs/configuration/runtime-tuning#workflow_node_http) for what else changes.

### `WORKFLOW_LOCAL_RECOVER_ACTIVE_RUNS`

Whether pending and running runs found in the data directory are re-enqueued when the World starts. Set to `0` or `false` to skip recovery and leave stale runs untouched. Default: `true`.

The Local World's queue is in memory, so a restart loses the messages runs had queued. Recovery re-enqueues each run with a recovery marker, which makes a single-orchestrator (spec 9) delivery send the run's step messages and wait timers again, and it also sends each recovered run a wake for every open wait (a `sleep()` or a timeout), due when the wait is, so no sleeping run is left without a timer.

Recovery also hands back to the queue any step that was running inline when the previous process exited. The step runs again right away instead of after the inline-ownership lease (about 14 minutes), and the interrupted attempt counts toward its retries. A step with `maxRetries: 0` that was interrupted mid-body therefore fails on restart with an "exceeded max retries" error instead of running again once the lease expires, as it already does after a crash on the Vercel World.

If you turn recovery off and re-enqueue runs yourself, call `releaseOrphanedSteps(runId)` before re-enqueueing each run. It is a method of `LocalWorld`, the type `createWorld()` from `@workflow/world-local` returns. The `World` type that `getWorld()` returns does not declare it, so a caller holding a `World` needs the `LocalWorld` type to call it.

A step counts as abandoned only if it started before the Local World loaded in the current process or worker thread. Steps started since then are never released, so runs this process picks up during or after recovery are not affected, and calling `releaseOrphanedSteps()` late is safe. Recovery assumes that nothing else is running workflows on the same data directory and `tag`. That includes an earlier worker thread of the same process: some dev servers reload into a new worker thread, and until the old one stops, the new one may dispatch a step the old one is still running, so the step can run twice. If several processes or workers run workflows on one data directory, turn recovery off or give each one its own `tag`.

### `WORKFLOW_LOCAL_SQLITE_KEEP_CONNECTIONS`

How long a process keeps its connection to `world.db` open between operations. `1` keeps it until it has been idle for a few seconds (the default, except on Windows). `brief` closes it once a burst of operations ends (the default on Windows, where an open database file cannot be deleted, so the data directory stays removable while the app runs). `0` opens and closes a connection for every operation, which is slower; the repository's own tests use it on Windows because they delete their data directory right after using it.

### `WORKFLOW_LOCAL_HOOK_RETENTION_LIMIT_DAYS`

Maximum [`experimental_minRetention`](/docs/api-reference/workflow/create-hook#keep-a-token-unavailable-after-the-run-ends) accepted by the Local World, in days. Default: `30`. Set this to the same limit as your production World so oversized values fail during local development.

### `WORKFLOW_STREAM_FLUSH_INTERVAL_MS`

Group-commit window, in milliseconds, for the leading chunk of an idle stream. Default: `0` (dispatch immediately). A positive value holds the first chunk up to that long to collect a group, trading first-chunk latency for fewer requests. Chunks arriving while a request is in flight always coalesce into the next group regardless.

### Programmatic configuration

Options passed to `createWorld()` take precedence over the environment variables above. Export the configured World from a module and point `WORKFLOW_TARGET_WORLD` at that module:

```typescript title="my-world.ts" lineNumbers
import { createWorld } from "@workflow/world-local";

export default createWorld({
  dataDir: "./custom-workflow-data",
  port: 5173,
  // baseUrl overrides port if set
  baseUrl: "https://local.example.com:3000",
  recoverActiveRuns: true, // overrides WORKFLOW_LOCAL_RECOVER_ACTIVE_RUNS
  streamFlushIntervalMs: 10, // WORKFLOW_STREAM_FLUSH_INTERVAL_MS, if set, overrides this
});
```

```bash title=".env"
WORKFLOW_TARGET_WORLD="./my-world.ts"
```

`createWorld()` also accepts `tag`, which scopes the runs and streams a World writes, and which runs its startup recovery re-enqueues, so several Worlds can share one data directory without seeing each other's data. A tagged World also reads untagged runs, and its `clear()` deletes only its own data. It is mainly used by test harnesses that share one `.workflow-data` directory with the app.

### Queue consumers other than the Workflow SDK

The Local World delivers queue messages over HTTP to the app, and by default every message goes to the Workflow SDK's flow route, `/.well-known/workflow/v1/flow`. A library that consumes messages of its own on the same World, such as a durable agent harness, uses its own queue prefix (`__{namespace}_wkf_workflow_`) and tells the World where those go:

```typescript title="lib/agent-queue.ts" lineNumbers
import { getWorld } from "workflow/runtime";

const PREFIX = "__agent_wkf_workflow_";

export async function registerAgentQueue(
  handler: (req: Request) => Promise<Response>
) {
  const world = await getWorld();
  // Over HTTP: deliveries for this prefix go to the app's own route.
  world.registerRoute?.(PREFIX, "/api/agent/queue");
  // In this process: deliveries skip HTTP entirely.
  world.registerHandler?.(PREFIX, handler);
}
```

`registerHandler()` takes precedence over `registerRoute()` for the same prefix. A prefix with neither still goes to the flow route, which answers `400` for a prefix it does not handle, and the Local World retries the message every five seconds, so a route registered later takes the next attempt. When the World restarts, `start()` re-enqueues each active run to the queue namespace it recorded at creation (`executionContext.queueNamespace`), so register the route or handler before calling `start()`.

## Data directory layout

Everything the Local World stores is in one SQLite database, `world.db` in the data directory (with SQLite's `world.db-wal` and `world.db-shm` files next to it): runs, their event logs, steps, waits, hooks, stream chunks and snapshots. Queue messages are not stored: a message is an HTTP request to the app (or a call to an in-process handler) made by the process that enqueued it, held only in that process's memory while it waits for a delay or a retry. It is opened with the runtime's built-in driver, `node:sqlite` on Node.js 22.13 or later and `bun:sqlite` on Bun, so there is no native dependency to install. Node.js releases that still mark `node:sqlite` as experimental (22.x) print `ExperimentalWarning: SQLite is an experimental feature` once per process; Node.js 24 does not.

Each World write is one transaction: an event and every change it makes to its run, step, wait and hook commit together or not at all, so a process that is killed mid-write leaves nothing half-written behind. Several processes can use one data directory at once (an app and a test runner, say). SQLite orders their writes, and the lock it takes is released by the operating system when a process exits, however it exits.

To look at the data directly, open it with any SQLite client:

```bash
sqlite3 .workflow-data/world.db "select seq, event_type, correlation_id from events where run_id = 'wrun_…' order by seq"
```

Earlier releases stored one JSON file per entity (`runs/`, `events/`, `steps/`, `hooks/`, `.locks/` and so on). That data is not migrated, and it is not deleted either: the World leaves those directories where they are, does not read them, and starts with an empty database next to them. Delete them by hand once you no longer need them. Older releases do not read `world.db`, so runs created with this release are not visible after a downgrade, and a `world.db` written by a newer release is refused rather than read.

The database needs a filesystem that supports SQLite's shared-memory file. A data directory on a network filesystem (NFS, SMB), or shared between a host and a container through a VM-backed mount, is not supported when more than one machine or VM writes to it.

## Limitations

The Local World is designed for development, not production:

- **In-memory queue**: Queue messages, including delayed ones and retries, do not survive a restart. Startup recovery re-enqueues active runs and their open waits.
- **Single machine**: The data directory is a local SQLite database, so the Local World cannot handle distributed deployments.
- **No authentication**: The Local World is suitable only for local development.

For production deployments, use the [Vercel World](/worlds/vercel), which handles execution, persistence, multi-tenancy, scale, observability, and security for you on Vercel, or check out the [Postgres World](/worlds/postgres) - a tested reference implementation that implements the complete World spec and can be used to deploy workflows anywhere.
