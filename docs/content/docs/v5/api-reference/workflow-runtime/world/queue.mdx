Queue methods live directly on the `world` object (not nested). They dispatch internal workflow invocations, including queued step work, to the queue backend.

<Callout type="warn">
  The Workflow SDK uses these methods internally to dispatch execution. In normal operations, use [`start()`](/docs/api-reference/workflow-api/start) to trigger workflows instead. You only need direct queue access to start the initial execution of a run you programmatically created via `world.events.create()` with a `run_created` event, or to debug flow resumption.
</Callout>

## Import

```typescript lineNumbers
import { getWorld } from "workflow/runtime";

const world = await getWorld(); // [!code highlight]
// Call queue methods directly on world, for example, world.queue()
```

## Methods

### getDeploymentId()

Get the current deployment ID. The SDK uses it internally to route queue messages to the correct deployment.

```typescript lineNumbers
const deploymentId = await world.getDeploymentId(); // [!code highlight]
```

**Returns:** `string`. The current deployment ID.

### queue()

Dispatch a message to a named queue. The message payload is an internal SDK type (`WorkflowInvokePayload` or `HealthCheckPayload`). Queued steps use `WorkflowInvokePayload` with `stepId` and `stepName`.

```typescript lineNumbers
const { messageId } = await world.queue(queueName, payload, opts); // [!code highlight]
```

**Parameters:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `queueName` | `ValidQueueName` | The queue name (branded string) |
| `message` | `QueuePayload` | Internal SDK payload |
| `opts` | `QueueOptions` | Optional: `deploymentId`, `idempotencyKey`, `delaySeconds`, `headers`, `region` (regional routing hint), `specVersion` |

**Returns:** `{ messageId: MessageId | null }`

### createQueueHandler()

Create an HTTP handler that processes messages from a queue. Use it to set up the queue consumer endpoint.

```typescript lineNumbers
const handler = world.createQueueHandler(prefix, callback); // [!code highlight]
```

**Parameters:**

| Parameter | Type | Description |
|-----------|------|-------------|
| `prefix` | `QueuePrefix` | Queue name prefix to match |
| `callback` | `(message, meta) => Promise<void \| { timeoutSeconds: number }>` | Handler called for each message. `meta` contains `attempt`, `queueName`, `messageId`, `requestId`. |

**Returns:** `(req: Request) => Promise<Response>`

#### What the callback can rely on

The callback needs `meta.messageId`, `meta.attempt` and its own result, and nothing about how the World holds a delivery. Every World gives it three rules:

- **A throw brings the same message back.** The World calls the callback again with the same `meta.messageId` and an incremented `meta.attempt`, after its retry backoff and up to its retry limit.
- **A crash brings the same message back.** While the callback runs, the World keeps its message from other handlers, and renews whatever holds the delivery (a visibility timeout, a job lock) itself. If the process running the callback dies, the World delivers the same message again with an incremented `meta.attempt`. The table below shows how long that takes.
- **A return means done.** The World acknowledges the delivery. Returning `{ timeoutSeconds: n }` also schedules a wake, which delivers the payload again after about `n` seconds. Whether the wake is the same message differs between Worlds, so don't return one while work is still recorded under this `messageId`, and don't rely on `meta.messageId` or `meta.attempt` carrying across it.

| World | Throw | Crash | Wake (`{ timeoutSeconds }`) |
|-------|-------|-------|-----------------------------|
| Vercel | Same message, after a backoff that starts at 5 seconds and doubles per delivery up to 15 minutes. A thrown error's numeric `retryAfter` is a lower bound. | Same message, once its visibility timeout lapses: about 300 seconds after the delivery started or the queue client last renewed it (every 60 seconds while the callback runs). | A new message, whose `meta.attempt` starts at 1. A delay is capped at about 23 hours per wake. |
| Postgres | Same message, after Graphile Worker's exponential backoff. | Same message, once Graphile Worker resets the job's lock, 4 hours after the job was claimed. A restart's `start()` re-enqueues each active run sooner, as a new message. | Same `meta.messageId`, and `meta.attempt` starts again at 1. |
| Local | Same message, after 5 seconds. | Not kept. The queue is held in memory, so a crash loses the delivery, and the next `start()` re-enqueues each active run as a new message. | Same message, and `meta.attempt` is incremented. |

Work that an earlier delivery recorded under this `messageId` and left open is this delivery's to recover: a callback never returns with work open, so that delivery threw or died. It may still be running if the World only lost its hold on it, for example after a stalled renewal or a frozen process, so the recovery must be fenced. `meta.attempt > 1` only says this isn't the message's first delivery. The runtime's inline step ownership works this way:

`meta.messageId` should be stable across redeliveries of the same message (one ID per enqueued message, reused on every delivery attempt). The runtime records it on inline `step_started` events as a liveness lease so that only a redelivery of the owning message re-executes a crashed inline step before the lease expires (see [Inline step message ownership](/docs/changelog/step-message-ownership)). A World whose queue mints a fresh ID per delivery degrades gracefully. Crashed inline steps recover via the delayed backstop instead of immediately on redelivery, but never wedge or duplicate.
