Start/enqueue a new workflow run.

```typescript lineNumbers
import { start } from "workflow/api";
import { myWorkflow } from "./workflows/my-workflow";

const run = await start(myWorkflow); // [!code highlight]
```

## Good to know

* Use the `start()` function in runtime contexts to programmatically trigger workflow executions.
* In v5, you can also call `start()` directly from a workflow function to spawn a child run or continue work in a new run. See [Workflow Composition](/cookbook/common-patterns/workflow-composition) and [Versioning](/docs/foundations/versioning).
* This is different from calling workflow functions directly, which is the typical pattern in Next.js applications.
* The function returns immediately after enqueuing the workflow. It doesn't wait for the workflow to complete.
* Without an idempotency key, each call to `start()` creates a new workflow run. To start at most one run per business key, such as an order ID, pass [`experimental_idempotencyKey`](#idempotency-keys): a duplicate call returns the run that already holds the key instead of creating another, decided atomically with creating the run. To also deliver a duplicate request's data to the active run, combine it with a deterministic hook token. See [Idempotency](/docs/foundations/idempotency#run-idempotency).
* The returned `Run` has `experimental_started: true` when this call created the run, and `false` when it returned an existing run that holds the call's idempotency key.
* All arguments must be [serializable](/docs/foundations/serialization).
* When you provide `deploymentId`, the argument types and return type become `unknown` because the workflow function's types may differ across deployments.
* When `deploymentId` names a deployment other than the caller's, the run is stamped with the spec version the *target* deployment reports on its capability probe (capped at the caller's own), since the target is what executes it. `start()` waits up to 10 seconds for the first probe to a deployment and returns as soon as the target answers; later starts to the same deployment reuse the answer. If the target does not answer in time, the run is stamped with spec version 6, the lowest version a v5 runtime executes; a target on an older major version (such as `stable`) cannot execute such a run, so it logs a warning. In either case, the `attributes` and `experimental_retention` checks below apply to the stamped version, and fail naming the target deployment.
* `attributes` seeds plaintext run metadata as part of creation and requires a World implementing spec version 4 or later. Keys that start with `$` are reserved for framework and library code; framework-level callers can pass `allowReservedAttributes: true` to seed reserved keys, with the same semantics as the [`setAttributes`](/docs/api-reference/workflow/set-attributes) option of the same name.
* `region` pins the new run to a specific region on Worlds with a regional dimension. The [Vercel World](/worlds/vercel#explicit-region-selection) then serves the run's storage, queue dispatch, and streams from that region. When you omit `region`, the run is pinned to the region where it was created. Worlds without regions ignore the option.
* `experimental_retention` asks the World to delete the run's user data as soon as the run completes or fails, instead of keeping it for the World's default window. `0` requests immediate deletion; `'default'` is identical to omitting the option. These are the only two values accepted — the value is a duration and zero is the only one implemented, and its unit is not yet decided. Recorded as the reserved `$retention` attribute, so it needs a World implementing spec version 4 or later. Retention is enforced by the World, not the SDK: the first-party Worlds implement it and a World that does not keeps the data. Note that `await run.returnValue` on a run started with `experimental_retention: 0` usually throws [`RunExpiredError`](/docs/errors/run-expired) rather than resolving, because the deletion races the read. See [Data retention](/docs/observability/retention).
* `compressArguments: false` stores the run's arguments uncompressed. By default they are compressed when the target run can decode them. Arguments of 256 KiB or more are compressed off the caller's event loop, so starting a run with a large input doesn't stall other requests the process is serving. The attempt still costs CPU proportional to the input size and is wasted on data that will not shrink (media, encrypted or random bytes), so skip it when you know the inputs are incompressible. `true` is the default and does not force compression. The option only affects the arguments; a [dynamic workflow's](/docs/advanced/dynamic-workflows) code is compressed regardless. To disable compression for every write in a process, see [`WORKFLOW_DISABLE_COMPRESSION`](/docs/configuration/runtime-tuning#workflow_disable_compression).

<Callout type="info">
If `start()` throws `'start' received an invalid workflow function. Ensure the Workflow SDK is configured correctly and the function includes a 'use workflow' directive.`, the compiler did not transform the passed function as a workflow. The two most common causes are a missing `"use workflow"` directive or missing framework integration. See [start-invalid-workflow-function](/docs/errors/start-invalid-workflow-function).
</Callout>

## Examples

### With arguments

const run = await start(userSignupWorkflow, ["user@example.com"]); // [!code highlight]
```

### With `StartOptions`

import { start } from "workflow/api";

const run = await start(myWorkflow, ["arg1", "arg2"], { // [!code highlight]

```

### Using `deploymentId: "latest"`

Set `deploymentId` to `"latest"` to automatically resolve the most recent deployment for the current environment. This is useful when you want to ensure a workflow run targets the latest deployed version of your application rather than the deployment that initiated the call. For when to use this and how it fits with default run pinning, see [Versioning](/docs/foundations/versioning).

```typescript
import { start } from "workflow/api";
import { myWorkflow } from "./workflows/my-workflow";

const run = await start(myWorkflow, ["arg1", "arg2"], { // [!code highlight]
  deploymentId: "latest" // [!code highlight]
}); // [!code highlight]
```

<Callout type="info">
The `deploymentId` option is currently a Vercel-specific feature. Other Worlds may implement this option differently to match their own deployment runtimes, and the World spec may rename it from `deploymentId` to `version` in a future SDK version. On Vercel, `"latest"` resolves to the most recent deployment matching your current environment: the same production target for production deployments, or the same git branch for preview deployments.

In Worlds without atomic, immutable deployments (such as local development or self-hosted Postgres), there is no notion of multiple deployments to resolve between, so `deploymentId: "latest"` has no effect: the SDK logs a warning and the run targets the current deployment. This means a workflow that opts into `"latest"` on Vercel still runs unchanged in local development.
</Callout>

<Callout type="info">
Resolving `"latest"` is the one `start()` path that calls the Vercel API, so it
needs an identity that can see the calling deployment. Inside a Vercel
deployment the SDK authenticates with the deployment's own OIDC token, which
carries the owning team, and this takes precedence over a `VERCEL_TOKEN` set in
the function's environment. A `VERCEL_TOKEN` belongs to a *user* and carries no
team, so authenticating with it scopes the lookup to that user's default team
and fails with a 404 whenever that is not the team that owns the deployment.
Outside a deployment (CLI, CI, the dashboard) the SDK uses the World's
`token`, falling back to `VERCEL_TOKEN`; configure the World's `teamId` so the
request is scoped explicitly. See
[Starting runs from outside a deployment](/worlds/vercel#starting-runs-from-outside-a-deployment).
</Callout>

<Callout type="warn">
When using `deploymentId: "latest"`, the workflow run will execute on a potentially different deployment than the one calling `start()`. Be mindful of forward and backward compatibility:

- **Workflow identity**: The function name and file path determine the workflow ID. If the latest deployment has renamed the workflow function or moved it to a different directory, the workflow ID will no longer match and the run will fail to start.
- **Input and output compatibility**: The calling deployment serializes the arguments passed to `start()`, and the target deployment deserializes them. Similarly, the target deployment serializes the workflow's return value, and the caller deserializes it. If the workflow's expected arguments or return type have changed (for example, added required fields, removed fields, or changed types), the run may fail or behave unexpectedly. Ensure that input and output schemas remain backward-compatible across deployments.
</Callout>

### Inside a workflow function

Call `start()` directly from a workflow function to spawn a child run. It is step-backed, so the spawn records a deterministic step boundary in the parent's event log.

```typescript
import { start } from "workflow/api";
import { childWorkflow } from "./workflows/child";

export async function parentWorkflow(value: number) {
  "use workflow";

  const childRun = await start(childWorkflow, [value]); // [!code highlight]
  const result = await childRun.returnValue; // [!code highlight]
  return { childRunId: childRun.runId, result };
}
```

<Callout type="info">
The returned `Run` object is fully functional inside a workflow. Each property access or method call (`.status`, `.returnValue`, `.cancel()`) executes as a separate step. See [Workflow Composition](/cookbook/common-patterns/workflow-composition) for choosing between spawning a child run and awaiting a workflow function directly.
</Callout>

<Callout type="warn">
`returnValue` polls the child run every second and holds the polling step's worker slot open for as long as the child takes to finish. For long-running children, spawn without awaiting `returnValue` and have the child resume a [hook](/docs/foundations/hooks) when it completes. See the [`startAndWait()` pattern](/cookbook/advanced/child-workflows).
</Callout>

### Idempotency keys

<Callout type="warn">
Experimental. The API may change without a major version bump. Requires a World that declares `capabilities.runIdempotencyKeys`, which the Vercel, Local, and Postgres Worlds do. On any other World, a keyed `start()` throws a `WorkflowRuntimeError` before anything is written.
</Callout>

Pass `experimental_idempotencyKey` to start at most one run per key. A second `start()` with the same key returns the run that already holds it instead of creating another, so a retried request or a duplicate webhook delivery can't start the same work twice.

```typescript lineNumbers
import { start } from "workflow/api";
import { processOrder } from "./workflows/process-order";

export async function POST(request: Request) {
  const { orderId } = await request.json();

  const run = await start(processOrder, [orderId], {
    experimental_idempotencyKey: `order:${orderId}`, // [!code highlight]
  });

  return Response.json({
    runId: run.runId,
    created: run.experimental_started, // [!code highlight]
  });
}
```

The World claims the key in the same atomic write that creates the run and its `run_created` event. Concurrent calls with one key therefore converge on one run: exactly one of them creates it, and the others receive a handle to it. Keys are scoped to the workflow, so the same key passed to two different workflows starts two runs. On the Vercel World, keys are also scoped to the run's region; see [Regions on Vercel](#regions-on-vercel).

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `experimental_idempotencyKey` | `string` | None | The key, 1 to 256 characters. Derive it from your domain, such as an order, invoice, or import ID. It is stored in plaintext on the run and shown in observability tools, so don't put personal or secret data in it. |
| `experimental_idempotencyKeyTTL` | `string \| number` | `'24h'` | How long the key stays held after the run holding it completes, fails, or is cancelled. A duration string such as `'1h'` or `'7d'`, or a whole number of milliseconds, between `'1s'` and `'30d'`. While the holding run is `pending` or `running`, it always holds the key, whatever the TTL. |
| `experimental_idempotencyKeyReusePolicy` | `IdempotencyKeyReusePolicy` | `'REJECT_DUPLICATE'` | Whether this call may take the key over from a holder that has closed but is still inside its TTL window: `'REJECT_DUPLICATE'`, `'ALLOW_DUPLICATE_FAILED_ONLY'`, or `'ALLOW_DUPLICATE'`. |
| `experimental_idempotencyKeyConflictPolicy` | `IdempotencyKeyConflictPolicy` | `'USE_EXISTING'` | What to do when the key is held and the reuse policy doesn't allow taking it over: `'USE_EXISTING'` returns the holding run, and `'FAIL'` throws [`WorkflowRunAlreadyStartedError`](/docs/errors/run-already-started). |

`IdempotencyKeyReusePolicy` and `IdempotencyKeyConflictPolicy` are exported from `workflow/api`. Passing the TTL or either policy without a key, a key outside 1 to 256 characters, a TTL outside `'1s'` to `'30d'`, or an unknown policy throws a `WorkflowRuntimeError` before anything is written.

#### When the key is already held

The outcome depends on the run currently holding the key and on the new call's reuse policy:

| Holding run | `REJECT_DUPLICATE` | `ALLOW_DUPLICATE_FAILED_ONLY` | `ALLOW_DUPLICATE` |
| --- | --- | --- | --- |
| None, or the holding run no longer exists | Create | Create | Create |
| `pending` or `running` | Conflict | Conflict | Conflict |
| `completed`, inside its TTL window | Conflict | Conflict | Create |
| `failed` or `cancelled`, inside its TTL window | Conflict | Create | Create |
| Closed, and its TTL window has expired | Create | Create | Create |

- **Create** starts a new run, and the new run holds the key from then on.
- **Conflict** applies the new call's conflict policy. `'USE_EXISTING'` returns a `Run` for the holding run with `experimental_started: false`. `'FAIL'` throws `WorkflowRunAlreadyStartedError`, whose `runId` and `runStatus` name the holding run.

The TTL window starts when the holding run closes, and its length is the TTL that run's own `start()` recorded. The reuse and conflict policies always come from the new call. When several calls race to take over the same key, exactly one wins and the others are evaluated against the winner.

When a call returns an existing run, its arguments and every other option it passed are ignored. The first call to claim the key wins, and arguments are never compared, so a duplicate with different arguments still receives the original run.

To reject duplicates instead, and to let a failed run's key be reused right away:

```typescript lineNumbers
import { start } from "workflow/api";
import { WorkflowRunAlreadyStartedError } from "workflow/errors";
import { importCatalog } from "./workflows/import-catalog";

export async function POST(request: Request) {
  const { catalogId } = await request.json();

  try {
    const run = await start(importCatalog, [catalogId], {
      experimental_idempotencyKey: `import:${catalogId}`,
      experimental_idempotencyKeyTTL: "1h", // [!code highlight]
      experimental_idempotencyKeyReusePolicy: "ALLOW_DUPLICATE_FAILED_ONLY", // [!code highlight]
      experimental_idempotencyKeyConflictPolicy: "FAIL", // [!code highlight]
    });
    return Response.json({ runId: run.runId }, { status: 202 });
  } catch (error) {
    if (WorkflowRunAlreadyStartedError.is(error)) { // [!code highlight]
      return Response.json(
        { runId: error.runId, status: error.runStatus },
        { status: 409 }
      );
    }
    throw error;
  }
}
```

#### `experimental_started`

The returned `Run` reports whether this call created the run:

| Value | Meaning |
| --- | --- |
| `true` | This call created the run. Every successful `start()` without a key returns `true`, as does a keyed call that claimed the key. |
| `false` | The key was already held, and `start()` returned the run holding it (`'USE_EXISTING'`). This call's arguments and options were ignored. |
| `undefined` | The handle did not come from `start()`, for example from [`getRun()`](/docs/api-reference/workflow-api/get-run), or it was serialized by an SDK version that predates the field. |

#### Regions on Vercel

On the [Vercel World](/worlds/vercel#multi-region), a key is claimed in the region the new run is pinned to, so keys are unique **per run region**. Two calls with the same key whose runs land in different regions, for example because functions in two regions served them, each create a run. To make a key unique across regions, pass the same [`region`](/worlds/vercel#explicit-region-selection) to every keyed `start()` for that workflow. The Local and Postgres Worlds have no regions, so their keys are unique per workflow.

When a keyed `start()` runs inside a workflow or step without `region`, the child run is pinned to the parent run's region, so a retried step claims the key in the same region as the attempt before it.

#### Good to know

- Retrying a keyed `start()` is safe. If a call fails after its run was created, a retry with the same key returns that run under `'USE_EXISTING'`, or throws `WorkflowRunAlreadyStartedError` naming it under `'FAIL'`.
- A keyed `start()` creates the run before it queues the run, instead of doing both at once, and it doesn't use the background recovery that an unkeyed `start()` uses when creating the run fails transiently. The failure is thrown, so retry the call with the same key.
- When `'USE_EXISTING'` returns a run that is still `pending`, `start()` queues that run's start message again, deduplicated against the original, so the handle never points at a run that nothing will execute.
- The key is recorded on the run as `idempotencyKey`, readable through [`world.runs.get()`](/docs/api-reference/workflow-runtime/world/storage#workflowrun-type).
- Re-running a run from the Workflow CLI or the web UI never copies its key: a re-run always creates a new run.
- If the World's backend creates the run without recording its key, for example a backend that predates idempotency keys, `start()` logs a warning and the key is not enforced for that call.

### Dynamic Workflow Source

<Callout type="warning">
Experimental and off by default. The API may change without a major version bump. The deployment must set `WORKFLOW_EXPERIMENTAL_DYNAMIC_WORKFLOWS=1`, and dynamic runs can only start on the current deployment.
</Callout>

`start()` also accepts a string of workflow **source** instead of an imported function, for orchestration whose shape is only known after you deploy. The source is compiled and stored with the run through the same serialization path as other run payloads, including encryption when the World supplies run key material.

Dynamic source runs with the full privileges of your deployment's functions: it can read environment variables, use the network and filesystem, and call any step in the deployment. Only pass source you trust as much as your own code.

`experimental_dynamic.steps` maps the aliases the source may call to steps that are already registered in your deployment. It keeps ordinary source from calling a step by a name it was not given, but it is not a security boundary. There is no way to define a new step from source.

```typescript
import { start } from "workflow/api";
import { fetchUser, sendEmail } from "./steps";

const run = await start(
  `
async function workflow(input) {
  "use workflow";

  const user = await steps.fetchUser(input.userId);
  await steps.sendEmail(user.email);

  return { ok: true };
}
`,
  [{ userId: "user_123" }],
  {
    experimental_dynamic: { // [!code highlight]
      steps: { fetchUser, sendEmail }, // [!code highlight]
    }, // [!code highlight]
  }
);
```

| Option | Type | Description |
| --- | --- | --- |
| `experimental_dynamic.steps` | `Record<string, StepFunction \| { stepId: string }>` | Required. Registered steps the source may call, keyed by the alias it calls them under. |
| `experimental_dynamic.exportName` | `string` | Name of the async workflow function in the source. Use letters, digits, and `_`, not starting with a digit. Defaults to `"workflow"`. |

The return type is `Run<unknown>`: the source's shape is only known to whatever generated it, so there is nothing to infer. The workflow ID is derived from the source and its step bindings — it cannot be supplied.

A dynamic start throws a `WorkflowRuntimeError`, before anything is written, when the deployment has not opted in, when `deploymentId` targets another deployment (including `'latest'` resolving to one), or when the World's backend does not support dynamic-source storage.

See [Dynamic Workflows](/docs/advanced/dynamic-workflows) for the opt-in, the source rules and limits, the predefined runtime bindings (`steps`, `sleep`, `createHook`), how the code is stored, and the security model.
