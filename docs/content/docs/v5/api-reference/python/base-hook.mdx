`BaseHook` creates a reusable, typed hook definition that keeps the payload
type consistent between hook creation and resumption.

Hooks are low-level primitives that pause a workflow until an external system
sends an arbitrary serializable payload. They are identified by a token and do
not have the HTTP-specific constraints of webhooks.

Subclass `BaseHook` with a Pydantic model or dataclass. Pydantic subclasses
validate received payloads at runtime; dataclass subclasses reconstruct an
instance from the received fields.

```python
import pydantic
from vercel.workflow import BaseHook

class Approval(pydantic.BaseModel, BaseHook):
    approved: bool
    comment: str | None = None
```

## API signature

```python
class BaseHook:
    @classmethod
    def wait(
        cls,
        *,
        token: str | None = None,
        metadata: Any = None,
    ) -> HookEvent[Self]: ...

    async def resume(
        self,
        token_or_hook: str | Hook,
        **kwargs,
    ) -> Hook: ...
```

## wait()

`wait()` creates a hook inside a workflow body and returns a
`HookEvent[Self]` that receives instances of the subclass.

| Parameter | Type | Default | Description |
| --- | --- | --- | --- |
| `token` | `str \| None` | `None` | Token application code uses to find and resume the hook. When omitted, the SDK generates one. Use a deterministic custom token when an external caller needs to know it. |
| `metadata` | `Any` | `None` | Serializable context stored on the hook and returned by `get_hook_by_token()`. It is separate from the resume payload. |

```python
@wf.workflow
async def approval_workflow(request_id: str) -> bool:
    approval = await Approval.wait(token=f"approval:{request_id}")
    return approval.approved
```

`wait()` can only be called from a workflow body. Calling it elsewhere raises
`RuntimeError`.

### HookEvent

`HookEvent[T]` is awaitable, asynchronously iterable, and an async context
manager:

| Operation | Behavior |
| --- | --- |
| `await event` | Suspend until the next payload arrives, then return one `T`. |
| `async for value in event` | Receive multiple payloads in order until the loop ends or the event is disposed. |
| `await event.get_conflict()` | Commit hook registration without waiting for a payload. Return `None` if this run owns the token, or a [`Run`](/docs/api-reference/python/run) for the existing owner. |
| `event.dispose()` | Stop receiving events and release the token. Repeated calls are safe. |
| `async with event` | Dispose the event when the block exits. |

A bare `await event` after disposal raises
[`HookDisposedError`](/docs/api-reference/python/errors#hookdisposederror).
Asynchronous iteration ends normally when the event is disposed.

#### get_conflict()

Use `get_conflict()` before duplicate-sensitive work when the token is also an
idempotency key:

```python
@wf.workflow
async def process_order(order_id: str):
    async with Approval.wait(token=f"order:{order_id}") as event:
        conflict = await event.get_conflict()
        if conflict is not None:
            return {"reused_run_id": conflict.run_id}

        await charge_order(order_id)
        approval = await event
        return {"approved": approval.approved}
```

Creating the `HookEvent` alone does not commit registration. The workflow must
suspend—for example by awaiting `get_conflict()`, awaiting the event, or
starting asynchronous iteration—before an external lookup can find the hook.

<Callout type="info">
Custom hook tokens are the recommended way to coordinate active workflow runs.
Use a deterministic token from your domain, create the hook near the beginning
of the workflow, and call `await event.get_conflict()` before work that depends
on owning the token. See
[Run idempotency](/docs/foundations/idempotency#run-idempotency).
</Callout>

When a conflict identifies the owner, `get_conflict()` returns a `Run` handle
for that run. Older conflict events might not include an owner run ID; in that
case it raises
[`HookConflictError`](/docs/api-reference/python/errors#hookconflicterror).

### Waiting for multiple payloads

`HookEvent` implements `AsyncIterator[T]`, so one hook can receive multiple
payloads in order:

```python
import pydantic
from vercel.workflow import BaseHook

class Message(pydantic.BaseModel, BaseHook):
    text: str
    done: bool = False

@wf.workflow
async def collect_messages(channel_id: str) -> list[str]:
    messages: list[str] = []
    async with Message.wait(token=f"channel:{channel_id}") as event:
        async for message in event:
            messages.append(message.text)
            if message.done:
                break
    return messages
```

Exiting `async with` disposes the hook, which stops future events and releases
the token for another workflow. Call `event.dispose()` to release it earlier.

<Callout type="info">
Python `BaseHook.wait()` currently accepts only `token` and `metadata`; it does
not have the TypeScript API's `experimental_minRetention` option.
</Callout>

## resume()

`resume()` resumes a workflow run by sending a typed payload to a hook
identified by its token or public `Hook` record. Construct the payload and call
the method from runtime code:

```python
result = await Approval(
    approved=True,
    comment="Looks good",
).resume("approval:req_123")

print(result.run_id)
```

| Parameter | Type | Description |
| --- | --- | --- |
| `token_or_hook` | `str \| Hook` | Hook token, or a `Hook` returned by [`get_hook_by_token()`](/docs/api-reference/python/get-hook-by-token). Passing the object reuses the lookup result. |
| `**kwargs` | keyword arguments | Optional arguments passed to Pydantic `model_dump()` or `dataclasses.asdict()` when creating the wire payload. |

`resume()` durably writes the `hook_received` event and only then publishes a
workflow wake. It resolves with the public `Hook` record only after both
operations succeed, in that order.

It raises
[`HookNotFoundError`](/docs/api-reference/python/errors#hooknotfounderror) when
no live hook holds the token, or when the event write is refused because the
hook was disposed or the run ended. If any other error is raised, the event may
already be durable even though dispatching the wake failed; a later wake will
deliver it. Calling `resume()` again can append a second `hook_received` event,
so callers that need at-most-once behavior across requests must deduplicate
their own request key.

Calling `resume()` from a workflow body raises `RuntimeError`; call it from
server-side application code or a step.

## Hook

`Hook` is an immutable dataclass returned by hook lookup and resume operations.

```python
@dataclass(frozen=True)
class Hook:
    token: str
    hook_id: str
    run_id: str
    created_at: datetime.datetime
    metadata: Any = None
```

| Field | Description |
| --- | --- |
| `token` | Application-facing hook token. |
| `hook_id` | Durable ID of this hook registration. |
| `run_id` | ID of the workflow run waiting on the hook. |
| `created_at` | Time the hook was registered. |
| `metadata` | Decoded metadata supplied to `wait()`, or `None`. |

## Dataclass hooks

```python
from dataclasses import dataclass
from vercel.workflow import BaseHook

@dataclass
class Approval(BaseHook):
    approved: bool
```

Hook payload classes must be Pydantic models or dataclasses. Other subclasses
raise `TypeError` when resumed.
