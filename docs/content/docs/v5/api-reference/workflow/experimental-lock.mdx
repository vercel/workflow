Acquires one slot of a distributed semaphore identified by a key, suspending the workflow run until a slot is free. At most `concurrency` runs hold a slot of the same key at once, across every run of every workflow that uses the key.

```typescript lineNumbers
import { experimental_lock } from "workflow";

declare function charge(customerId: string): Promise<void>; // @setup

export async function chargeCustomer(customerId: string) {
  "use workflow";

  await using slot = await experimental_lock(`stripe:${customerId}`, { concurrency: 5 }); // [!code highlight]
  await charge(customerId);
  // released when the scope exits
}
```

Note the two `await`s: `await using` only awaits the release at scope exit, so acquiring the slot needs its own `await`.

<Callout type="warn">
`experimental_lock()` is experimental: its API may change in a minor release, and it will be renamed `lock()` when it is stable. The event log it writes is stable, so runs that use it keep replaying across releases. The first release has these limits:

- **Run-level only.** `experimental_lock()` works in workflow functions, not in steps. To limit a step, wrap its call site, as shown below.
- **World support.** The Local and Postgres Worlds support locks, with the FIFO waitlist described in [Waiting](#waiting). The Vercel World supports them once its backend ships them; until then it declares support only with [`WORKFLOW_VERCEL_EXPERIMENTAL_LOCKS=1`](/docs/configuration/worlds#workflow_vercel_experimental_locks), and the waitlist only with [`WORKFLOW_VERCEL_EXPERIMENTAL_LOCKS_FIFO=1`](/docs/configuration/worlds#workflow_vercel_experimental_locks_fifo). On a World without the `locks` capability, `experimental_lock()` throws [`LockUnsupportedError`](/docs/errors/lock-unsupported) instead of running the section unbounded.
</Callout>

A run waiting for a slot is suspended like a run in `sleep()`: nothing executes, and it adds no events to its event log, however long it waits.

### Returns

A `LockSlot`:

| Property | Description |
| --- | --- |
| `key` | The lock key. |
| `fencingToken` | A number that strictly increases with every grant of this key. See [Fencing tokens](#fencing-tokens). |
| `concurrency` | The concurrency the key enforces, which can differ from the one you asked for (see [Concurrency is fixed by the first run](#concurrency-is-fixed-by-the-first-run)). |
| `release()` | Releases the slot. `[Symbol.dispose]` and `[Symbol.asyncDispose]` do the same, so `using` and `await using` work. Releasing twice does nothing. |

## Examples

### Limiting a step

`experimental_lock()` is called in the workflow function. To cap how many runs execute a step at once, hold the slot around the call:

```typescript lineNumbers
import { experimental_lock } from "workflow";

declare function callProvider(prompt: string): Promise<string>; // @setup

export async function summarize(prompt: string) {
  "use workflow";

  let summary: string;
  {
    await using slot = await experimental_lock("provider:acme", { concurrency: 10 }); // [!code highlight]
    summary = await callProvider(prompt); // a step
  }
  return summary;
}
```

### Releasing explicitly

Call `release()` when the scope does not fit the critical section. A slot that is never released is freed when its run completes, fails, or is cancelled.

```typescript lineNumbers
import { experimental_lock } from "workflow";

declare function reserve(sku: string): Promise<void>; // @setup
declare function notify(sku: string): Promise<void>; // @setup

export async function restock(sku: string) {
  "use workflow";

  const slot = await experimental_lock(`inventory:${sku}`, { concurrency: 1 });
  try {
    await reserve(sku);
  } finally {
    slot.release(); // [!code highlight]
  }
  await notify(sku); // runs without holding the slot
}
```

## How slots are held and freed

A run keeps its slot until it releases it or until the run completes, fails, or is cancelled. There is no default time limit: a slot held across `sleep("7d")` stays held for the seven days. A host crashing does not free the slot, because it does not end the run; the run resumes on another host and still holds it.

### Leases

Pass `leaseTtlMs` to let the World take a slot back after a time limit, even from a run that is still running:

```typescript lineNumbers
import { experimental_lock } from "workflow";

declare function exportAll(): Promise<void>; // @setup

export async function nightlyExport() {
  "use workflow";

  await using slot = await experimental_lock("export:nightly", {
    concurrency: 1,
    leaseTtlMs: 3_600_000, // [!code highlight]
  });
  await exportAll();
}
```

Once the lease expires, another run can be admitted while the first is still inside its critical section, so **two holders can run at once**. Only use a lease when a stuck holder is worse than an occasional overlap, and use the fencing token to reject the stale holder's writes.

### Fencing tokens

Every grant of a key gets a `fencingToken` higher than every earlier grant of that key. Pass it to the systems the critical section writes to, and have them reject a write that carries a lower token than one they have already accepted. Such a write comes from a holder that has since lost its slot to an expired lease.

## Waiting

Runs that find every slot taken wait in a queue per key, in the order they asked. When a slot frees, it is handed straight to the run at the head of the queue, which is woken to take it. A new run never takes a slot ahead of a run that is already waiting.

A run handed a slot has a grace period (60 seconds by default) to take it. If it has not taken it by then, for example because the wake that was sent to it was lost, the next run in the queue gets the slot and the slow run moves to the back of the queue. It keeps its place in the queue and is handed a later slot. As a backstop, a waiting run also checks for its slot on its own every few minutes.

A World caps how many runs can wait for one key (100,000 by default). An acquisition past the cap throws [`LockWaitlistFullError`](/docs/errors/lock-waitlist-full) rather than wait, and you can catch it:

```typescript lineNumbers
import { experimental_lock } from "workflow";
import { LockWaitlistFullError } from "workflow/errors";

declare function charge(customerId: string): Promise<void>; // @setup
declare function deferCharge(customerId: string): Promise<void>; // @setup

export async function chargeCustomer(customerId: string) {
  "use workflow";

  try {
    await using slot = await experimental_lock(`stripe:${customerId}`, { concurrency: 5 });
    await charge(customerId);
  } catch (error) {
    if (LockWaitlistFullError.is(error)) { // [!code highlight]
      await deferCharge(customerId);
      return;
    }
    throw error;
  }
}
```

The refusal is recorded in the run's event log, so the run takes the same branch every time it replays.

A World without the waitlist (the Vercel World without `WORKFLOW_VERCEL_EXPERIMENTAL_LOCKS_FIFO`, or the Local and Postgres Worlds with `WORKFLOW_LOCKS_FIFO=0`) does not queue: waiting runs poll for a free slot with backoff (starting at 1 second, capped at 30 seconds), and whichever polls first after a release wins it.

## Cost and throughput

Waiting is cheap, however long it lasts:

- **Uncontended.** An acquisition that finds a free slot is one write to the World, and adds one event to the run's log.
- **Contended, with the waitlist.** A run that has to wait makes two writes (one to join the queue, one to take the slot it is handed) and is woken once, by the run that released the slot. Its log gains two events, the same however long the queue.
- **Contended, without the waitlist.** Each poll is one write and one queue message, and adds no events to the log.
- **Release.** One write and one event. When someone is waiting, the same write hands the slot on, and the releasing run sends the wake.

Handoffs on one key happen one at a time: the woken run has to resume before it can take its slot, which typically takes from a few hundred milliseconds to a few seconds. A key therefore admits at most roughly `concurrency / (hold time + handoff time)` runs per second. At `concurrency: 1` that is a few runs per second even for a critical section that does almost nothing. For a higher rate, raise `concurrency` or split the work across more keys.

## Concurrency is fixed by the first run

The first acquisition of a key fixes its concurrency. A later acquisition that asks for a different value is admitted against the existing one, and a warning is logged. A key nobody holds takes the next acquisition's value. Use one value per key.

## Deadlocks

A run can hold several locks, but two runs that acquire the same two keys in opposite orders can each wait for the other forever. The runtime logs a warning when a run holds more than one lock. Acquire keys in a consistent order.

## Keys

A key is a string of up to 512 characters, shared by every run in the same World (on Vercel, the same project and environment). Include whatever makes the limit specific, such as a customer, tenant, or provider ID.
