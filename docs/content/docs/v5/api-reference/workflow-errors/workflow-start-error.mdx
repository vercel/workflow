`WorkflowStartError` is thrown when [`start({ hook })`](/docs/api-reference/workflow-api/start#prevent-duplicate-starts) cannot confirm whether its candidate run was queued or admitted, for example because the World timed out. The outcome is unknown, not failed: the candidate may still become the run that owns the token.

```typescript lineNumbers
import { start } from "workflow/api";
import { WorkflowStartError } from "workflow/errors";
import { processOrder } from "./workflows/process-order";
declare const orderId: string; // @setup

async function startOrder() {
  try {
    return await start(processOrder, [orderId], {
      hook: { token: `order:${orderId}`, experimental_minRetention: "1h" },
    });
  } catch (error) {
    if (WorkflowStartError.is(error)) { // [!code highlight]
      console.warn(`Unconfirmed start ${error.runId} (${error.stage}); retrying`);
      return await start(processOrder, [orderId], {
        hook: { token: `order:${orderId}`, experimental_minRetention: "1h" },
      });
    }
    throw error;
  }
}
```

`WorkflowStartError` is only thrown by a start that passes `hook`, and retrying it with the same token is safe while the token is held. If the first candidate was admitted and still holds the token, the retry throws [`HookConflictError`](/docs/api-reference/workflow-errors/hook-conflict-error) with `conflictingRunId` set to it; if it was not admitted, the retry's run becomes the owner. The owner holds the token until it ends, then for any `experimental_minRetention`, unless it [disposes its start Hook](/docs/api-reference/workflow-api/start#take-care-with-the-start-hooks-lifecycle) first, which releases the token at once. A retry after the token is released is admitted as a new run, which is why the example sets a retention that covers its retry window. Either way, a payload you meant for the run can go to [`resumeHook()`](/docs/api-reference/workflow-api/resume-hook) after a conflict, as in [Start or route to the owner](/docs/foundations/idempotency#start-or-route-to-the-owner). Inside a workflow, the `start()` step retries it on its own. It extends `WorkflowError`, not `WorkflowWorldError`: it is not a World response, so World error checks never classify it as permanent.

## API Signature

### Properties

<TSDoc
definition={`
import { WorkflowStartError } from "workflow/errors";
export default WorkflowStartError;`}
/>

`start()` re-confirms an uncertain admission a few times with the same candidate before it throws, so a candidate that was in fact admitted is usually found. It also throws this error when the World answered that admission is switched off without recording a decision, since another copy of the candidate may still be admitted once it is back on.

A start with stream arguments pipes its streams only to a confirmed run. If it throws this error, the candidate may be admitted and waiting on input that nothing will send: cancel it with `getRun(error.runId).cancel()`. That ends the candidate as it would any run, so its token is released (once any `experimental_minRetention` has passed). `cancel()` works even if the run doesn't exist yet: a candidate that was admitted but never created can no longer be created once cancelled. If `cancel()` throws `WorkflowRunNotFoundError`, the World had not decided the candidate at all, and its queued copy can still create the run later. To learn who owns the token in that case, start again with the same token: you either become the owner or get a `HookConflictError` naming it.

`stage` is `"queue"` when the SDK could not confirm that the run was queued, and `"admission"` when it was queued but the SDK could not confirm the World's admission decision. `runId` is the candidate's run ID, for inspection.
