# Lazy `resumeHook()`

## Motivation

`resumeHook()` has to do two things to resume a run: persist a `hook_received` event and dispatch the workflow queue message that re-triggers execution. Doing them one after the other pays two sequential round trips. This change overlaps them on a fast path, cutting resume latency, without weakening the exactly-once guarantee — a backend constraint is what makes the two racing writers safe. Tolerance of a transient direct-write failure falls out for free: because the queue message already carries the payload, a failed event write still resumes the run.

## Design

- On the fast path, `resumeHook()` writes the `hook_received` event and dispatches the workflow queue message **concurrently** (`Promise.allSettled`). Both writers carry the same client-minted `resumeId` idempotency key and a digest of the payload bytes.
- The queue message carries a `hookInput` payload — the dehydrated hook payload plus that `resumeId`, digest, and the hook token — so the workflow runtime can materialize the `hook_received` event itself on replay if the direct write has not landed.
- The backend enforces a `(runId, resumeId)` constraint: the direct write and the queue consumer's re-ensure are collapsed onto exactly one committed event. A byte-different payload reusing a live `resumeId` is rejected; the digest is what lets the backend detect that reuse.
- Replay also deduplicates defensively: `hook_received` events sharing a `resumeId` belong to the same resume attempt, and only the first in the event log is delivered to workflow code, so even a redelivered queue message reaches the workflow exactly once.
- On the fast path, a transient event-write failure (429/5xx) or an expected `resumeId` write conflict is swallowed: the run was already re-triggered via the queue, whose consumer ensures the `hook_received` before replay. A terminal-run rejection still surfaces as `HookNotFoundError`, and a queue-dispatch failure still throws — the run was not re-triggered.
- `resumeHook()` returns `Promise<Hook>` on both paths; the resume outcome is identical to the caller regardless of which path ran.

## Compatibility

The fast path is only taken when **both** the target run's consumer and the live backend independently attest support for the `(runId, resumeId)` dedup protocol — the consumer via a per-run execution-context marker, the backend via a fresh, response-only capability on the by-token hook lookup. When either attestation is absent (older deployment, kill switch, or rollback), or the payload is too large to inline on the queue message, `resumeHook()` transparently falls back to the original sequential path (event write first, then dispatch). The fast path can also be disabled outright with `WORKFLOW_DISABLE_LAZY_HOOK_RESUME=1`. Because runs keep executing on the deployment they were created on, and both attestations are re-evaluated per resume, every rollout and rollback direction degrades safely.
