# Review: single orchestrator (spec 9)

<Callout type="warn">
This is a temporary review document for the pull request that introduces spec version 9. It is written for the people reviewing that PR and will be removed before merge. The user-facing description of the change is [Single orchestrator](/docs/changelog/single-orchestrator).
</Callout>

## 1. Overview

The PR changes how a run is driven. Before it, several invocations of a run could decide what the run does next, and the World kept step and wait rows that refused a second start or a second outcome. After it, runs at spec version 9 have one decider: the run's orchestrator. Step invocations only run step bodies and report outcomes. The World no longer keeps step state to check writes against; it fences the orchestrator as the only in-band writer instead.

The PR does four things:

1. **Spec 9 runtime.** A new orchestrator under `packages/core/src/runtime/spec9/`.
2. **Spec 8 kept side by side.** The previous orchestrator moves to `packages/core/src/runtime/spec8/`, and each delivery is routed by the run's stored spec version.
3. **World contract changes.** A required in-band fence for Worlds that declare spec 9, a `{ timeoutSeconds: 0 }` handoff every World implements for spec 9 runs, in-band event time and per-entity batch order as part of the spec 9 storage contract, and optional coalescing.
4. **Vercel queue serialization.** On Vercel, spec 9 runs are kept to one orchestrator invocation by a Vercel Queues concurrency key per run on the existing `__wkf_workflow_*` topic. Spec 8 runs keep `main`'s queue topology and behavior. This needs `@vercel/queue` 0.9.0 or later, the first release with the experimental concurrency key and lease handoff support.

## 2. The spec 9 model

### One decider

Only the orchestrator writes decisions: `step_created`, `wait_created`, `wait_completed`, hook and attribute events, `run_completed` and `run_failed`. It also runs inline steps. A background step's own invocation writes only that step's `step_started` and outcome, then sends the orchestrator one plain wake, without reading the log. On a plain first delivery of its message, a step that allows retries starts its body while its `step_started` is in flight, and writes the outcome only once that start committed (section 7, "Background step bodies start before their start commits").

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function checkout(orderId: string) {
  "use workflow";
  const order = await loadOrder(orderId);   // inline: run by the orchestrator
  const charge = await chargeCard(order);   // inline
  await sendReceipt(charge);                // inline
  return charge.id;
}

async function chargeCard(order: Order) {
  "use step";
  return await payments.charge(order.total);
}
```

A run of `checkout` typically completes in one orchestrator invocation. If a step fails with a retryable error, its retry moves to its own queue message, and that step invocation only reports the outcome. The orchestrator decides what happens next. `main` does the same with an inline step's retry. The step's message then owns its remaining attempts: the queue holds the backoff instead of a live invocation, and the at-most-once and retention rules for retries are enforced on that one message. Retrying a short backoff inline, within the inline deadline, is possible and is not implemented.

### The in-band fence

Every orchestrator write is **in-band** (`inBand: true`). It carries `expectedSeqInBand`, the orchestrator's count of in-band positions, which it took from the `snapshot` of its log load. The World refuses a stale count with `InBandSupersededError` (HTTP 412). Two live orchestrators of one run can therefore never both write. The refused one stops writing and running inline steps, sends the queue messages its own committed writes still owe, and acknowledges its message (section 5).

**Example: an invocation that stalls past its lease.** An orchestrator's event loop blocks for longer than its queue lease (for example, a CPU-heavy inline step). The queue redelivers the run's message, and a second orchestrator starts. The second one writes first and moves the count. The first one wakes up, tries to write its next decision, gets a 412, and stops. Nothing is written twice, and the second one drives the run on.

### Step and wait events are plain appends

The world-vercel backend no longer writes step and wait rows in the same transaction as each event. Step state is folded from the log when it is read. Replay treats any event for an entity after its terminal event as inert, which is what lets a late duplicate append be harmless.

### Run-ahead

When no other writer could change what the workflow does next, the orchestrator hands an inline step's outcome to the workflow before the write commits ([`WORKFLOW_RUN_AHEAD_DEPTH`](/docs/configuration/runtime-tuning#workflow_run_ahead_depth) outcomes at most). The writes still go out in decision order. An awaited hook, an `AbortController`, a step running elsewhere, or a wait due within the invocation makes the orchestrator wait for its writes first. Run-ahead exists on the node engine only (section 7, "QuickJS").

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function pipeline(input: string) {
  "use workflow";
  const a = await stepA(input); // stepB starts while stepA's outcome commits
  const b = await stepB(a);
  return await stepC(b);
}
```

### Turbo

On a run's first delivery, the log holds only `run_created`. The orchestrator writes `run_started` without waiting, starts the in-band writer from the count after creation instead of loading the log, and starts the first inline step bodies before their start commits. A redelivery, or a coalesced re-run of the first delivery (section 5), takes the normal path and loads the log.

### `maxRetries: 0` is at most once

A background step keeps one queue message for its whole life and retries in place on it. Any delivery other than a plain first delivery reads the log before running the body.

{/* @skip-typecheck - illustrative workflow */}
```typescript
async function sendWireTransfer(amount: number) {
  "use step";
  await bank.transfer(amount); // must never run twice
}
sendWireTransfer.maxRetries = 0;
```

If the step's invocation crashes after the transfer but before `step_completed`, the redelivery reads the log, sees a started attempt with no outcome, and fails the step instead of running the body again.

## 3. Spec 8 and spec 9 side by side

### Per-run routing

Each delivery is routed by the spec version of its run, resolved in this order:

1. `runInput.specVersion` on a first delivery.
2. `runContext.specVersion` on a step message.
3. The `runSpecVersion` hint on the message. `queueMessage`/`queueMessages` stamp it on every message for a run, and the direct `world.queue` call sites (`runs.ts`, `hook-wake.ts`, `resume-hook.ts`) set it explicitly.
4. A per-process cache of run spec versions (10,000 entries).
5. `runs.get`, and if the run is not found, the World's own spec version.

Runs at spec 9 or later go to `runtime/spec9`, and anything earlier goes to `runtime/spec8`, which is the previous orchestrator.

**Example: a spec 8 run continuing after a World upgrade.** A long approval workflow is started on a World that declares spec 8, then sleeps for a week.

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function approval(requestId: string) {
  "use workflow";
  await notifyApprover(requestId);
  await sleep("7d");
  return await escalate(requestId);
}
```

During that week the app upgrades to a World that declares spec 9. When the sleep ends, the run's stored spec version is still 8, so the delivery goes to the spec 8 orchestrator, which reads the spec 8 log as it always did. New runs started after the upgrade are spec 9. `world-testing` has a test that does exactly this with world-local (`spec8-upgrade.test.ts`).

### Choosing the spec for new runs

`mintedSpecVersion()` returns the current version (9), or 8 when [`WORKFLOW_SPEC_VERSION=8`](/docs/configuration/runtime-tuning#workflow_spec_version) is set. First-party Worlds call it when they are created, so the variable also works as a kill switch: setting it makes new runs spec 8 without touching runs already in flight. `WORKFLOW_SEALED_LOG` is no longer read: an app that sets `WORKFLOW_SEALED_LOG=0` now mints spec 9 runs, and the runtime warns once that the variable is ignored.

### Writers outside the orchestrator

Writes made outside a delivery (cancel, resume, wake-up, external attributes) stamp the run's own version (`specVersionForRunWrite(run.specVersion)`), not the SDK's current one. A spec 8 run never receives a spec 9 event. The in-band fence is required only when the World declares spec 9 (checked in `start()`), or when the run itself is spec 9.

### Code layout

- `packages/core/src/runtime.ts`: the shared entrypoint. It parses the message, resolves the run's spec, and hands the delivery to one orchestrator through a small `Orchestrator` interface (`runDelivery`, `countsTowardMaxDeliveries`, `writeMaxDeliveriesFailure`).
- `runtime/spec8/`: the previous orchestrator and its tests.
- `runtime/spec9/`: the single orchestrator.
- Shared: `runtime/delivery.ts`, `suspension-hooks.ts`, `quickjs-pending-ops.ts`, `hook-creation.ts`, `step-streams.ts`, `quickjs-delivery-shared.ts`, `step-single-flight.ts`, and the end-of-run drain in `workflow.ts`. Each spec passes its own options, such as the event spec version to stamp, into the shared code.

The delivery bodies and step executors were left separate: they are mostly different code, and sharing them further would add more parameters than it removes.

## 4. World contract changes

| Surface | Change |
|---|---|
| `capabilities.inBandFence` | **Required** for a World that declares spec 9. The runtime refuses such a World without it, in `start()` and at the start of every spec 9 delivery. This is the only new capability. |
| Handler result `{ timeoutSeconds }` | Its meaning now depends on the message's run, read off the payload (`messageRunSpecVersion`, `isSingleOrchestratorMessage` in `@workflow/world`). Spec 9 run: `n > 0` redelivers the same message after `n` seconds; `0` is a **handoff** (below). Spec 8 and earlier: unchanged from `main`, continue after `n` seconds by a redelivery or a new message (world-vercel sends a new message, up to 23 hours out). An unstamped message counts as spec 8. |
| Handoff, `{ timeoutSeconds: 0 }` on a spec 9 run | New, required of every World. Deliver the same message again at once and do not count this delivery toward `attempt`. world-vercel uses the Vercel Queues lease handoff. world-local redelivers the same message with `attempt` unchanged, behind any orchestrator message of the run already waiting at its gate; world-postgres reschedules it on a new Graphile job with no delay, behind jobs already on the run's queue, and restarts `attempt` (section 7). A fence-refused delivery acknowledges instead (section 5). |
| `meta.attempt` | `deliveryCount` less the deliveries that followed a handoff and less coalesced re-runs. The delivery cap counts it. On a World with neither it equals `deliveryCount`. |
| `meta.deliveryCount` on a coalesced re-run | The delivery's count plus the re-run number, so the runtime treats the re-run as a redelivery (turbo off, log read). There is no separate re-run field. |
| `meta.invocationStartedAt` | New, optional. Epoch milliseconds at which the function invocation began. world-vercel passes it to every coalesced re-run, and the spec 9 delivery measures its inline deadline from it. |
| Incomplete skipped-slot report | `hasMore: true` on the write's `EventResult` or `EventBatchResult`. world-vercel maps the backend's `reportIncomplete` to it. |
| In-band `occurredAt` as `createdAt` | Part of the spec 9 storage contract, no capability. The runtime still checks each speculative write's stored time and turns run-ahead off for the World on a mismatch. world-postgres now stores it (it did not before, so run-ahead was off there); the shared fence conformance suite checks it. |
| Per-entity `createBatch` order | Part of the spec 9 storage contract, no capability. world-vercel's backend orders batches; world-local and world-postgres have no `createBatch`. |
| `step_started.creatorMessageId` | Removed. Only a background step's `step_created` and a `wait_created` record their creator; creator rules never read an inline step's. |

world-local and world-postgres declare the fence and serialize orchestrator deliveries per run for spec 9 runs only, with an in-process per-run gate and a per-run Graphile named queue. Spec 8 runs are not serialized there, as on `main`: a spec 8 delivery can hold an inline step until another wake of the same run aborts it, and run-level exclusion would hold that wake back. Neither coalesces, and both mint spec 9 runs by default (section 7, "world-local and world-postgres do not coalesce").

## 5. Vercel queue serialization

### Before (`main`)

All flow messages, orchestrator and step, go to one topic per workflow name (`__wkf_workflow_<name>`). Its consumer has no `maxConcurrency`, so two orchestrator invocations of one run can run at the same time, and the World's step and wait rows refuse the loser's duplicate writes.

`WORKFLOW_SEQUENTIAL_REPLAYS=1` is an opt-in on `main`. It gives each run its own topic (`__wkf_workflow_<name>_<runId>`), each step its own topic, and the flow trigger `maxConcurrency: 1`, so a run has at most one orchestrator invocation at a time.

This PR keeps all of that for spec 8 runs: the shared unkeyed topic, the new-message continuation of a `{ timeoutSeconds }` result, and the opt-in.

### After, for spec 9 runs

- **Same topic and trigger as `main`.** Spec 9 messages go to `__wkf_workflow_<name>`, next to spec 8 messages, and flow routes keep `main`'s single trigger with no `maxConcurrency`. An earlier version of this PR had a second `__wkf_keyed_*` topic family and trigger, because it had moved spec 8 runs onto `maxConcurrency` topics and Vercel Queues refuses (400) a keyed send to a topic a `maxConcurrency` consumer reads. Restoring spec 8's topology removed the need.
- **Under `WORKFLOW_SEQUENTIAL_REPLAYS=1`.** The opt-in keeps `main`'s per-run, per-step and per-probe topics and `maxConcurrency: 1` trigger for every run. Spec 9 messages are then sent **unkeyed** (a keyed send would get the 400): the per-run topic serializes the orchestrator, nothing is coalesced, and handoffs still work, since a lease handoff does not depend on a key.
- **Keyed vs unkeyed.** Orchestrator messages carry the run id as the concurrency key. Step messages and health checks carry none. A spec 9 run's step dispatches now share one topic, so a fan-out's step messages go out in parallel queue batch requests of up to `STEP_DISPATCH_QUEUE_BATCH_SIZE` (16) messages each (`enqueueStepMessages`, `spec9/delivery.ts`, node engine).
- **One delivery per run.** Vercel Queues keeps at most one delivery per key active. A keyed message claimed while another delivery holds the key is **coalesced**: it is never delivered, and it is counted on the holder.
- **Coalesced re-runs.** The holder's acknowledgment is refused while coalesced messages it has not covered are pending. The client then runs the handler again within the same delivery, with the lease still held (`experimental_maxCoalescedReruns`, 32 in world-vercel), and acknowledges again covering the reported count. world-vercel reports each re-run with the next `deliveryCount` and the same `attempt`, so the runtime treats it as a redelivery: turbo is off and the log is read.
- **Which runs are spec 9.** world-vercel decides from the payload alone, at send and at delivery alike: `runInput.specVersion`, `runContext.specVersion` or the `runSpecVersion` hint, which every runtime that creates spec 9 runs stamps. A message without a stamp is treated as spec 8 (unkeyed, new-message continuation). An unstamped spec 9 orchestrator message is then fenced but not serialized. Every spec 9 send site in this runtime names the run's spec version itself; producers outside it do not (section 7, "Spec detection").

**Example: a fan-out whose completions coalesce.**

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function resizeAll(urls: string[]) {
  "use workflow";
  const sizes = await Promise.all(urls.map((url) => resize(url))); // 50 background steps
  return sizes;
}
```

The 50 step invocations finish over a few seconds, and each one sends the orchestrator one plain wake, without reading the log first. While the orchestrator is running, every wake is coalesced into it. When it finishes a pass and tries to acknowledge, it is told how many wakes arrived, reads the log once, and sees all the outcomes that landed. The run is woken a few times instead of 50, and there is never a second orchestrator to refuse. Without coalescing (world-local, world-postgres, and world-vercel under `WORKFLOW_SEQUENTIAL_REPLAYS=1`), each of the 50 wakes is its own orchestrator delivery, one after another (section 7).

Coalescing is safe because every producer commits what the wake is for (a step outcome, a `hook_received`) before it sends the wake, so the holder's next read sees it. The exceptions are `run.wakeUp()`, which is best-effort (section 7), and a timer, which names its wait ("Timers" below).

### Handoffs

A spec 9 delivery that has to end before the run's work is done hands its message off (`{ timeoutSeconds: 0 }`) instead of sending itself a new one, on every World. On a keyed topic, a message the orchestrator sent itself would be coalesced into its own delivery and run again in the same invocation, which defeats the point of ending it. On world-vercel, the client sends `Vqs-Experimental-Handoff: 1` on the lease change, Vercel Queues redelivers the same message at once, and the handed-off delivery counts toward neither its backoff nor `maxAttempts`. Handoffs are used for:

- the invocation deadline (node engine);
- inline step stream writes still flushing in the background;
- a hook conflict the workflow has to consume in a fresh pass;
- QuickJS exits on the replay budget, an elapsed wait, or an unread write of its own.

**Example: a long workflow crossing the inline deadline.**

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function nightlyReport() {
  "use workflow";
  for (let day = 0; day < 365; day++) {
    await aggregateDay(day); // inline steps, about 2 seconds each
  }
}
```

The run needs about 12 minutes of inline work, longer than one invocation's inline budget. Near the deadline, the orchestrator ends its delivery and the next invocation continues from the log: with a handoff when an inline step runs into the deadline, or through one background step when the inline-start margin comes first (section 7). A year of handoffs counts as zero attempts, so the run is not failed by the delivery cap (`WORKFLOW_MAX_QUEUE_DELIVERIES`, 48 by default).

**Example: a webhook whose response stream is still flushing.**

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function webhookWorkflow() {
  "use workflow";
  const webhook = createWebhook();
  for await (const request of webhook) {
    await respond(request);
  }
}

async function respond(request: RequestWithResponse) {
  "use step";
  await request.respondWith(new Response("ok"));
}
```

`respondWith` writes the HTTP response into a stream that is flushed in the background. The step can return before the flush finishes. The orchestrator then ends its delivery so the flush can finish in `waitUntil`, and continues in a handoff. This is the path the e2e `webhookWorkflow` test exercises.

### Creator rules count attempts

Some rules depend on whether a delivery is a redelivery of the message that created a step or a wait (for example, re-enqueueing a background step whose dispatch was lost in a crash). These now count `attempt`, so a delivery after a handoff behaves like the new message it replaces and does not re-send every step that has not started yet. A delivery after a crash still counts as a redelivery.

### No orchestrator message carries state the log needs

A coalesced message is never delivered, and its holder only re-reads the log, so a message may be coalesced only if losing its payload loses nothing the log does not hold. Every orchestrator message is keyed except an intermediate hop of a long wait's timer. Earlier heads of this PR sent three kinds unkeyed (`QueueOptions.coalesce: false`), because they carried state that existed only on the message. All three are gone or demoted, and timers are the fourth row:

| Message | Message-only state | Now |
|---|---|---|
| Replacement after a fence refusal or a run-ahead stop | `replacesMessage`: the creator identity of the replaced message | Removed. A fence-refused delivery sends the messages its own writes owe and one plain keyed wake, and acknowledges. A run-ahead stop continues in place. |
| Replay-divergence recovery | `replayDivergence`: the divergence history | Removed for spec 9. The delivery replays again in place and counts divergences in memory. Spec 8 still sends it. |
| `run.wakeUp()` | `completeWaits`: the waits to complete now | Keyed, best-effort (section 7). |
| Timer | `waitContinuation`: the wait it is for | A final timer (due with its wait) is keyed: coalesced, the holder's re-run sees the wait due, and the delivery that completes a wait arms its chain's next timer. An intermediate hop of a wait longer than one queue delay is unkeyed and never coalesced ("Timers" below). |

`QueueOptions.coalesce` and the payload's `replacesMessage` are removed from `@workflow/world`, with `MAX_MESSAGE_REPLACEMENTS` and `WORKFLOW_FENCE_REDELIVERY_DELAY_SECONDS`.

**Fence refusal.** A delivery whose in-band write is refused keeps, from its writer's accepted events, what those writes owe the queue: the message of each background step whose `step_created` it committed (trailing fan-out batches included), the message of each inline step whose retry it moved to the background with a committed `step_retrying`, and the timers of the wait chains it owns ("Timers" below). It sends exactly the ones it has not sent, with their usual idempotency keys. On a redelivery of its message it also sends what the creator rules re-send for an earlier delivery of it. If it dies before those sends, its message is redelivered (attempt 2), and the creator rules re-send them; both paths have tests.

Then it sends one plain orchestrator wake (run id, trace carrier, spec stamp; no delay, no message-only state) and acknowledges. A refusal does not prove that another orchestrator is running. The world-vercel backend also answers 412 `in-band-superseded` when it sealed the writer's own position (its put outlived the staleness bound, `appendEventRow`), and a 409 it returns after it allocated the position moves `seqInBand` past the writer's count, so the writer's next write gets the 412. In both cases nothing else is queued for the run (section 7, "A refused write with no other orchestrator stranded the run"). What the wake costs:

- **world-vercel, a live winner holds the key:** coalesced into the winner, which reads the log anyway. Free.
- **world-vercel, this delivery holds the key:** coalesced into itself, so its acknowledgment is refused and it runs again from a fresh load in the same invocation. A delivery refused on every pass is bounded by the client's 32 re-runs (`MAX_COALESCED_RERUNS`), after which `@vercel/queue` throws `ConcurrencyCoalescedPendingError` and world-vercel hands the message off (checked in `@vercel/queue`'s `acknowledgeCoveringCoalesced` and world-vercel's `retry` hook).
- **world-vercel, no holder:** delivered as a new orchestrator delivery.
- **world-local, world-postgres:** delivered after the running delivery.

The wake is keyed, so it cannot reintroduce the replacement storm (section 7): it never runs next to a keyed holder, and a refusal sends at most one of it.

**Run-ahead stop.** The delivery lets the outcomes a hazard stop still allows commit, sends what its writes owe (as above), takes a fresh writer, reloads the log and replays from cold in the same delivery, with run-ahead off for the rest of the delivery. With run-ahead off a second stop cannot occur; `MAX_RUN_AHEAD_RESTARTS` (1) still bounds the restarts, and a stop past it hands the message off. The inline deadline applies to the restarted pass as to any other.

**Replay divergence.** The delivery discards the VM, reloads the log and replays from cold in a fresh VM, up to `WORKFLOW_REPLAY_DIVERGENCE_MAX_RETRIES` times, then fails the run with the same `CORRUPTED_EVENT_LOG` error and message as before. The first natural write after a recovered divergence still carries `replayDivergenceCount`. Across crashes and redeliveries the count starts again, and the delivery cap bounds it. The QuickJS engine had no divergence recovery before this change and has none after it.

### Timers

A sleep's timer is a delayed message carrying `waitContinuation` (the wait it is for). Two rules keep a timer that Vercel Queues coalesces from losing anything:

- **The delivery that completes a wait arms the next one.** A delivery arms the earliest open wait of each wait chain it owns: the waits its own message created, and the waits created with any wait whose `wait_completed` it committed (`ownedWaitChains`, `waitTimersToArm` in `spec9/creator-rules.ts`), plus its own wait when it is a timer delivered before its wait is due. It arms a completed wait's chain right after the completion, not at suspend, because the delivery may end in a handoff first and the next delivery does not know what this one completed. A redelivery of a timer message (a crash) also owns its timer's chain.
- **Hops before the last are unkeyed.** A wait longer than one queue delay (`WAIT_CONTINUATION_MAX_DELAY_SECONDS`, 23 hours) is reached in hops. Every hop but the last carries the wait's deadline (`waitContinuation.resumeAtMs`), which `isIntermediateWaitHop` in `@workflow/world` reads, and `orchestratorRunIdOf` leaves out, so world-vercel sends it with no concurrency key and world-local and world-postgres do not hold it behind the running delivery. Its delivery reads only the run's status, writes nothing, sends the next hop and acknowledges, so it is safe next to a live orchestrator. The last hop is an ordinary keyed timer: coalesced, the holder's re-run sees the wait due and completes it, and the rule above arms the next.

If the lock was released before a keyed timer came due, Vercel Queues compares the timer's due time, not its send time, with the release, so the timer is delivered normally.

## 6. Decisions and tradeoffs

### The PR was not split into "format" and "capability" halves

A split was considered: ship spec 9 as an event-format change only (the creation-bearing `step_started`, the inert-after-terminal rule, the new fields), and gate the single orchestrator on a World capability. It was not done because:

- The format changes exist because the World stops keeping step state, and that is only safe with one fenced writer.
- The World has to know per run whether to keep step rows. A process-wide capability can't express that; a stored per-run flag would be a second spec version with another name.
- A capability check would hand spec 8 runs created before an upgrade to the new orchestrator, and those runs have no in-band count from creation.

The PR can still be reviewed and released in stages: readers first (raise `SPEC_VERSION_MAX_SUPPORTED` while minting stays at 8), then the backend, then minting.

### Spec 8 keeps its code, side by side

Spec 8 runs keep the previous orchestrator unchanged instead of being migrated. The cost is two orchestrators in one package until spec 8 is dropped. The benefit is that runs in flight during the upgrade finish on the code that started them, and `WORKFLOW_SPEC_VERSION=8` is a working kill switch.

### Spec 8 messages are not keyed

Spec 8 messages carry no concurrency key. Keying them would serialize them, and a coalesced wake would become a re-run inside the same invocation instead of a separate delivery, which changes spec 8 behavior. Spec 8 runs keep `main`'s shared, unserialized topic, its new-message continuation and its opt-in.

### `{ timeoutSeconds: 0 }` means handoff, by run spec

The handoff could have stayed a flag on the result (`handoff: true`) behind a capability. It is the plain `{ timeoutSeconds: 0 }` instead, with the meaning chosen by the message's run: a handoff for spec 9 messages, `main`'s continuation for earlier ones. That leaves no capability for a World to forget and no second result shape. The cost is that a World must read the run's spec off the message, which `@workflow/world` provides. On world-local and world-postgres, spec 9 continuations that used to be new orchestrator messages are now handoffs of the same message: the next delivery keeps the message's id (and so its creator identity) and the attempt count of the delivery that handed off, as on world-vercel.

### Per-run and per-step topics are dropped for spec 9

With the key doing the serialization, a spec 9 run uses one topic per workflow name. This reduces the number of topics and lets a fan-out's step messages share batch requests (16 messages each, sent in parallel). The tradeoff is that the key is now the only serialization: when it is not applied, spec 9 runs have none and only the fence keeps them safe. That happened once, through a client bug (section 8), and would happen for a spec 9 message sent without its spec stamp (section 7, "Spec detection").

### Coalesced re-runs instead of new deliveries

A re-run reads the log in the same invocation, so a burst of wakes costs one more pass instead of one cold invocation per wake. The cost is that the re-run is bounded by the invocation's deadline and by the re-run cap (section 9).

## 7. Known gaps and risks

### `run.wakeUp()` is best-effort while an orchestrator runs (decided)

On spec 9, `run.wakeUp()` names the waits to complete on an orchestrator message (`completeWaits`), so the orchestrator writes `wait_completed` in-band. The message is an ordinary keyed orchestrator message. On world-vercel, one that arrives while an orchestrator delivery of the run holds the key is coalesced into it and lost: the re-run reads only the log, and the sleeps run their full length while `wakeUp()` reports them in `stoppedCount`, which counts the waits it asked to complete. That is accepted. A wake-up is useful when the run is suspended on its sleeps, and then nothing holds the key and the message is delivered on its own. world-local and world-postgres never coalesce: their per-run gate delivers the message after the running delivery, and a world-local delivery does not linger past its work (no `events.subscribe`), so `@workflow/vitest`'s `waitForSleep()` and `wakeUp()` keep working. Tests cover both queue shapes, for both engines.

This also removes the two bugs the unkeyed wake had when an orchestrator was already running: a wake delivery that lost the fence dropped `completeWaits` in its replacement, and one that won it refused the running orchestrator's `step_completed`, so the open inline step's body ran a second time. A keyed wake never overlaps the running delivery.

The alternative, `wakeUp()` writing `wait_completed` out-of-band the way `resumeHook()` writes `hook_received`, needs a backend change: the world-vercel backend refuses an out-of-band `wait_completed` on spec 9 runs on purpose, with 409 `wait-completion-in-band-only`. An out-of-band completion could land below events the orchestrator already acted on while running ahead, and a later replay would order them differently.

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function digest(userId: string) {
  "use workflow";
  const first = await fetchUpdates(userId); // run-ahead: the outcome reaches
  const timeout = sleep("1h");              // the workflow before it commits
  const winner = await Promise.race([timeout, nextUpdate(userId, first)]);
  return winner;
}
```

If the `wait_completed` committed below `fetchUpdates`'s outcome, the live run saw the step first and the replay sees the wait first. A reliable wake-up under a running orchestrator would be a new out-of-band "wake requested" event, written like `hook_received` and turned into an in-band `wait_completed` by the orchestrator. Not implemented.

Callers of `run.wakeUp()`: the public API (`Run.wakeUp()`), `@workflow/vitest`'s `waitForSleep()` pattern, the local observability UI (`packages/web`), and the Vercel dashboard's wake-up action. The dashboard calls `wakeUpRun` from a pinned `@workflow/core` release that writes `wait_completed` out-of-band, which the backend refuses on spec 9 runs. Its wake-up therefore does not work on spec 9 runs until it moves to a release with this change.

### A second concurrent sleep lost its timer (fixed twice)

A spec 9 delivery arms one timer per wait chain, for its earliest open wait. In `await Promise.all([sleep("1h"), sleep("2h")])`, a timer delivery used to own only its own wait, so the first timer completed the first sleep and armed nothing for the second, and the run stayed suspended until something else woke it. e2e did not catch it: its only parallel sleeps have equal durations, which one timer covers.

The first fix let a timer delivery own the waits created with its own wait. That still failed on world-vercel, as a reviewer showed with scratch tests on both engines: a timer is keyed, so one that comes due while a hook or step wake holds the run is coalesced into that delivery, which completes the first sleep and, not being the timer, armed nothing. The same loss hit a sleep longer than one queue hop when an intermediate hop was coalesced: the holder found the wait not yet due and did not re-arm it.

Now the delivery that completes a wait owns its chain, whatever message it is, and intermediate hops are unkeyed ("Timers", section 5). The harness's `coalesce` mode can now coalesce a delayed message that comes due while a delivery holds the key (`AppendOnlyWorld.comeDue`), and `spec9/wait-chains.runtime.test.ts` covers both cases on both engines; each fails with the earlier rule or with keyed hops. While fixing it, a second gap showed up and is fixed too: a delivery that owned waits of two chains armed only the earliest of all of them, so the other chain was left without a timer once that one completed. Timers are now armed per chain.

Residual risks: a delivery that commits a `wait_completed` and dies before its next send leaves that chain without a timer unless it was the timer's own delivery (whose redelivery owns the chain); and if world-vercel's `VERCEL_QUEUE_MAX_DELAY_SECONDS` is set below the runtime's hop length, a final hop is clamped and arrives early, and a coalesced early final hop is not re-armed. Neither is covered by a test.

### A refused write with no other orchestrator stranded the run (fixed)

A fence-refused delivery used to send what its writes owed and acknowledge with no wake, on the premise that the refusal meant a live winner. The world-vercel backend also refuses a write whose own position it sealed (`appendEventRow`, when the put outlived the staleness bound) and, after a 409 that allocated, the writer's next write; then no other orchestrator exists and nothing is queued, so the run stopped until an outside event woke it. A reviewer reproduced it on both engines. The delivery now sends one plain keyed wake before acknowledging (section 5, "Fence refusal"). Tests in `spec9/fenced-overlap.runtime.test.ts`, both engines: a self-refused write completes the run on a serializing queue and, on a coalescing queue, within the same delivery; a delivery refused on every pass hands off once its coalesced re-runs run out; the existing overlap tests still have one orchestrator doing the work, with the loser's wake finding the run done.

### Step bodies a run-ahead stop can run twice

When a hazard stops run-ahead, a step whose body started ahead of its creation, and whose creation the stop then refused, has no committed start, so the restarted pass runs its body again. Per-entity batch order is now part of the spec 9 contract, so one refused speculative batch can carry up to `WORKFLOW_RUN_AHEAD_DEPTH` such steps (10 by default): up to that many bodies can run twice per stop, where earlier heads of this PR ran at most one. A stop needs the speculative writes to fail or be overtaken: a refused entry in a speculative batch, a World that did not store a write at its `occurredAt`, or another writer's path-changing event landing below them (`spec9/delivery.ts`, `runAheadHazard` in `spec9/run-ahead.ts`). An awaited hook is not one of them: it makes the boundary path-changing, so the orchestrator waits for its writes instead of running ahead. Which real-world writers can still produce a stop is not verified; see [Run-ahead and turbo](/docs/changelog/single-orchestrator-diagrams/run-ahead-and-turbo). A step declared with `maxRetries: 0` never starts before its start commits (`mayRunBeforeItsStart` in `spec9/step-executor.ts`), so it is never one of the steps run twice.

### An inline `maxRetries: 0` step could run twice after an orchestrator crash (fixed)

A redelivered orchestrator re-runs an open inline step with the next attempt. Only a background step's own message checked the retry budget before running the body (`failStepForExhaustedRetries` in `spec9/step-handler.ts`), so an inline `maxRetries: 0` step whose orchestrator died between its `step_started` and its outcome ran its body a second time on the redelivery. Reproduced on both engines with the test harness. `executeStep` now fails an attempt past `maxRetries + 1` without running the body, for inline and background steps alike, which also covers a winner re-running a refused overlap's open inline step (commit `75ddd45207`; test `runs an inline maxRetries: 0 step at most once across an orchestrator crash` in `spec9/orchestrator.runtime.test.ts`, both engines).

### Background step bodies start before their start commits (behavior change)

On a plain first delivery of a background step's message (`deliveryCount` 1, no `stepAttempt` above 1, so no log read), a step that allows retries starts its body while its out-of-band `step_started` is in flight, as turbo already does for a first delivery's inline steps (`forceOptimisticStart` in `spec9/step-handler.ts`, commit `83ee22003e`). The outcome is written only once the start committed. A start that is throttled (429), refused as too early, or refused because the run ended (`RunExpiredError`, for example a cancelled run) discards the body's outcome: a throttled start redelivers the message after the backoff, a run-ended start acknowledges. Any other failed start throws its error out of the delivery, as an awaited start would.

What changes for users: on a cancelled run, or while the World throttles, such a body now runs before the refusal arrives, and its side effects happen even though its outcome is dropped. Before this change the awaited start was refused first and the body never ran. A `maxRetries: 0` step keeps the awaited start (`mayRunBeforeItsStart`), and so does every delivery that reads the log (a redelivery, a retry's message). [`WORKFLOW_OPTIMISTIC_INLINE_START=0`](/docs/configuration/runtime-tuning#workflow_optimistic_inline_start) turns it off for background steps as well as inline ones.

### world-local and world-postgres do not coalesce (open)

Both mint spec 9 runs by default (`mintedSpecVersion()` in `packages/world-local/src/index.ts` and `packages/world-postgres/src/index.ts`). Both serialize a spec 9 run's orchestrator deliveries, but neither coalesces orchestrator messages, so every background completion's wake becomes its own orchestrator delivery, run one after another behind the run's gate. A 97-step fan-out sends 97 wakes and gets 97 orchestrator deliveries. A delivery that finds the log tail at the position this process last consumed acknowledges after one tail read (`consumed-position.ts`); every other one loads the full log and replays. world-vercel under `WORKFLOW_SEQUENTIAL_REPLAYS=1` has the same shape: its spec 9 messages are unkeyed on per-run topics, so nothing is coalesced and each wake is one function invocation.

What they implement today of the handoff semantics, from the code:

| | world-local | world-postgres | world-vercel (keyed) |
|---|---|---|---|
| `{ timeoutSeconds: 0 }` on a spec 9 message | Same message again, `attempt` unchanged (up to 10,000 handoffs), but the delivery releases the run gate and takes it again in FIFO order, so wakes already waiting run first | A new Graphile job on the run's named queue with no delay, behind jobs already queued; `attempt` restarts (section 7, "world-postgres resets `attempt`") | Lease handoff, same message at once |
| A message for a run whose delivery is running | Waits behind the gate, delivered later | Waits behind the named queue, delivered later | Coalesced into the running delivery |
| Re-run with the lease held | None | None | Up to 32 (`MAX_COALESCED_RERUNS`) |
| Coalesced count reported to the handler | None | None | `deliveryCount + rerun`, same `attempt` |
| `invocationStartedAt` | Not passed | Not passed | Passed to every re-run |

What coalescing needs there: drop an orchestrator message claimed while the run's delivery holds the gate and count it on the holder; when the holder's handler returns, run it again in the same process with the next `deliveryCount`, the same `attempt` and the first run's `invocationStartedAt`, until no counted message is left uncovered; cap the re-runs and hand off past the cap, as world-vercel does. A message with state the log does not hold must not be dropped: an intermediate wait hop is already ungated, and every other spec 9 orchestrator message is safe to coalesce (section 5, "No orchestrator message carries state the log needs"). A handoff should also go to the front of the run's queue rather than behind waiting wakes. Not implemented.

### Fan-out latency

durabench's fan-out TTLS is measured to the last branch's body start, not its end. On a 64-branch fan-out on world-vercel, this PR measured a p50 of 1654 ms against 1096 ms on `main`, before the fixes below. Causes found:

- **Serialized creation chunks.** The in-band writer sends one write at a time, and the 61 background `step_created` went out in 4 batches of 16. Now up to `MAX_IN_BAND_CREATION_BATCH_EVENTS` (64) events and `MAX_IN_BAND_CREATION_BATCH_BYTES` (512 KiB) per creation batch (#5030, commit `3c7440e344`, node engine).
- **The inline starts' own batch.** They went out in a first batch of their own, one more round trip in front of every background creation. Now they share the first creation batch, so a 64-wide fan-out is one creation batch (commit `5b53481478`, node engine).
- **Inline outcome writes between creation chunks.** An inline step that finished early queued its outcome on the writer between two creation batches and held up the background creations behind it. Now an inline outcome waits until every creation batch is queued on the writer (`commitInChunks().queued`, commit `5b53481478`, node engine).
- **One 61-message queue batch.** All step messages went out in one queue request, whose latency grows with its size. Now parallel batches of up to `STEP_DISPATCH_QUEUE_BATCH_SIZE` (16) (commit `e277334dbc`, node engine).
- **The awaited background `step_started`.** Each branch waited for its start to commit before its body began. Now the body starts while the start is in flight (commit `83ee22003e`, above).
- **Inline bodies waited for the background dispatch.** The inline bodies started only once every background step message was sent, which since `5b53481478` is the whole fan-out's dispatch. Now the dispatch runs next to the inline bodies and joins `creationsInFlight`, so no pass decides and the delivery does not end before it settled; a failed dispatch fails the delivery, whose redelivery re-sends the steps that have not started (commit `670ea7bdfe`, node engine). This also fixes a `maxRetries: 0` inline sibling of a failed dispatch failing at attempt 2 without running. QuickJS keeps the old order.
- **Later creation batches dispatched together.** The background steps of every creation batch after the first went out only once the last batch committed (`chunks.rest`). The in-band writer commits those batches one after another, 300 to 420 ms each for 64 events, so at 256 branches 192 messages left about 1.8 s in, after the 4th commit, and the second and third batches' steps sat idle 0.6 to 1.2 s. Now each later batch's steps are enqueued as soon as that batch commits (`commitInChunks(onLaterBatch)`), each enqueue in `creationsInFlight`, so no pass decides before every batch and its enqueue settled. A step is only enqueued once its creation committed; a batch that fails stops the batches behind it and fails the delivery, whose redelivery creates and enqueues the rest (commit `8a79811aa6`, node engine). Expected: the k-th of n creation batches starts its steps n - k commits earlier, so the median branch start drops by about half the creation span (0.3 to 0.8 s at 256 branches, about 2.5 to 3 s at 1024), and the last branch by close to nothing. Not re-measured. QuickJS writes a suspension's creations one by one and keeps its order. Tests: `spec9/inline-step-writes.runtime.test.ts` (a slow third batch, a failed third batch, and a `Promise.race` won by a branch that finished before the last batch committed).
- **Batch payload resolution.** Not a measured cause of TTLS, fixed in the same series: the in-band writer no longer escalates a write batch to `resolveData: 'all'` when a write in it asked for `skip-step-inputs` (#5034, commit `2cd65d5af2`).

Re-measured on durabench at `f1d403fae5`, before `670ea7bdfe`: 20 runs per width per version, 100 ms of work per step, 1 KB JSON payloads, against `main` at `4f8e5ba` (spec 8). p50 in milliseconds, p90 in parentheses:

| Branches | First branch, PR | First branch, `main` | TTLS, PR | TTLS, `main` | Join, PR | Join, `main` |
|---:|---:|---:|---:|---:|---:|---:|
| 16 | 428 (580) | 434 (523) | 630 (2478) | 956 (2587) | 120 (214) | 333 (552) |
| 64 | 705 (803) | 459 (606) | 916 (1258) | 1030 (1161) | 264 (1952) | 306 (482) |
| 256 | 882 (1288) | 676 (852) | 3232 (4822) | 19322 (73419) | 770 (6299) | 737 (1432) |
| 1024 | 3194 (3459) | 2603 (5426) | 11789 (159975) | 91390 (146354) | 84530 (114219) | 2753 (44680) |

What the numbers show:

- **TTLS** is below `main` at every width, by about 6x at 256 branches and 8x at 1024. The 64-branch regression is gone.
- **First branch** is 200 to 600 ms behind `main` from 64 branches up. Two causes, from the run timelines:
  - The inline bodies waited for the dispatch, about 85 to 135 ms of it, which `670ea7bdfe` removes. Estimated first branch after it: about 590 ms at 64 branches. Not re-measured.
  - The rest is the single 64-event first creation batch. world-vercel's commit time grows with the batch size, about 5 to 6 ms per event: 60 to 100 ms for 16 events and 300 to 420 ms for 64. The inline starts ride that batch, so the inline bodies wait for the whole fan-out's creations. `main` commits about 13 events per chunk in parallel and starts its inline steps after the first.
- **Join at 1024 branches** regressed: p50 84.5 s against 2.8 s. In half of the runs every branch started within 13 s and the join took 80 to 105 s; in the others, late branch starts took the same time out of the join instead, so E2E is close to `main` (p50 113 s against 96 s).
  - **Cause.** In a clean run, every outcome had committed 18 s after the start, and the orchestrator held every event 25 s in, through the live feed and tail polls. It stayed in its one invocation, CPU-bound, until it continued past the join 100 s in: polls scheduled every 2 s fired every 5 to 6 s, and a lease renewal took 5.8 s on the client. Every step still pending when the event walk reaches the end of the log signals a suspension, and each signal started its own idle poll (`scheduleWhenIdle`), which polled until the run went idle. Spec 9 resumes its retained session once per batch of incoming outcomes, a new suspension generation each time, so polls piled up as generations times pending steps, and those of past generations kept polling. `main` replays once per wake and never stacks generations. The code is the same on both.
  - **Measured locally** on the in-memory World, node engine, all steps in the background: timers set per run grew with about the cube of the width (1.1 k at 32 branches, 8.5 k at 64, 104 k at 128, 1.1 M at 256, 92 M at 1024), and the join after the last outcome took 14 to 25 s at 1024.
  - **Fixes.** Signals of one generation share its earliest poll, and a poll ends once its generation moves on (commit `9f96925239`). Disabled debug logging returns before building anything, and the step consumer logs only its own events (commit `ff5ef5c6ac`). The event walk offers an event only to the consumers keyed to its correlation id plus the unkeyed ones, in registration order (commit `ad9f92fff0`). Locally at 1024 branches the run now sets about 1.1 k timers, the join after the last outcome takes 0.2 to 0.3 s, and the outcomes are taken in within 2.1 s instead of 17 to 23 s. Test: `spec9/fan-out-idle-poll.runtime.test.ts`.
  - The tail poll also backs off while the live feed keeps up (commit `48c58658b3`). The clean run's polls drew 429s during the join. With the push up, the poll now starts at 10 s (`WORKFLOW_ORCHESTRATOR_FEED_POLL_INTERVAL_MS`) and backs off to at most 20 s, so an event the push misses without a sign waits at most 20 s, against 16 s before. Without a push (a World without `events.subscribe`, a refused or ended subscription, or a push that showed a gap) it polls every 2 s as before (`WORKFLOW_ORCHESTRATOR_POLL_INTERVAL_MS`).
  - QuickJS does not use this path and showed no regression locally. Production has not been re-measured.
- **Dispatch itself** is not slow: the 4 parallel queue requests for 61 messages take 44 to 141 ms each, start within 2 ms of each other, and the first queued step is invoked 60 to 85 ms after its request returns.

Cold world-vercel backend instances behind the step invocations' events WebSockets explain the p90 outliers of about 4 s seen earlier: 5 of 25 runs on this PR, 0 of 25 on `main`. Why only this PR hits them is not verified. 5 of 61 step messages of one 64-branch run were also delivered twice about 6 ms apart; the losing invocation got a 409 and exited, and when the winner was a cold instance that branch started 1.3 s late.

Not done yet, in order of expected gain:

- **A small first creation batch.** The inline starts and about 16 creations first, so the inline bodies and the first background steps start after a 60 to 100 ms commit instead of a 300 to 420 ms one. Estimated 200 to 320 ms off the first branch from 64 branches up. Partly reverts `5b53481478`; the reason not to do it before, that a 64-wide fan-out would gain nothing at one 64-event batch, does not hold once the commit cost is per event. Each later batch's steps already go out as it commits (`8a79811aa6`), so the early branches' out-of-band writes already land while later creation batches commit. They do not move the in-band fence, and the orchestrator wakes they send are the same count as before, earlier; their cost on world-vercel's per-run sequence item is not measured.
- **A lower per-event commit cost in world-vercel**, which would help every width.

### Spec 8 retries and sleeps on Vercel (fixed)

An earlier version of this PR redelivered the same message for every `{ timeoutSeconds }` result, spec 8 included. Vercel Queues caps a redelivery's delay at 900 seconds, and spec 8 counts every delivery toward `WORKFLOW_MAX_QUEUE_DELIVERIES` (48), so a spec 8 sleep or step retry chain longer than about 12 hours would have failed with `MAX_DELIVERIES_EXCEEDED`. world-vercel now answers a spec 8 run's `{ timeoutSeconds }` with a new message (up to 23 hours of delay) before acknowledging, as on `main`. Unit-tested; not run against Vercel.

### Spec detection rests on the payload stamp

Topic, key and continuation are chosen from the spec version the message carries. A spec 9 message without one would be sent unkeyed and continue on new messages; a spec 9 step message continuing on a new message would lose its same-message retry and arrive as a plain first delivery, which skips the log read the at-most-once rule of `maxRetries: 0` steps depends on.

Every spec 9 send site in this runtime now names the run's spec version (`specVersion` on the queue options, which `withRunSpecVersion` stamps as `runSpecVersion`; a step message carries `runContext`): the orchestrator's wakes, timers and fence-refusal wake (from the routed spec, `WorkflowDelivery.runSpecVersion`), the QuickJS engine's wakes and timers, and the step handler's wakes. They used to fall back to a 10,000-entry per-process memory of run spec versions, so after 10,000 other runs in one process their messages went out unstamped. `spec9/spec-stamp.runtime.test.ts` forgets the run before every write and step body, on both engines, and checks every message is stamped.

Unstamped producers outside this runtime remain: `resumeHook()` and `cancel()` callers in deployments on an older SDK, the Vercel dashboard's pinned `@workflow/core`, and the admin re-enqueue path. Their messages to a spec 9 run are treated as spec 8: sent unkeyed, so they run next to the keyed orchestrator, where the in-band fence keeps them safe (the loser stands down with one keyed wake) at the cost of an overlapping invocation.

### Long step retries cost an invocation every 900 seconds on Vercel

A spec 9 step retries in place: its message is redelivered after `retryAfter` (`{ timeoutSeconds: n }`). Vercel Queues caps a redelivery's delay at 900 seconds, so a retry more than 15 minutes out is reached in 900-second redeliveries, each an invocation that reads the log and asks again: about 96 a day for a day-long backoff, where `main` sends a new message of up to 23 hours (about 2 a day). Not measured.

### world-postgres resets `attempt` on every reschedule

Verified with a scratch test against Docker Postgres (graphile-worker, a spec 9 payload). world-postgres computes `attempt` from the Graphile job's own attempt counter, and every `{ timeoutSeconds }` result, a handoff or not, reschedules on a new job (`packages/world-postgres/src/queue.ts`, the reschedule path), so `attempt` drops back to 1 while `deliveryCount` keeps counting. Observed sequences (`attempt/deliveryCount`): reject then handoff then acknowledge gave `1/1`, `2/2`, `1/3`, where the contract asks for `1/1`, `2/2`, `2/3`; a `{ timeoutSeconds: 1 }` result does not raise `attempt` either. The narrow consequence: a crash redelivery (attempt 2) that then hands off loses its creator re-send right on the next delivery (`creatorDeliveryCount = min(deliveryCount, attempt)` becomes 1), so a step message lost in the crash window is not re-sent and the run can strand. Whether a redelivery can hand off before it reaches its re-send point I do not know. A reschedule also resets what the delivery cap counts. Not fixed here.

### An inline step's retry can run twice after 24 hours

When an inline step's retry moves to the background with a `retryAfter` beyond 24 hours, its retry message can be re-sent after Vercel Queues' 24-hour idempotency window has passed, and then two messages own one step's body. Reported by a reviewer, predates this PR; I have not verified it.

### Rollout coupling between builders and world-vercel (resolved)

The `__wkf_keyed_*` topics and the second trigger are gone, so a deployment built by an older `@workflow/builders` consumes every message world-vercel sends.

### Billing

Vercel Queues bills operations on keyed messages at its premium rate (2x) for the send, the notify and the delete. Today, `maxConcurrency` topics bill the notify at 2x. Spec 9 runs therefore cost more queue units per orchestrator message, offset by fewer messages (coalescing) and fewer invocations. Not measured.

### Storm workflows cascaded on unkeyed replacements (fixed, not re-measured)

Measured on Vercel for heads `16f7001` and `5d51` from the world-vercel backend's own fence-refusal logs. The client `[diag]` lines undercount: each request's console logs stop at 256 lines, and debug output fills that within seconds.

- **Where.** 54 of 60 storm runs are clean (1 to 4 orchestrator invocations, at most 1 refusal). 6 runs cascade, 5 of 12 `stepStormReproWorkflow` runs and 1 of 12 `hookStormReproWorkflow` runs, with 48 to 164 orchestrator invocations and 48 to 159 refusals each, and up to 18 orchestrators running at once. The regular e2e suite shows none, because it runs no storm workflows.
- **Mechanism.** In every cascade run, invocations equal refusals plus one to three. The extra invocations were `replacesMessage` replacements. They were unkeyed, so a replacement ran next to the keyed holder, lost or won the fence, and the loser sent another unkeyed replacement. After `MAX_MESSAGE_REPLACEMENTS` a chain fell back to redelivering its unkeyed message, so a chain did not die out. No `run.wakeUp()` or replay-divergence messages, lease expiry, handoff overlap, or unenforced key were found.
- **Chain root.** In the one run where it is visible, a keyed holder sent its own unkeyed replacement (a run-ahead stop, by elimination) and kept running as a coalesced re-run in the same invocation.
- **Cost.** 46 to 162 extra orchestrator invocations and 120 to 225 extra function-seconds per cascade run (4 to 6 times a clean run), and 7 to 19 seconds more wall time. Each wasted replacement loads 300 to 760 events and replays before it is refused. Open inline steps can be re-run by each overlapping orchestrator; how often is not known.

The first two candidate fixes are implemented (section 5): a run-ahead stop restarts in place, and a fence refusal sends the loser's own committed-but-unsent messages and one keyed wake, and acknowledges. The only unkeyed orchestrator-topic messages left are intermediate wait hops, which write nothing, so a refused delivery starts no chain: its wake is keyed and cannot run next to a keyed holder. The other two (never overlap a replacement with a coalesced re-run, back replacements off by count) have nothing left to apply to. The storm runs have not been re-measured on Vercel since.

### Handoffs verified live, and a long sequential run rarely reaches one

Verified on Vercel with a throwaway probe deployment of head `16f7001`. The handoff was then signalled with a `handoff: true` result flag; it is now `{ timeoutSeconds: 0 }` on a spec 9 run (section 4), with the same queue call underneath. Not re-verified since:

- **Deadline handoff.** A run of 100-second inline steps reached the 5-minute inline deadline (`elapsedMs: 300421`) and handed off. The same queue message was redelivered 1.2 seconds later with `deliveryCount: 2` and `attempt: 1`: the handoff count reaches the next delivery, and `attempt` leaves the handoff out.
- **Stream-flush handoffs.** All 28 stream-flush handoffs (`readableStreamWorkflow`, `fetchWorkflow`) on the e2e deployments were redelivered once, on the same message, about 2 seconds after the first invocation started.
- **Not observed directly:** the queue's answer to a handoff (`accepted`, `not_immediate` or `limit_reached`), which the client does not log. A redelivery within about a second implies `accepted`.

The deadline handoff fires only when an inline step runs into the deadline. A run of short sequential inline steps reaches the inline-start margin first (`WORKFLOW_INLINE_STEP_DEADLINE_MARGIN_MS`, 60 seconds before the inline deadline), and its next step goes to the background on its own message. The step's completion then wakes the orchestrator on a fresh message.

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function nightlyReport() {
  "use workflow";
  for (let day = 0; day < 365; day++) {
    await aggregateDay(day); // about 1 second each
  }
}
```

Each invocation runs about 4 minutes of `aggregateDay` inline, then sends one step to the background and ends. That costs a step invocation and a queue hop where a handoff would cost a redelivery. Handing off at the margin would remove that hop. Not implemented.

### QuickJS

Spec 9 runs on both engines. Every spec 9 runtime test file runs on both, except the run-ahead suite, and the QuickJS Vercel Prod lanes pass what the node lanes pass. Differences and gaps:

- **No run-ahead.** QuickJS always waits for its writes to commit, so run-ahead stops, their restarts, and the out-of-band `wait_completed` hazard in the `wakeUp()` section never occur on it.
- **No replay-divergence recovery.** As before this change, QuickJS fails the run on a VM failure.
- **Continuations covered by typecheck only.** Its exit continuations (replay budget, an elapsed wait, an unread write of its own) hand off through `continueInNextDelivery`. No test triggers them, because QuickJS keeps its VM live through inline steps. The deadline handoff verified on Vercel was on the node engine.
- **Fence refusal** shares the node path's handling, through the catch in `spec9/delivery.ts`; QuickJS reports its sent step and timer messages back (`onStepMessageSent`, `onWaitTimerSent`). Covered by the orchestrator tests that run on both engines; QuickJS inline-step retries have no dedicated test.

## 8. Bugs found during this work

### The concurrency key was never sent

The first e2e run on Vercel showed `webhookWorkflow` failing: its `respond` step started two to four times and failed with 409 "stream already completed".

- **Scale.** In the staging analytics table, spec 9 `webhookWorkflow` runs on earlier heads of the branch had 1 duplicate start in 910 runs. The first run with the queue change had 22 in 81.
- **Diagnosis.** Temporary warn-level `[diag]` logs on spec 9 delivery exits showed several orchestrator messages of one run delivered in parallel, each with `deliveryCount` 1, and many fence refusals ("superseded"). The key was evidently not serializing anything.
- **Cause.** `@vercel/queue`'s `QueueClient.send` copied a fixed list of options into the API call and dropped `experimental_concurrencyKey`. Batch sends were unaffected. The client's own tests had called the lower-level API client directly and missed it.
- **After the fix.** Fence refusals per Vercel e2e deployment went from 100 to 140 to 0 to 5. Re-runs of an open inline step went from 30 to 50 to 0 to 6. All 27 Vercel Prod lanes pass.

### A coalesced re-run could outlive its lease

Found by an automated review of the client change. The lease renewal loop stops before each acknowledgment. Restarting it with its regular first delay meant that a re-run under a short server-assigned lease that had never been renewed could outlive the lease. The fix renews at once when a re-run starts.

### A deadline test that raced a timer

The first version of the deadline-handoff test used a 75ms deadline. On the Windows CI runner, the deadline passed before the step could start inline, so the step went to the background and nothing handed off. The test now advances `Date.now()` from inside the step body.

### A lost completion wake stalled the run

A background step's wake is the only thing that moves the run on after its outcome commits; the node orchestrator arms no backstop for background steps on spec 9. If sending the wake failed, the step message was redelivered, its log check found the step terminal and acknowledged with no wake, and the run stalled. Now a redelivery whose decision is to acknowledge because the step is terminal (`step-delivery.ts`, reason `step-terminal`) sends the plain wake again: a live orchestrator absorbs it, and one with nothing new acknowledges it after a tail read. A run-terminal acknowledgment still sends nothing (commit `76643fe621`; test `re-sends the wake when a redelivered step message finds the step terminal` in `spec9/orchestrator.runtime.test.ts`, both engines).

### Idle polls grew with generations times pending steps

The 1024-branch join regression above. One idle poll per suspension signal, never stopped for a past generation, cost about 10^8 timers on a lingering spec 9 orchestrator. Signals of a generation now share its earliest poll, which ends when the generation moves on, so a suspension is raised no earlier than before (commit `9f96925239`; tests `spec9/fan-out-idle-poll.runtime.test.ts` and `suspension-poll.test.ts`). The polling code is shared with spec 8, which keeps its behavior with fewer timers.

## 9. Fixes made at the end of the review

The first two fixes are in commit `12894c55f8`, and the World contract change is documented in Building a World.

### Coalesced re-runs no longer reset the inline deadline

Each coalesced re-run is a new delivery inside the same function invocation. The inline deadline used to be measured from the start of each delivery. Every re-run therefore started a fresh 2-minute budget, and a busy run could keep re-running past the function's maximum duration. It would then be killed mid-work and recover only after its lease lapsed.

world-vercel now stamps `invocationStartedAt` (epoch milliseconds when the request began) and passes it in the handler metadata to every re-run. The spec 9 delivery measures its inline deadline from it, so a late re-run finds the deadline already near and hands off.

**Example.** A chat agent receives a message every second while one turn runs inline. Each message is coalesced into the running delivery, and each re-run handles the next message. Without the fix, a few minutes of steady traffic would keep one invocation alive past its maximum duration.

### Running out of re-runs hands off

After 32 re-runs, a refused acknowledgment used to go to the retry handler, which backed off and counted an attempt. world-vercel's retry handler now answers that refusal with a handoff (`{ afterSeconds: 0, experimental_handoff: true }`).

**Example.** A fan-out of hundreds of steps whose completions keep coalescing into the orchestrator. Every pass finds more completions waiting, and the 32 re-runs run out. Before the fix, each time that happened counted as a failed attempt with a backoff, so a long, busy fan-out could reach the delivery cap. Now the next delivery continues at once, and nothing is counted.

### Terminal-event bookkeeping keeps the QuickJS heap flat

`main` added a heap stability test (#4945) that requires the QuickJS VM heap to stay flat over long runs. Spec 9's terminal-inert rule (every event after an entity's terminal event is inert, by log position) kept one entry per correlation id in the VM heap for the whole run, and failed it with 224k to 438k bytes against a 64 KiB bound.

The rule now keeps no per-entity record. Within one batch of events, the host holds each id's first terminal position. Across batches it reads closure from state the VM already has: a step, wait or attribute id the VM has drawn with no resolver left, an outcome buffered for an id not drawn yet, or a user hook whose entry has been released or force-claimed. Only terminals that VM state cannot show (a disposal that reached the log before this VM disposed the hook, an `AbortController` hook, an id outside the ULID scheme) go into a small heap record, dropped once VM state shows them, so it survives a snapshot. Six tests cover a live session and a snapshot restore. Residual: that record still grows by one entry per hook disposed before this VM reached its `dispose()` and never matched later (a hook force-claimed before this VM created it, for example), which I expect to be rare in production but have not measured.
