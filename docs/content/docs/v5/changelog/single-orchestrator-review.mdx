# Review: single orchestrator (spec 9)

<Callout type="warn">
This is a temporary review document for the pull request that introduces spec version 9. It is written for the people reviewing that PR and will be removed before merge. The user-facing description of the change is [Single orchestrator](/docs/changelog/single-orchestrator).
</Callout>

## 1. Overview

The PR changes how a run is driven. Before it, several invocations of a run could decide what the run does next, and the World kept step and wait rows that refused a second start or a second outcome. After it, runs at spec version 9 have one decider: the run's orchestrator. Step invocations only run step bodies and report outcomes. The World no longer keeps step state to check writes against; it fences the orchestrator as the only in-band writer instead.

The PR does four things:

1. **Spec 9 runtime.** A new orchestrator under `packages/core/src/runtime/spec9/`.
2. **Spec 8 kept side by side.** The previous orchestrator moves to `packages/core/src/runtime/spec8/`, and each delivery is routed by the run's stored spec version.
3. **World contract changes.** A required in-band fence for Worlds that declare spec 9, a `{ timeoutSeconds: 0 }` handoff every World implements for spec 9 runs, in-band event time and per-entity batch order as part of the spec 9 storage contract, and optional coalescing.
4. **Vercel queue serialization.** On Vercel, spec 9 runs are kept to one orchestrator invocation by a Vercel Queues concurrency key per run on the existing `__wkf_workflow_*` topic. Spec 8 runs keep `main`'s queue topology and behavior. This needs a pre-release `@vercel/queue` with the experimental concurrency key and lease handoff support.

## 2. The spec 9 model

### One decider

Only the orchestrator writes decisions: `step_created`, `wait_created`, `wait_completed`, hook and attribute events, `run_completed` and `run_failed`. It also runs inline steps. A background step's own invocation writes only that step's `step_started` and outcome, then wakes the orchestrator.

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function checkout(orderId: string) {
  "use workflow";
  const order = await loadOrder(orderId);   // inline: run by the orchestrator
  const charge = await chargeCard(order);   // inline
  await sendReceipt(charge);                // inline
  return charge.id;
}

async function chargeCard(order: Order) {
  "use step";
  return await payments.charge(order.total);
}
```

A run of `checkout` typically completes in one orchestrator invocation. If a step fails with a retryable error, its retry moves to its own queue message, and that step invocation only reports the outcome. The orchestrator decides what happens next. `main` does the same with an inline step's retry. The step's message then owns its remaining attempts: the queue holds the backoff instead of a live invocation, and the at-most-once and retention rules for retries are enforced on that one message. Retrying a short backoff inline, within the inline deadline, is possible and is not implemented.

### The in-band fence

Every orchestrator write is **in-band** (`inBand: true`). It carries `expectedSeqInBand`, the orchestrator's count of in-band positions, which it took from the `snapshot` of its log load. The World refuses a stale count with `InBandSupersededError` (HTTP 412). Two live orchestrators of one run can therefore never both write. The refused one stops writing and running inline steps, sends the queue messages its own committed writes still owe, and acknowledges its message (section 5).

**Example: an invocation that stalls past its lease.** An orchestrator's event loop blocks for longer than its queue lease (for example, a CPU-heavy inline step). The queue redelivers the run's message, and a second orchestrator starts. The second one writes first and moves the count. The first one wakes up, tries to write its next decision, gets a 412, and stops. Nothing is written twice, and the second one drives the run on.

### Step and wait events are plain appends

The world-vercel backend no longer writes step and wait rows in the same transaction as each event. Step state is folded from the log when it is read. Replay treats any event for an entity after its terminal event as inert, which is what lets a late duplicate append be harmless.

### Run-ahead

When no other writer could change what the workflow does next, the orchestrator hands an inline step's outcome to the workflow before the write commits ([`WORKFLOW_RUN_AHEAD_DEPTH`](/docs/configuration/runtime-tuning#workflow_run_ahead_depth) outcomes at most). The writes still go out in decision order. An awaited hook, an `AbortController`, a step running elsewhere, or a wait due within the invocation makes the orchestrator wait for its writes first. Run-ahead exists on the node engine only (section 7, "QuickJS").

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function pipeline(input: string) {
  "use workflow";
  const a = await stepA(input); // stepB starts while stepA's outcome commits
  const b = await stepB(a);
  return await stepC(b);
}
```

### Turbo

On a run's first delivery, the log holds only `run_created`. The orchestrator writes `run_started` without waiting, starts the in-band writer from the count after creation instead of loading the log, and starts the first inline step bodies before their start commits. A redelivery, or a coalesced re-run of the first delivery (section 5), takes the normal path and loads the log.

### `maxRetries: 0` is at most once

A background step keeps one queue message for its whole life and retries in place on it. Any delivery other than a plain first delivery reads the log before running the body.

{/* @skip-typecheck - illustrative workflow */}
```typescript
async function sendWireTransfer(amount: number) {
  "use step";
  await bank.transfer(amount); // must never run twice
}
sendWireTransfer.maxRetries = 0;
```

If the step's invocation crashes after the transfer but before `step_completed`, the redelivery reads the log, sees a started attempt with no outcome, and fails the step instead of running the body again.

## 3. Spec 8 and spec 9 side by side

### Per-run routing

Each delivery is routed by the spec version of its run, resolved in this order:

1. `runInput.specVersion` on a first delivery.
2. `runContext.specVersion` on a step message.
3. The `runSpecVersion` hint on the message. `queueMessage`/`queueMessages` stamp it on every message for a run, and the direct `world.queue` call sites (`runs.ts`, `hook-wake.ts`, `resume-hook.ts`) set it explicitly.
4. A per-process cache of run spec versions (10,000 entries).
5. `runs.get`, and if the run is not found, the World's own spec version.

Runs at spec 9 or later go to `runtime/spec9`, and anything earlier goes to `runtime/spec8`, which is the previous orchestrator.

**Example: a spec 8 run continuing after a World upgrade.** A long approval workflow is started on a World that declares spec 8, then sleeps for a week.

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function approval(requestId: string) {
  "use workflow";
  await notifyApprover(requestId);
  await sleep("7d");
  return await escalate(requestId);
}
```

During that week the app upgrades to a World that declares spec 9. When the sleep ends, the run's stored spec version is still 8, so the delivery goes to the spec 8 orchestrator, which reads the spec 8 log as it always did. New runs started after the upgrade are spec 9. `world-testing` has a test that does exactly this with world-local (`spec8-upgrade.test.ts`).

### Choosing the spec for new runs

`mintedSpecVersion()` returns the current version (9), or 8 when [`WORKFLOW_SPEC_VERSION=8`](/docs/configuration/runtime-tuning#workflow_spec_version) is set. First-party Worlds call it when they are created, so the variable also works as a kill switch: setting it makes new runs spec 8 without touching runs already in flight. `WORKFLOW_SEALED_LOG` is no longer read: an app that sets `WORKFLOW_SEALED_LOG=0` now mints spec 9 runs, and the runtime warns once that the variable is ignored.

### Writers outside the orchestrator

Writes made outside a delivery (cancel, resume, wake-up, external attributes) stamp the run's own version (`specVersionForRunWrite(run.specVersion)`), not the SDK's current one. A spec 8 run never receives a spec 9 event. The in-band fence is required only when the World declares spec 9 (checked in `start()`), or when the run itself is spec 9.

### Code layout

- `packages/core/src/runtime.ts`: the shared entrypoint. It parses the message, resolves the run's spec, and hands the delivery to one orchestrator through a small `Orchestrator` interface (`runDelivery`, `countsTowardMaxDeliveries`, `writeMaxDeliveriesFailure`).
- `runtime/spec8/`: the previous orchestrator and its tests.
- `runtime/spec9/`: the single orchestrator.
- Shared: `runtime/delivery.ts`, `suspension-hooks.ts`, `quickjs-pending-ops.ts`, `hook-creation.ts`, `step-streams.ts`, `quickjs-delivery-shared.ts`, `step-single-flight.ts`, and the end-of-run drain in `workflow.ts`. Each spec passes its own options, such as the event spec version to stamp, into the shared code.

The delivery bodies and step executors were left separate: they are mostly different code, and sharing them further would add more parameters than it removes.

## 4. World contract changes

| Surface | Change |
|---|---|
| `capabilities.inBandFence` | **Required** for a World that declares spec 9. The runtime refuses such a World without it, in `start()` and at the start of every spec 9 delivery. This is the only new capability. |
| Handler result `{ timeoutSeconds }` | Its meaning now depends on the message's run, read off the payload (`messageRunSpecVersion`, `isSingleOrchestratorMessage` in `@workflow/world`). Spec 9 run: `n > 0` redelivers the same message after `n` seconds; `0` is a **handoff** (below). Spec 8 and earlier: unchanged from `main`, continue after `n` seconds by a redelivery or a new message (world-vercel sends a new message, up to 23 hours out). An unstamped message counts as spec 8. |
| Handoff, `{ timeoutSeconds: 0 }` on a spec 9 run | New, required of every World. Deliver the same message again at once and do not count this delivery toward `attempt`. world-vercel uses the Vercel Queues lease handoff, world-local and world-postgres redeliver at once with `attempt` unchanged. A fence-refused delivery acknowledges instead (section 5). |
| `meta.attempt` | `deliveryCount` less the deliveries that followed a handoff and less coalesced re-runs. The delivery cap counts it. On a World with neither it equals `deliveryCount`. |
| `meta.deliveryCount` on a coalesced re-run | The delivery's count plus the re-run number, so the runtime treats the re-run as a redelivery (turbo off, log read). There is no separate re-run field. |
| `meta.invocationStartedAt` | New, optional. Epoch milliseconds at which the function invocation began. world-vercel passes it to every coalesced re-run, and the spec 9 delivery measures its inline deadline from it. |
| Incomplete skipped-slot report | `hasMore: true` on the write's `EventResult` or `EventBatchResult`. world-vercel maps the backend's `reportIncomplete` to it. |
| In-band `occurredAt` as `createdAt` | Part of the spec 9 storage contract, no capability. The runtime still checks each speculative write's stored time and turns run-ahead off for the World on a mismatch. world-postgres now stores it (it did not before, so run-ahead was off there); the shared fence conformance suite checks it. |
| Per-entity `createBatch` order | Part of the spec 9 storage contract, no capability. world-vercel's backend orders batches; world-local and world-postgres have no `createBatch`. |
| `step_started.creatorMessageId` | Removed. Only a background step's `step_created` and a `wait_created` record their creator; creator rules never read an inline step's. |

world-local and world-postgres declare the fence and serialize orchestrator deliveries per run for spec 9 runs only, with an in-process per-run gate and a per-run Graphile named queue. Spec 8 runs are not serialized there, as on `main`: a spec 8 delivery can hold an inline step until another wake of the same run aborts it, and run-level exclusion would hold that wake back. Neither coalesces.

## 5. Vercel queue serialization

### Before (`main`)

All flow messages, orchestrator and step, go to one topic per workflow name (`__wkf_workflow_<name>`). Its consumer has no `maxConcurrency`, so two orchestrator invocations of one run can run at the same time, and the World's step and wait rows refuse the loser's duplicate writes.

`WORKFLOW_SEQUENTIAL_REPLAYS=1` is an opt-in on `main`. It gives each run its own topic (`__wkf_workflow_<name>_<runId>`), each step its own topic, and the flow trigger `maxConcurrency: 1`, so a run has at most one orchestrator invocation at a time.

This PR keeps all of that for spec 8 runs: the shared unkeyed topic, the new-message continuation of a `{ timeoutSeconds }` result, and the opt-in.

### After, for spec 9 runs

- **Same topic and trigger as `main`.** Spec 9 messages go to `__wkf_workflow_<name>`, next to spec 8 messages, and flow routes keep `main`'s single trigger with no `maxConcurrency`. An earlier version of this PR had a second `__wkf_keyed_*` topic family and trigger, because it had moved spec 8 runs onto `maxConcurrency` topics and Vercel Queues refuses (400) a keyed send to a topic a `maxConcurrency` consumer reads. Restoring spec 8's topology removed the need.
- **Under `WORKFLOW_SEQUENTIAL_REPLAYS=1`.** The opt-in keeps `main`'s per-run, per-step and per-probe topics and `maxConcurrency: 1` trigger for every run. Spec 9 messages are then sent **unkeyed** (a keyed send would get the 400): the per-run topic serializes the orchestrator, nothing is coalesced, and handoffs still work, since a lease handoff does not depend on a key.
- **Keyed vs unkeyed.** Orchestrator messages carry the run id as the concurrency key. Step messages and health checks carry none. A spec 9 run's step dispatches now share one topic, so a fan-out batches into one request again.
- **One delivery per run.** Vercel Queues keeps at most one delivery per key active. A keyed message claimed while another delivery holds the key is **coalesced**: it is never delivered, and it is counted on the holder.
- **Coalesced re-runs.** The holder's acknowledgment is refused while coalesced messages it has not covered are pending. The client then runs the handler again within the same delivery, with the lease still held (`experimental_maxCoalescedReruns`, 32 in world-vercel), and acknowledges again covering the reported count. world-vercel reports each re-run with the next `deliveryCount` and the same `attempt`, so the runtime treats it as a redelivery: turbo is off and the log is read.
- **Which runs are spec 9.** world-vercel decides from the payload alone, at send and at delivery alike: `runInput.specVersion`, `runContext.specVersion` or the `runSpecVersion` hint, which every runtime that creates spec 9 runs stamps. A message without a stamp is treated as spec 8 (unkeyed, new-message continuation). An unstamped spec 9 orchestrator message is then fenced but not serialized; no runtime producer sends one.

**Example: a fan-out whose completions coalesce.**

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function resizeAll(urls: string[]) {
  "use workflow";
  const sizes = await Promise.all(urls.map((url) => resize(url))); // 50 background steps
  return sizes;
}
```

The 50 step invocations finish over a few seconds, and each one wakes the orchestrator. While the orchestrator is running, every wake is coalesced into it. When it finishes a pass and tries to acknowledge, it is told how many wakes arrived, reads the log once, and sees all the outcomes that landed. The run is woken a few times instead of 50, and there is never a second orchestrator to refuse.

Coalescing is safe because every producer commits what the wake is for (a step outcome, a `hook_received`) before it sends the wake, so the holder's next read sees it. The one exception is `run.wakeUp()`, which is best-effort (section 7).

### Handoffs

A spec 9 delivery that has to end before the run's work is done hands its message off (`{ timeoutSeconds: 0 }`) instead of sending itself a new one, on every World. On a keyed topic, a message the orchestrator sent itself would be coalesced into its own delivery and run again in the same invocation, which defeats the point of ending it. On world-vercel, the client sends `Vqs-Experimental-Handoff: 1` on the lease change, Vercel Queues redelivers the same message at once, and the handed-off delivery counts toward neither its backoff nor `maxAttempts`. Handoffs are used for:

- the invocation deadline (node engine);
- inline step stream writes still flushing in the background;
- a hook conflict the workflow has to consume in a fresh pass;
- QuickJS exits on the replay budget, an elapsed wait, or an unread write of its own.

**Example: a long workflow crossing the inline deadline.**

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function nightlyReport() {
  "use workflow";
  for (let day = 0; day < 365; day++) {
    await aggregateDay(day); // inline steps, about 2 seconds each
  }
}
```

The run needs about 12 minutes of inline work, longer than one invocation's inline budget. Near the deadline, the orchestrator ends its delivery and the next invocation continues from the log: with a handoff when an inline step runs into the deadline, or through one background step when the inline-start margin comes first (section 7). A year of handoffs counts as zero attempts, so the run is not failed by the delivery cap (`WORKFLOW_MAX_QUEUE_DELIVERIES`, 48 by default).

**Example: a webhook whose response stream is still flushing.**

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function webhookWorkflow() {
  "use workflow";
  const webhook = createWebhook();
  for await (const request of webhook) {
    await respond(request);
  }
}

async function respond(request: RequestWithResponse) {
  "use step";
  await request.respondWith(new Response("ok"));
}
```

`respondWith` writes the HTTP response into a stream that is flushed in the background. The step can return before the flush finishes. The orchestrator then ends its delivery so the flush can finish in `waitUntil`, and continues in a handoff. This is the path the e2e `webhookWorkflow` test exercises.

### Creator rules count attempts

Some rules depend on whether a delivery is a redelivery of the message that created a step or a wait (for example, re-enqueueing a background step whose dispatch was lost in a crash). These now count `attempt`, so a delivery after a handoff behaves like the new message it replaces and does not re-send every step that has not started yet. A delivery after a crash still counts as a redelivery.

### No orchestrator message carries state the log needs

A coalesced message is never delivered, and its holder only re-reads the log, so every orchestrator message is keyed and may be coalesced. Earlier heads of this PR sent three kinds unkeyed (`QueueOptions.coalesce: false`), because they carried state that existed only on the message. All three are gone or demoted:

| Message | Message-only state | Now |
|---|---|---|
| Replacement after a fence refusal or a run-ahead stop | `replacesMessage`: the creator identity of the replaced message | Removed. A fence-refused delivery sends the messages its own writes owe and acknowledges. A run-ahead stop continues in place. |
| Replay-divergence recovery | `replayDivergence`: the divergence history | Removed for spec 9. The delivery replays again in place and counts divergences in memory. Spec 8 still sends it. |
| `run.wakeUp()` | `completeWaits`: the waits to complete now | Keyed, best-effort (section 7). |

`QueueOptions.coalesce` and the payload's `replacesMessage` are removed from `@workflow/world`, with `MAX_MESSAGE_REPLACEMENTS` and `WORKFLOW_FENCE_REDELIVERY_DELAY_SECONDS`.

**Fence refusal.** A delivery whose in-band write is refused keeps, from its writer's accepted events, what those writes owe the queue: the message of each background step whose `step_created` it committed (trailing fan-out batches included), the message of each inline step whose retry it moved to the background with a committed `step_retrying`, and a timer for each open wait it owns (its own `wait_created`, or the wait a timer delivery is for). It sends exactly the ones it has not sent, with their usual idempotency keys, then acknowledges. On a redelivery of its message it also sends what the creator rules re-send for an earlier delivery of it. It sends no wake: the winner's fenced write came after every write the loser committed, so the winner holds them, and whatever the loser read below them reached the winner too, through its load or its write's skipped-slot report. If the loser dies before those sends, its message is redelivered (attempt 2), and the creator rules re-send them; both paths have tests.

**Run-ahead stop.** The delivery lets the outcomes a hazard stop still allows commit, sends what its writes owe (as above), takes a fresh writer, reloads the log and replays from cold in the same delivery, with run-ahead off for the rest of the delivery. With run-ahead off a second stop cannot occur; `MAX_RUN_AHEAD_RESTARTS` (1) still bounds the restarts, and a stop past it hands the message off. The inline deadline applies to the restarted pass as to any other.

**Replay divergence.** The delivery discards the VM, reloads the log and replays from cold in a fresh VM, up to `WORKFLOW_REPLAY_DIVERGENCE_MAX_RETRIES` times, then fails the run with the same `CORRUPTED_EVENT_LOG` error and message as before. The first natural write after a recovered divergence still carries `replayDivergenceCount`. Across crashes and redeliveries the count starts again, and the delivery cap bounds it. The QuickJS engine had no divergence recovery before this change and has none after it.

### Timers stay keyed

A sleep's timer is a delayed keyed message. If it comes due while the orchestrator is running, it is coalesced into it, and the orchestrator's re-run sees the wait due. If the lock was released before the timer came due, Vercel Queues compares the timer's due time, not its send time, with the release, so the timer is delivered normally.

## 6. Decisions and tradeoffs

### The PR was not split into "format" and "capability" halves

A split was considered: ship spec 9 as an event-format change only (the creation-bearing `step_started`, the inert-after-terminal rule, the new fields), and gate the single orchestrator on a World capability. It was not done because:

- The format changes exist because the World stops keeping step state, and that is only safe with one fenced writer.
- The World has to know per run whether to keep step rows. A process-wide capability can't express that; a stored per-run flag would be a second spec version with another name.
- A capability check would hand spec 8 runs created before an upgrade to the new orchestrator, and those runs have no in-band count from creation.

The PR can still be reviewed and released in stages: readers first (raise `SPEC_VERSION_MAX_SUPPORTED` while minting stays at 8), then the backend, then minting.

### Spec 8 keeps its code, side by side

Spec 8 runs keep the previous orchestrator unchanged instead of being migrated. The cost is two orchestrators in one package until spec 8 is dropped. The benefit is that runs in flight during the upgrade finish on the code that started them, and `WORKFLOW_SPEC_VERSION=8` is a working kill switch.

### Spec 8 messages are not keyed

Spec 8 messages carry no concurrency key. Keying them would serialize them, and a coalesced wake would become a re-run inside the same invocation instead of a separate delivery, which changes spec 8 behavior. Spec 8 runs keep `main`'s shared, unserialized topic, its new-message continuation and its opt-in.

### `{ timeoutSeconds: 0 }` means handoff, by run spec

The handoff could have stayed a flag on the result (`handoff: true`) behind a capability. It is the plain `{ timeoutSeconds: 0 }` instead, with the meaning chosen by the message's run: a handoff for spec 9 messages, `main`'s continuation for earlier ones. That leaves no capability for a World to forget and no second result shape. The cost is that a World must read the run's spec off the message, which `@workflow/world` provides. On world-local and world-postgres, spec 9 continuations that used to be new orchestrator messages are now handoffs of the same message: the next delivery keeps the message's id (and so its creator identity) and the attempt count of the delivery that handed off, as on world-vercel.

### Per-run and per-step topics are dropped for spec 9

With the key doing the serialization, a spec 9 run uses one topic per workflow name. This reduces the number of topics and lets a fan-out's step messages batch into one request. The tradeoff is that the key is now the only serialization: when it is not applied, spec 9 runs have none and only the fence keeps them safe. That happened once, through a client bug (section 8), and would happen for a spec 9 message sent without its spec stamp (section 7, "Spec detection").

### Coalesced re-runs instead of new deliveries

A re-run reads the log in the same invocation, so a burst of wakes costs one more pass instead of one cold invocation per wake. The cost is that the re-run is bounded by the invocation's deadline and by the re-run cap (section 9).

## 7. Known gaps and risks

### `run.wakeUp()` is best-effort while an orchestrator runs (decided)

On spec 9, `run.wakeUp()` names the waits to complete on an orchestrator message (`completeWaits`), so the orchestrator writes `wait_completed` in-band. The message is an ordinary keyed orchestrator message. On world-vercel, one that arrives while an orchestrator delivery of the run holds the key is coalesced into it and lost: the re-run reads only the log, and the sleeps run their full length while `wakeUp()` reports them in `stoppedCount`, which counts the waits it asked to complete. That is accepted. A wake-up is useful when the run is suspended on its sleeps, and then nothing holds the key and the message is delivered on its own. world-local and world-postgres never coalesce: their per-run gate delivers the message after the running delivery, and a world-local delivery does not linger past its work (no `events.subscribe`), so `@workflow/vitest`'s `waitForSleep()` and `wakeUp()` keep working. Tests cover both queue shapes, for both engines.

This also removes the two bugs the unkeyed wake had when an orchestrator was already running: a wake delivery that lost the fence dropped `completeWaits` in its replacement, and one that won it refused the running orchestrator's `step_completed`, so the open inline step's body ran a second time. A keyed wake never overlaps the running delivery.

The alternative, `wakeUp()` writing `wait_completed` out-of-band the way `resumeHook()` writes `hook_received`, needs a backend change: the world-vercel backend refuses an out-of-band `wait_completed` on spec 9 runs on purpose, with 409 `wait-completion-in-band-only`. An out-of-band completion could land below events the orchestrator already acted on while running ahead, and a later replay would order them differently.

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function digest(userId: string) {
  "use workflow";
  const first = await fetchUpdates(userId); // run-ahead: the outcome reaches
  const timeout = sleep("1h");              // the workflow before it commits
  const winner = await Promise.race([timeout, nextUpdate(userId, first)]);
  return winner;
}
```

If the `wait_completed` committed below `fetchUpdates`'s outcome, the live run saw the step first and the replay sees the wait first. A reliable wake-up under a running orchestrator would be a new out-of-band "wake requested" event, written like `hook_received` and turned into an in-band `wait_completed` by the orchestrator. Not implemented.

Callers of `run.wakeUp()`: the public API (`Run.wakeUp()`), `@workflow/vitest`'s `waitForSleep()` pattern, the local observability UI (`packages/web`), and the Vercel dashboard's wake-up action. The dashboard calls `wakeUpRun` from a pinned `@workflow/core` release that writes `wait_completed` out-of-band, which the backend refuses on spec 9 runs. Its wake-up therefore does not work on spec 9 runs until it moves to a release with this change.

### A second concurrent sleep lost its timer (fixed)

A spec 9 delivery arms one timer, for the earliest open wait it owns (`armTimers`), and a timer delivery used to own only its own wait (`schedulesWaitTimer`). So in `await Promise.all([sleep("1h"), sleep("2h")])`, the first timer delivery completed the first sleep and armed nothing for the second, and the run stayed suspended until something else woke it. Reproduced on both engines with the test harness. e2e did not catch it: its only parallel sleeps have equal durations, which one timer covers.

A timer delivery now also owns the open waits created by the message that created its own wait, so each timer arms the next one once its own completes. There is still one timer per creating message at a time, so timers do not pile up across suspensions.

### Step bodies a run-ahead stop can run twice

When a hazard stops run-ahead, a step whose body started ahead of its creation, and whose creation the stop then refused, has no committed start, so the restarted pass runs its body again. Per-entity batch order is now part of the spec 9 contract, so one refused speculative batch can carry up to `WORKFLOW_RUN_AHEAD_DEPTH` such steps (2 by default): up to that many bodies can run twice per stop, where earlier heads of this PR ran at most one. A hazard needs another writer (a hook payload for an awaited hook, an out-of-band step event, a cancellation) to land below the speculative writes.

{/* @skip-typecheck - illustrative workflow */}
```typescript
export async function moderate(postId: string) {
  "use workflow";
  const hook = createHook<{ approved: boolean }>();
  const score = await classify(postId);  // run-ahead: outcome handed over early
  await notifyModerators(postId, score); // may start ahead of its creation
  return await hook;
}
```

If the hook's payload lands below `classify`'s speculative outcome, the stop refuses the batch that creates `notifyModerators`, and the restarted pass runs it again. A step declared with `maxRetries: 0` never starts before its start commits, under run-ahead or turbo (`mayRunBeforeItsStart` in `spec9/step-executor.ts`), so it is never one of them.

### Spec 8 retries and sleeps on Vercel (fixed)

An earlier version of this PR redelivered the same message for every `{ timeoutSeconds }` result, spec 8 included. Vercel Queues caps a redelivery's delay at 900 seconds, and spec 8 counts every delivery toward `WORKFLOW_MAX_QUEUE_DELIVERIES` (48), so a spec 8 sleep or step retry chain longer than about 12 hours would have failed with `MAX_DELIVERIES_EXCEEDED`. world-vercel now answers a spec 8 run's `{ timeoutSeconds }` with a new message (up to 23 hours of delay) before acknowledging, as on `main`. Unit-tested; not run against Vercel.

### Spec detection rests on the payload stamp

Topic, key and continuation are chosen from the spec version the message carries. A spec 9 message without one would be sent unkeyed and continue on new messages; a spec 9 step message continuing on a new message would lose its same-message retry and arrive as a plain first delivery, which skips the log read the at-most-once rule of `maxRetries: 0` steps depends on. Every runtime producer stamps spec 9 messages (`queueMessage`/`queueMessages` and the direct `world.queue` call sites; a step message carries `runContext`). I do not know of an unstamped producer, but nothing enforces it at the World boundary.

### Rollout coupling between builders and world-vercel (resolved)

The `__wkf_keyed_*` topics and the second trigger are gone, so a deployment built by an older `@workflow/builders` consumes every message world-vercel sends.

### Billing

Vercel Queues bills operations on keyed messages at its premium rate (2x) for the send, the notify and the delete. Today, `maxConcurrency` topics bill the notify at 2x. Spec 9 runs therefore cost more queue units per orchestrator message, offset by fewer messages (coalescing) and fewer invocations. Not measured.

### Storm workflows cascaded on unkeyed replacements (fixed, not re-measured)

Measured on Vercel for heads `16f7001` and `5d51` from the world-vercel backend's own fence-refusal logs. The client `[diag]` lines undercount: each request's console logs stop at 256 lines, and debug output fills that within seconds.

- **Where.** 54 of 60 storm runs are clean (1 to 4 orchestrator invocations, at most 1 refusal). 6 runs cascade, 5 of 12 `stepStormReproWorkflow` runs and 1 of 12 `hookStormReproWorkflow` runs, with 48 to 164 orchestrator invocations and 48 to 159 refusals each, and up to 18 orchestrators running at once. The regular e2e suite shows none, because it runs no storm workflows.
- **Mechanism.** In every cascade run, invocations equal refusals plus one to three. The extra invocations were `replacesMessage` replacements. They were unkeyed, so a replacement ran next to the keyed holder, lost or won the fence, and the loser sent another unkeyed replacement. After `MAX_MESSAGE_REPLACEMENTS` a chain fell back to redelivering its unkeyed message, so a chain did not die out. No `run.wakeUp()` or replay-divergence messages, lease expiry, handoff overlap, or unenforced key were found.
- **Chain root.** In the one run where it is visible, a keyed holder sent its own unkeyed replacement (a run-ahead stop, by elimination) and kept running as a coalesced re-run in the same invocation.
- **Cost.** 46 to 162 extra orchestrator invocations and 120 to 225 extra function-seconds per cascade run (4 to 6 times a clean run), and 7 to 19 seconds more wall time. Each wasted replacement loads 300 to 760 events and replays before it is refused. Open inline steps can be re-run by each overlapping orchestrator; how often is not known.

The first two candidate fixes are implemented (section 5): a run-ahead stop restarts in place, and a fence refusal sends the loser's own committed-but-unsent messages and acknowledges, with no wake. No unkeyed orchestrator message is left, so a refused delivery starts no chain. The other two (never overlap a replacement with a coalesced re-run, back replacements off by count) have nothing left to apply to. The storm runs have not been re-measured on Vercel since.

### Handoffs verified live, and a long sequential run rarely reaches one

Verified on Vercel with a throwaway probe deployment of head `16f7001`. The handoff was then signalled with a `handoff: true` result flag; it is now `{ timeoutSeconds: 0 }` on a spec 9 run (section 4), with the same queue call underneath. Not re-verified since:

- **Deadline handoff.** A run of 100-second inline steps reached the 5-minute inline deadline (`elapsedMs: 300421`) and handed off. The same queue message was redelivered 1.2 seconds later with `deliveryCount: 2` and `attempt: 1`: the handoff count reaches the next delivery, and `attempt` leaves the handoff out.
- **Stream-flush handoffs.** All 28 stream-flush handoffs (`readableStreamWorkflow`, `fetchWorkflow`) on the e2e deployments were redelivered once, on the same message, about 2 seconds after the first invocation started.
- **Not observed directly:** the queue's answer to a handoff (`accepted`, `not_immediate` or `limit_reached`), which the client does not log. A redelivery within about a second implies `accepted`.

The deadline handoff fires only when an inline step runs into the deadline. A run of short sequential inline steps reaches the inline-start margin first (`WORKFLOW_INLINE_STEP_DEADLINE_MARGIN_MS`, 60 seconds before the inline deadline), and its next step goes to the background on its own message. The step's completion then wakes the orchestrator on a fresh message.

### QuickJS

Spec 9 runs on both engines. Every spec 9 runtime test file runs on both, except the run-ahead suite, and the QuickJS Vercel Prod lanes pass what the node lanes pass. Differences and gaps:

- **No run-ahead.** QuickJS always waits for its writes to commit, so run-ahead stops, their restarts, and the out-of-band `wait_completed` hazard in the `wakeUp()` section never occur on it.
- **No replay-divergence recovery.** As before this change, QuickJS fails the run on a VM failure.
- **Continuations covered by typecheck only.** Its exit continuations (replay budget, an elapsed wait, an unread write of its own) hand off through `continueInNextDelivery`. No test triggers them, because QuickJS keeps its VM live through inline steps. The deadline handoff verified on Vercel was on the node engine.
- **Fence refusal** shares the node path's handling, through the catch in `spec9/delivery.ts`; QuickJS reports its sent step and timer messages back (`onStepMessageSent`, `onWaitTimerSent`). Covered by the orchestrator tests that run on both engines; QuickJS inline-step retries have no dedicated test.

## 8. Bugs found during this work

### The concurrency key was never sent

The first e2e run on Vercel showed `webhookWorkflow` failing: its `respond` step started two to four times and failed with 409 "stream already completed".

- **Scale.** In the staging analytics table, spec 9 `webhookWorkflow` runs on earlier heads of the branch had 1 duplicate start in 910 runs. The first run with the queue change had 22 in 81.
- **Diagnosis.** Temporary warn-level `[diag]` logs on spec 9 delivery exits showed several orchestrator messages of one run delivered in parallel, each with `deliveryCount` 1, and many fence refusals ("superseded"). The key was evidently not serializing anything.
- **Cause.** `@vercel/queue`'s `QueueClient.send` copied a fixed list of options into the API call and dropped `experimental_concurrencyKey`. Batch sends were unaffected. The client's own tests had called the lower-level API client directly and missed it.
- **After the fix.** Fence refusals per Vercel e2e deployment went from 100 to 140 to 0 to 5. Re-runs of an open inline step went from 30 to 50 to 0 to 6. All 27 Vercel Prod lanes pass.

### A coalesced re-run could outlive its lease

Found by an automated review of the client change. The lease renewal loop stops before each acknowledgment. Restarting it with its regular first delay meant that a re-run under a short server-assigned lease that had never been renewed could outlive the lease. The fix renews at once when a re-run starts.

### A deadline test that raced a timer

The first version of the deadline-handoff test used a 75ms deadline. On the Windows CI runner, the deadline passed before the step could start inline, so the step went to the background and nothing handed off. The test now advances `Date.now()` from inside the step body.

## 9. Fixes made at the end of the review

Both fixes are in commit `12894c55f8`, and the World contract change is documented in Building a World.

### Coalesced re-runs no longer reset the inline deadline

Each coalesced re-run is a new delivery inside the same function invocation. The inline deadline used to be measured from the start of each delivery. Every re-run therefore started a fresh 2-minute budget, and a busy run could keep re-running past the function's maximum duration. It would then be killed mid-work and recover only after its lease lapsed.

world-vercel now stamps `invocationStartedAt` (epoch milliseconds when the request began) and passes it in the handler metadata to every re-run. The spec 9 delivery measures its inline deadline from it, so a late re-run finds the deadline already near and hands off.

**Example.** A chat agent receives a message every second while one turn runs inline. Each message is coalesced into the running delivery, and each re-run handles the next message. Without the fix, a few minutes of steady traffic would keep one invocation alive past its maximum duration.

### Running out of re-runs hands off

After 32 re-runs, a refused acknowledgment used to go to the retry handler, which backed off and counted an attempt. world-vercel's retry handler now answers that refusal with a handoff (`{ afterSeconds: 0, experimental_handoff: true }`).

**Example.** A fan-out of hundreds of steps whose completions keep coalescing into the orchestrator. Every pass finds more completions waiting, and the 32 re-runs run out. Before the fix, each time that happened counted as a failed attempt with a backoff, so a long, busy fan-out could reach the delivery cap. Now the next delivery continues at once, and nothing is counted.

### Terminal-event bookkeeping keeps the QuickJS heap flat

`main` added a heap stability test (#4945) that requires the QuickJS VM heap to stay flat over long runs. Spec 9's terminal-inert rule (every event after an entity's terminal event is inert, by log position) kept one entry per correlation id in the VM heap for the whole run, and failed it with 224k to 438k bytes against a 64 KiB bound.

The rule now keeps no per-entity record. Within one batch of events, the host holds each id's first terminal position. Across batches it reads closure from state the VM already has: a step, wait or attribute id the VM has drawn with no resolver left, an outcome buffered for an id not drawn yet, or a user hook whose entry has been released or force-claimed. Only terminals that VM state cannot show (a disposal that reached the log before this VM disposed the hook, an `AbortController` hook, an id outside the ULID scheme) go into a small heap record, dropped once VM state shows them, so it survives a snapshot. Six tests cover a live session and a snapshot restore. Residual: that record still grows by one entry per hook disposed before this VM reached its `dispose()` and never matched later (a hook force-claimed before this VM created it, for example), which I expect to be rare in production but have not measured.
