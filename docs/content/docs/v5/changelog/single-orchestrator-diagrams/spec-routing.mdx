# Spec routing

<Callout type="warn">
This page is temporary review material for the pull request that introduces spec version 9, and is removed before merge. The written review is [Review: single orchestrator](/docs/changelog/single-orchestrator-review).
</Callout>

The runtime keeps two orchestrators side by side: `runtime/spec8/` (the previous one) and `runtime/spec9/`. A run keeps the spec version family it was created with, and every delivery is routed by that stored version. Runs at 9 or later go to the spec 9 orchestrator, anything earlier to spec 8 (`packages/core/src/runtime.ts:59`). The backend may raise a run's version across capability-only versions (for example 5 to 8, see `CAPABILITY_ONLY_SPEC_VERSIONS`), never across 9, so a run never changes orchestrator.

## Resolving a delivery's spec

`resolveRunSpec` (`packages/core/src/runtime/run-spec-routing.ts:53`) tries, in order:

1. `runInput.specVersion`, on a run's first delivery from `start()`.
2. `runContext.specVersion`, on a step message.
3. `runSpecVersion`, the hint on every other message of a run, a world-vercel rotation's continuation included: it drops the start message's `runInput` and stamps the version `runInput` carried (`singleOrchestratorContinuationPayload` in `@workflow/world`).
4. `runs.get(runId, { resolveData: 'none' })`. A run without a stored version is `SPEC_VERSION_LEGACY`. A run that is not found takes the World's own spec version, and the orchestrator handles the missing run. The run read here is handed on, so the orchestrator does not read it again.

Nothing is remembered between messages: a stamped message never reads the run, and an unstamped one reads it once. A wrong hint routes the message to the other orchestrator, which finds the run's own version on the row it loads and sends the message again with that version before it replays anything (`handOffToRunOrchestrator`, `packages/core/src/runtime/delivery.ts:125`).

```mermaid

    A -->|"set"| R["Use it"]
```

The World decides the queue side from the payload alone, with `messageRunSpecVersion` (steps 1 to 3 only). It never reads the run. An unstamped message is spec 8 there, whatever the run is. See [Queue topology](/docs/changelog/single-orchestrator-diagrams/queue-topology).

## Spec 8 and spec 9 side by side

| | Spec 8 run | Spec 9 run |
|---|---|---|
| Orchestrator | `runtime/spec8` | `runtime/spec9` |
| Writers | Several orchestrator invocations may write; the World's step and wait rows refuse duplicates | One fenced in-band writer; out-of-band writers for hook payloads, step outcomes, cancellation, attributes |
| world-vercel topic | `__wkf_workflow_<name>`, unkeyed | Same topic, orchestrator messages keyed by run id |
| world-vercel `{ timeoutSeconds: n }` | New message, up to 23 hours | Same message redelivered; `0` is a handoff |
| world-local, world-postgres | Not serialized per run | Serialized per run (run gate, Graphile named queue) |
| Wake idempotency keys | `hook-<resumeId>`, `hook-force-claim-<hookId>` | None on wakes; each hop of a wait's timer carries `wait:<correlationId>:<resumeAt>:<hopAt>`, and a near-due re-arm `wait:<correlationId>:<resumeAt>:s<second>` |
| `run.wakeUp()` | Writes `wait_completed` out-of-band | Sends `completeWaits` to the orchestrator |

world-local and world-postgres serialize only spec 9 runs (`singleOrchestratorRunIdOf`, `packages/world/src/queue.ts:705`). A spec 8 delivery can hold an inline step until another wake of the same run aborts it, and a per-run gate would hold that wake back.

## Minting new runs

`mintedSpecVersion()` returns 9, or the version `WORKFLOW_SPEC_VERSION` names (6 to 9), or 6 when `WORKFLOW_SEALED_LOG=0` is set and `WORKFLOW_SPEC_VERSION` is not (`packages/world/src/spec-version.ts`). First-party Worlds call it when they are created, so `WORKFLOW_SPEC_VERSION=8` works as a kill switch: new runs are spec 8, runs in flight keep their version. An unrecognised value is ignored with a one-time warning. This is the behaviour at this head; the planned opt-in flips the default to 8 and mints 9 only for `WORKFLOW_SPEC_VERSION=9` on a World with the in-band fence (review page, section 10).

## Stamps at every send site

Every send of a run's message in this runtime names the run's version, for spec 8 runs as well as spec 9 ones. A producer either puts `runSpecVersion` (or `runContext`, `runInput`) on the payload itself, or passes the run's version as `opts.specVersion`, which `queueMessage` and `queueMessages` copy onto the payload (`withRunSpecVersion`, `packages/core/src/runtime/run-spec-routing.ts:82`; `packages/core/src/runtime/helpers.ts:1388`). `spec9/spec-stamp.runtime.test.ts` checks every message of a spec 9 run on both engines, and `spec-stamp-world-local.test.ts` checks spec 8 and spec 9 runs end to end on world-local, including that routing reads the run only for an unstamped message.

## An unstamped message

A message to a spec 9 run without a stamp still reaches the right orchestrator, because `resolveRunSpec` falls through to `runs.get`. The World treats it as spec 8: on world-vercel it is sent unkeyed and a `{ timeoutSeconds }` result continues on a new message; on world-local and world-postgres it skips the per-run gate. It then runs next to the keyed holder, and the in-band fence keeps that safe: the loser's write gets a 412, and it asks for a redelivery of its own message (see [The in-band fence and its 412s](/docs/changelog/single-orchestrator-diagrams/in-band-fence)). The log stays linear, but the overlap can cost more than one invocation: a spec 9 inline step's start carries no owner, so the unserialized delivery can start and run the body of an inline step the holder is still running, and the fence refuses only the later outcome write. Every producer in this runtime stamps its messages for that reason, including the restart recovery of world-local and world-postgres (`reenqueueActiveRuns`). A producer outside it can still send an unstamped message, or one stamped below 9, for a spec 9 run, and nothing in the runtime can prevent that; a hint below 9 reaches the spec 8 orchestrator first, which hands the message on once it loads the run. The comments on `resolveRunSpec` and on `messageRunSpecVersion` in `@workflow/world` record this.

```mermaid
sequenceDiagram
    participant P as Unstamped producer
    participant Q as Vercel Queues
    participant O1 as Keyed holder
    participant O2 as Unkeyed delivery
    participant W as World
    O1->>W: in-band writes at the current count
    P->>Q: wake for a spec 9 run, no stamp, no key
    Q->>O2: delivered beside the holder
    O2->>O2: resolveRunSpec, runs.get says 9, spec 9 orchestrator
    O2->>W: in-band write at its count
    alt O1 wrote first
        W-->>O2: 412 in-band superseded
        O2->>Q: messages its own writes owe
        O2->>Q: timeoutSeconds 1, continued as for a spec 8 message (a new message, unkeyed)
    else O2 wrote first
        W-->>O1: 412 on its next write
        O1->>Q: owed messages, then a redelivery of its own message
    end
```

A spec 9 step message without a stamp would lose its same-message retry on world-vercel and arrive as a plain first delivery, which skips the log read the at-most-once rule of `maxRetries: 0` depends on. Every step message this runtime sends carries `runContext`, so this applies only to a producer outside it.

## A spec 8 run after an upgrade

A run started on a World that declares spec 8 keeps spec 8 after the app moves to a World that declares spec 9. `packages/world-testing/test/spec8-upgrade.test.ts` does this with world-local.

```typescript
export async function approval(requestId: string) {
  "use workflow";
  await notifyApprover(requestId);
  await sleep("7d");
  return await escalate(requestId);
}
```

```mermaid
sequenceDiagram
    participant S8 as Spec 8 SDK
    participant W as World
    participant Q as Queue
    participant S9 as Upgraded SDK
    S8->>W: run_created, specVersion 8
    S8->>Q: timer for the 7d sleep
    Note over S8,S9: app upgrades, World now declares spec 9
    Q->>S9: timer delivered
    S9->>S9: resolveRunSpec, stamp or runs.get gives 8
    S9->>S9: runtime/spec8 replays the spec 8 log
    S9->>W: spec 8 events, stamped with the run's version
    Note over S9: new runs started now are spec 9
```

Writes made outside a delivery (cancel, resume, wake-up, attributes) stamp the run's own version through `specVersionForRunWrite(run.specVersion)`, so a spec 8 run never receives a spec 9 event (`packages/core/src/runtime/resume-hook.ts:929`).

## An older SDK and a spec 9 run

The world-vercel backend accepts writes to a spec 9 run only over its API version 5. Every older API version gets 400 `spec-version-requires-api-v5` on a write, while reads stay available. An older SDK (a deployment rolled back, or another deployment's `resumeHook()`) therefore fails on the write, before it sends any wake. It cannot resume a hook or cancel a spec 9 run.

```mermaid
sequenceDiagram
    participant Old as Older SDK
    participant B as world-vercel backend
    participant Q as Vercel Queues
    Old->>B: hook_received or run_cancelled on a spec 9 run, API below 5
    B-->>Old: 400 spec-version-requires-api-v5
    Note over Old,Q: no wake is sent, the run is unchanged
```

## Edge cases

- A run that is not found during routing takes the World's own spec version, and that orchestrator then handles the missing run (`packages/core/src/runtime/run-spec-routing.ts:66`).
- Routing keeps no per-process memory of run versions. An earlier version cached them; the spec 8 orchestrator's own sends relied on that cache for their hint and now stamp it explicitly.
- `withRunSpecVersion` never overwrites a `runSpecVersion` the payload already carries (`packages/core/src/runtime/run-spec-routing.ts:86`).
- A health check has no run spec and is never keyed or gated (`packages/world/src/queue.ts:696`).
- The in-band fence is checked where a spec 9 run is created (`start()`) and where its orchestrator delivery begins writing (the `InBandWriter`); a World that declares spec 8 creates spec 8 runs and is not checked (`assertWorldSupportsInBandFence`, `packages/core/src/runtime/world-compatibility.ts:78`).
- `WORKFLOW_SPEC_VERSION` accepts an integer from 6 to 9; any other value is ignored with a one-time warning and the default is minted (`mintedSpecVersion`, `packages/world/src/spec-version.ts:202`).
- An older SDK's 400 is answered on the write, so no stale wake is left queued for a spec 9 run.
