# Durable hook resume

## Motivation

The previous lazy path published the serialized hook payload on the workflow
queue and left the queue consumer to create `hook_received`. If the hook was
disposed after `resumeHook()` returned but before the consumer write committed,
that write was rejected and the acknowledged queue delivery could not resume the
workflow.

`resumeHook()` now resolves only after both the durable event write and the
workflow wake have succeeded.

## Design

- The producer always writes `hook_received`, including a client-minted
  `resumeId` and payload digest when the backend supports atomic resume claims.
- A compatible producer publishes a payload-less wake in parallel with that
  write. The wake identifies the expected `resumeId` and hook.
- The consumer does not replay or acknowledge a producer-committed wake until
  the matching durable event is visible. If the event is still in flight, the
  delivery fails transiently so the queue redelivers it.
- If the durable log proves the run ended or the hook was disposed without the
  matching event, the consumer safely consumes the permanently refused wake.
- Queue publication is retried a bounded number of times. A publish failure is
  still returned to the caller, but the committed event is retained.
- `ResumedHook.resilientResume` remains on the type for source compatibility and
  is no longer set. The internal `resumeHookDurable()` entry point is deprecated
  because `resumeHook()` now provides the same guarantee.

A resolved call proves that the event is durable and the wake was accepted.
`HookNotFoundError` proves this invocation committed no event. Any other thrown
error is ambiguous: the event may be durable already, and a fresh invocation
mints a new `resumeId`, so blindly retrying can append another delivery.

## Compatibility

The parallel path requires both an atomic `(runId, resumeId)` backend claim and
a target run whose consumer advertises the producer-committed wake barrier.
Existing runs advertise the older consumer protocol and continue to use
write-then-publish. Legacy runs, unsupported Worlds, and
`WORKFLOW_DISABLE_LAZY_HOOK_RESUME=1` also use write-then-publish.

Consumers continue to accept legacy `hookInput` messages from older producers,
materializing their payload before replay. This permits rolling upgrades without
a coordinated producer, consumer, and backend deployment.
