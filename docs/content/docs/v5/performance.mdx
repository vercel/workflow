We benchmark the Workflow SDK runtime on Vercel at each point where a workflow waits on it: starting a run, moving from one step to the next, fanning out, resuming from a hook, and delivering a stream, plus a five-turn agent loop that combines them. This page explains what each benchmark measures and how, and then shows the [latest results](#latest-results), which compare the latest release with earlier ones.

## What we measure

Each benchmark starts a clock at one line of code and stops it at another. The work inside a step is not counted, so the numbers measure the runtime itself. Choose a metric below, then play or scrub through a run to see when its clock runs.

<PerformanceExplainer />

### Time to first step (TTFS)

How long it takes from your app calling [`start()`](/docs/api-reference/workflow-api/start) until the first line of the workflow's first step runs. This covers creating and queuing the run, running the workflow code up to its first step, and starting that step. It is measured on a five-step workflow. See [Steps and long runs](#steps-and-long-runs) for the latest results.

### Step-to-step overhead (STSO)

How long it takes from one step finishing until the next step starts: recording the step's result, resuming the workflow, and starting the next step. It is measured on the same five-step workflow, and at steps 1 to 20, 101 to 120, and 1,001 to 1,020 of a 1,020-step workflow, which shows whether the overhead grows as the run's [event log](/docs/how-it-works/event-sourcing) grows. See [Steps and long runs](#steps-and-long-runs) for the latest results.

### Fan-out (TTFS, TTLS, join)

A workflow starts 64 one-step branches at once with `Promise.all`. The runtime queues the branches in batches, so they start close together and in no fixed order. The first branch (TTFS) and the slowest branch to start, or time to last step (TTLS), are timed from `start()` until that branch's first line runs. The join is timed from the slowest branch finishing until the code after `Promise.all` runs. See [Fan-out](#fan-out) for the latest results.

### Time to resume (TTR)

A workflow creates a [hook](/docs/foundations/hooks) and waits on it for 1 s, the way an agent waits for a person's approval, and then your app calls `resumeHook()`. Time to resume runs from that call until the first line of the workflow's next step runs. Each run resumes five times. See [Resuming a workflow](#resuming-a-workflow) for the latest results.

### Chunk trip time (CTT)

One step replays a recorded AI agent's token stream, 2,593 chunks over 52.4 s, in real time to a [namespaced stream](/docs/foundations/streaming#namespaced-streams) with [`getWritable()`](/docs/api-reference/workflow/get-writable), and a second step in the same run reads it with `getRun(runId).getReadable()`. Chunk trip time runs from the writer writing a chunk until the reader receives it. The same benchmark records how long the whole response takes to reach the reader and how many runs had a chunk delayed by over 1 s. See [Streams](#streams) for the latest results.

### Agent loop overhead

A five-turn agent built from plain steps, shaped like a durable AI agent. Each turn is one model step that streams 10 tokens over 100 ms to [`getWritable()`](/docs/api-reference/workflow/get-writable). On turns 1 to 4 the model then calls two tools, which run in parallel as 100 ms steps, and turn 5 answers. Each message is 1 KB of JSON, and the conversation passed to every step grows each turn. The overhead runs from `start()` until the first line of a step after the last turn, minus the 900 ms of model and tool work on the critical path. The loop runs with and without streaming its tokens. See [Agent loop](#agent-loop) for the latest results.

Every step uses the default retry settings. A model step marked [`maxRetries = 0`](/docs/foundations/errors-and-retries), as some agent libraries do, waits until its start is recorded before it runs, which added about 70 ms per turn on v5.8.0 in our measurements.

## Methodology

- **Platform**: Each version runs the same benchmark app on Vercel production in `iad1`, against the managed [Vercel World](/worlds/vercel), on its own deployment. The versions are measured at the same time. Before each sweep of a benchmark, every deployment runs one warm-up that is not counted: a five-step workflow before the 1,020-step run, and one run of the benchmark otherwise. The agent loop runs on a separate app, deployed the same way once per version, which runs one loop with and one without streaming before measuring.
- **Workload**: Every step takes 1 KB of JSON in and out and does 100 ms of simulated work, which the overhead measurements exclude.
- **Runs**: Each version runs every benchmark several times, and each result pools the samples from all of its runs. The run counts are listed with the latest results.
- **Percentiles**: Each percentile pools every sample across a version's runs and uses the nearest-rank method. Half of the samples are at or below the p50 (the median), three quarters at or below the p75, and all but the slowest 1% at or below the p99. With 100 or fewer samples, a p99 is the slowest sample.

### Limits

- The benchmarks run in one region, against one World. Other regions, Worlds, and workloads will see different numbers.
- The versions share the platform while they are measured. Any exception is noted with the results.
- The explainer and the animations are schematic: they show where each clock starts and stops, not real timings.

In the fan-out, the first branch started after more than 1 s in 8 of 25 runs on v5.2.0, 5 on v5.8.0 and 1 on v4.8.18; on v5.2.0 those runs set the p75. Each version ran the sequential workflow 10 times, the agent stream 10 times, the fan-out 25 times, the resume benchmark 25 times, the 1,020-step run 5 times, and the agent loop 15 times with streaming and 15 times without.

{/* generated:performance sequential */}

At p75, a five-step workflow reaches its first step in 197 ms on v5.8.0, 189 ms on v5.2.0 and 662 ms on v4.8.18. Between steps, it adds 7 ms on v5.8.0, 260 ms on v5.2.0 and 818 ms on v4.8.18.

### Streams

{/* generated:performance streams */}

The agent produced its 2,593-chunk response over 52.4 s. On v4.8.18 the writer step manages about 12 chunks per second, so the response takes 215.1 s to reach the reader. v5.2.0 and v5.8.0 write streams over a WebSocket by default, keep up at about 49 chunks per second, and deliver the response in 54.1 s on v5.2.0 and 53.5 s on v5.8.0.

At p75, a chunk reaches the reader in 93 ms on v5.8.0, 94 ms on v5.2.0 and 160 ms on v4.8.18. A chunk was delayed by over 1 s in 0 of 10 runs on v5.8.0, 0 of 10 runs on v5.2.0 and 6 of 10 runs on v4.8.18.

{/* end generated:performance streams */}

On the Vercel World, [`WORKFLOW_STREAMS_TRANSPORT`](/docs/configuration/worlds#workflow_streams_transport) sets the transport for stream writes.

### Agent loop

{/* generated:performance agent-loop */}

The loop runs on a benchmark app of its own, deployed once per version, and each version ran it 15 times with streaming and 15 times without.

At p75, the five-turn loop that streams its tokens adds 892 ms on v5.8.0, 3,394 ms on v5.2.0 and 9,814 ms on v4.8.18. Without streaming, v5.8.0 adds 366 ms, of which 198 ms is the time to reach the first step (at p75), against 2,252 ms on v5.2.0 and 7,078 ms on v4.8.18.

On v5.8.0, the streaming loop waits after each model step until its last tokens are stored: the tools start 130 ms after the model step at p75, against 7 ms without streaming.
