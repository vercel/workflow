Use child workflows when a single workflow needs to orchestrate many independent units of work. Each child runs as its own workflow with a separate event log, retry boundary, and failure scope. If one child fails, it doesn't take down the parent or siblings.

## When to use child workflows

Child workflows are the right choice when:

- **Work units are independent**: Each child can run without knowing about the others (for example, when processing individual documents or generating separate reports).
- **You need isolated failure boundaries**: A failing child should not abort unrelated work. The parent decides how to handle failures.
- **You want large fan-out**: Spawning 50 or 500 children is practical because each runs on its own infrastructure. The parent still pays for each spawn, so start them in chunks rather than all at once (see [Chunked spawning](#fan-out-pattern-chunked-spawning)).
- **You need per-item observability**: Each child workflow has its own run ID, status, and event log for monitoring.
- **One run would otherwise get too big**: A run's event log and step count are both capped, see [Vercel World limits](/worlds/vercel#per-run-limits). Replay reads the whole log, so split before the cap: a run headed for more than a few thousand events belongs in several runs.

For simpler cases where steps share a single event log, use [direct await composition](/cookbook/common-patterns/workflow-composition#direct-await-flattening) instead.

## Waiting for a child

Start the child with [`start()`](/docs/api-reference/workflow-api/start) and await its `returnValue`:

```typescript
import { start } from "workflow/api";

declare function fetchDocument(documentId: string): Promise<string>; // @setup
declare function analyzeContent(content: string): Promise<string>; // @setup
declare function generateSummary(analysis: string): Promise<string>; // @setup

// Child workflow -- processes a single document
export async function processDocument(documentId: string) {
  "use workflow";

  const content = await fetchDocument(documentId);
  const analysis = await analyzeContent(content);
  const summary = await generateSummary(analysis);

  return { documentId, summary };
}

// Parent workflow -- orchestrates document processing
export async function processDocumentBatch(documentIds: string[]) {
  "use workflow";

  const runs = await Promise.all(
    documentIds.map((documentId) => start(processDocument, [documentId])) // [!code highlight]
  );
  const results = await Promise.all(runs.map((run) => run.returnValue)); // [!code highlight]

  return { processed: results.length, results };
}
```

`returnValue` is typed from the child's return type. A child that fails or is canceled rejects it with [`WorkflowRunFailedError`](/docs/api-reference/workflow-errors/workflow-run-failed-error) or [`WorkflowRunCancelledError`](/docs/api-reference/workflow-errors/workflow-run-cancelled-error).

### How the parent waits

Awaiting `returnValue` of a run the workflow started does not poll. The SDK waits on a **system hook**, the same handshake you would otherwise write by hand:

1. `start()` marks the child so that it resumes its parent when it finishes, and remembers the parent on the returned `Run`.
2. When the parent awaits `returnValue`, it registers a hook whose token is derived from the child's run ID, then reads the child once. A child that already finished is answered from that read.
3. Otherwise the parent suspends on the hook. When the child completes, fails, or is canceled, its runtime resumes the hook and the parent reads the result.

This gives you:

- **Zero compute while waiting**: The parent is suspended rather than waking on a poll interval, and holds no worker slot. Worker-based Worlds such as [Postgres](/worlds/postgres) do not need a slot per waiting parent.
- **Immediate wake-up**: The parent resumes as soon as the child finishes, not on the next poll tick.
- **No wiring**: There is no hook to define, no token to pass, and no wrapper workflow to export.

The `Run` keeps this behavior when it travels within the parent: a step of the parent that calls `start()` and returns the `Run` hands the parent a handle it can await the same way. Awaiting the same child twice shares one hook.

### When `returnValue` polls instead

`returnValue` falls back to polling the child, inside a step that holds its worker slot until the child finishes, when the waiting code is not the workflow that started it:

- a step, API route, or other server code (for example, a step that calls `start()` and awaits the result itself)
- a different workflow that was handed the `Run` as an argument

It also polls for a child started on another deployment (`deploymentId`) whose SDK predates the system hook, and for every child started while [`WORKFLOW_CHILD_RUN_COMPLETION_HOOK=0`](/docs/configuration/runtime-tuning#workflow_child_run_completion_hook) is set.

## Fan-out pattern: chunked spawning

When spawning hundreds of children, batch the `start()` calls to avoid overwhelming the system. Each awaited child gets its own system hook, so a chunk costs nothing while it waits.

```typescript
import { start } from "workflow/api";

declare function queryDatabase(reportId: string, query: string): Promise<string>; // @setup
declare function formatReport(reportId: string, data: string): Promise<string>; // @setup

const CHUNK_SIZE = 10;

export async function generateReport(reportId: string, query: string) {
  "use workflow";

  const data = await queryDatabase(reportId, query);
  const formatted = await formatReport(reportId, data);
  return { reportId, formatted };
}

export async function largeReportBatch(
  reportConfigs: Array<{ id: string; query: string }>
) {
  "use workflow";

  const results = [];
  for (let i = 0; i < reportConfigs.length; i += CHUNK_SIZE) {
    const chunk = reportConfigs.slice(i, i + CHUNK_SIZE);
    const runs = await Promise.all(
      chunk.map((config) => start(generateReport, [config.id, config.query]))
    );
    results.push(...(await Promise.all(runs.map((run) => run.returnValue))));
  }

  return { total: results.length, results };
}
```

## Error handling

### Tolerating partial failures

Use `Promise.allSettled` over the children's `returnValue` so one failing child doesn't abort its siblings. A failed child's entry is rejected with `WorkflowRunFailedError`, whose `cause` is the error the child threw.

```typescript
import { start } from "workflow/api";

declare function processDocument(
  documentId: string
): Promise<{ documentId: string; summary: string }>; // @setup

export async function processDocumentBatchTolerant(documentIds: string[]) {
  "use workflow";

  const runs = await Promise.all(
    documentIds.map((documentId) => start(processDocument, [documentId]))
  );
  const settled = await Promise.allSettled(runs.map((run) => run.returnValue));

  const results = settled
    .filter(
      (entry): entry is PromiseFulfilledResult<{ documentId: string; summary: string }> =>
        entry.status === "fulfilled"
    )
    .map((entry) => entry.value);

  const failed = settled.filter((entry) => entry.status === "rejected").length;

  return { processed: results.length, failed, results };
}
```

### Retrying failed children

When a child fails, start a replacement. Track restart counts to prevent infinite retry loops.

```typescript
import { start } from "workflow/api";

declare function processDocument(
  documentId: string
): Promise<{ documentId: string; summary: string }>; // @setup

async function processDocumentWithRetries(
  documentId: string,
  maxRestarts: number
): Promise<{ documentId: string; summary: string }> {
  for (let attempt = 0; ; attempt++) {
    const run = await start(processDocument, [documentId]);
    try {
      return await run.returnValue;
    } catch (error) {
      if (attempt >= maxRestarts) throw error;
    }
  }
}
```

## Signaling the parent before the child finishes

The system hook fires only when the child finishes. When the parent needs to hear from a child mid-run (a progress milestone, an approval request, a partial result), create a [hook](/docs/foundations/hooks) in the parent and pass its token to the child, which resumes it from a step:

```typescript
import { createHook } from "workflow";
import { resumeHook, start } from "workflow/api";

declare function prepareDraft(documentId: string): Promise<string>; // @setup
declare function publishDraft(draft: string): Promise<void>; // @setup

async function notifyDraftReady(token: string, draft: string) {
  "use step";
  await resumeHook(token, { draft });
}

export async function draftDocument(documentId: string, draftToken: string) {
  "use workflow";

  const draft = await prepareDraft(documentId);
  await notifyDraftReady(draftToken, draft); // the parent continues from here
  await publishDraft(draft);
  return { documentId, published: true };
}

export async function reviewDocument(documentId: string) {
  "use workflow";

  const draftReady = createHook<{ draft: string }>();
  const run = await start(draftDocument, [documentId, draftReady.token]);

  const { draft } = await draftReady; // mid-run signal from the child
  const result = await run.returnValue; // completion, via the system hook
  return { draft, ...result };
}
```

## Tips

- **Await only the children you need**: A child whose parent never awaits its `returnValue` costs one extra hook lookup when it finishes, and nothing in the parent.
- **Use chunked spawning for large batches**: Starting 500 children at once can create a large burst of work. Break the work into chunks of 10–50.
- **Watch the parent's log too**: Each child bounds its own log, but the parent records events for spawning and for collecting every child (the spawn step, the system hook, and the steps that read the child), so the parent's log grows with the number of children. Count those events per child against the parent's own [run limits](/worlds/vercel#per-run-limits); when the parent alone would exceed them, add a layer, so each parent spawns a modest number of intermediate runs that in turn spawn the leaves.
- **Account for each child's retry semantics**: Steps inside child workflows retry independently. The parent only sees the child's final result or error.
- **Cancel children through the SDK**: [`run.cancel()`](/docs/api-reference/workflow-api/get-run), `cancelRun()` and `cancelRuns()`, `workflow cancel`, and the `workflow web` UI resume a waiting parent when they cancel its child. A cancellation written to the World directly, bypassing the SDK, does not, and leaves the parent suspended until something resumes the hook.
- **Use `deploymentId: "latest"` when children should run on the most recent deployment**: See [Versioning](/docs/foundations/versioning) for the full model and the [`start()` API reference](/docs/api-reference/workflow-api/start#using-deploymentid-latest) for compatibility considerations.

## Key APIs

- [`start()`](/docs/api-reference/workflow-api/start): Spawns a new workflow run and returns a `Run` whose `returnValue` the parent can await.
- [`getRun()`](/docs/api-reference/workflow-api/get-run): Documents the `Run` handle, with `returnValue`, `status`, and `cancel()`.
- [`createHook()`](/docs/api-reference/workflow/create-hook): Creates a hook for signals from a child before it finishes.
- [`resumeHook()`](/docs/api-reference/workflow-api/resume-hook): Resumes a parent's hook from a step in the child.
- [`"use workflow"`](/docs/foundations/workflows-and-steps): Marks the orchestrator function.
- [`"use step"`](/docs/foundations/workflows-and-steps): Marks functions with full Node.js access.
