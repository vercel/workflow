Use this pattern when a platform runs orchestration whose shape is chosen after deploy, such as a set of "missions" that operators assemble and review, over a fixed catalog of steps that ship with the app. The steps are ordinary deployed code. Each mission is a short, reviewed JavaScript template that [`start()`](/docs/api-reference/workflow-api/start) runs as a [dynamic workflow](/docs/advanced/dynamic-workflows), with no build or deploy per mission.

<Callout type="warning">
Dynamic workflows are **experimental**. Before this recipe runs:

- The deployment must set `WORKFLOW_EXPERIMENTAL_DYNAMIC_WORKFLOWS=1`. Without it, `start()` throws.
- A dynamic run can only start on the deployment that calls `start()`.
- On Vercel, the project must have dynamic-workflow storage enabled. Without it, `start()` throws.

See [Enabling dynamic workflows](/docs/advanced/dynamic-workflows#enabling-dynamic-workflows) and [World support](/docs/advanced/dynamic-workflows#world-support) for the details.
</Callout>

## When to use this

- **Templates are yours.** Your team writes or reviews every mission template, the same way you would review a pull request.
- **The catalog is fixed.** Every step a mission can call is already deployed. Missions only recombine them.
- **Missions change more often than deploys.** New combinations of existing steps should not need a build.

This is not a way to run code written by end users, or generated by a model from their input. Dynamic source runs with your deployment's full privileges; see [Security](#security). If your workflows are known at build time, write normal workflow functions instead.

## The step catalog

The catalog is a workflow file of ordinary step functions, compiled and deployed with the app. Dynamic source cannot define steps, so everything a mission does outside of orchestration happens here.

```typescript title="workflows/mission-steps.ts" lineNumbers
import { resumeHook } from "workflow/api";

export interface BirdDetection {
  id: number;
  species: string;
  confidence: number;
}

declare function callVisionModel(image: string, maxDetections: number): Promise<BirdDetection[]>; // @setup
declare function pageReviewer(detection: BirdDetection, token: string): Promise<void>; // @setup
declare function postToChannel(message: string): Promise<void>; // @setup

/** Detects birds in an image with a vision model. */
export async function detectBirds(request: { image: string; count: number }) {
  "use step";
  return await callVisionModel(request.image, request.count);
}

/** Asks an expert to review one detection. */
export async function requestExpertReview(detection: BirdDetection, token: string) {
  "use step";
  await pageReviewer(detection, token);
  return { detectionId: detection.id, token };
}

/** Posts a status message. */
export async function notify(message: string) {
  "use step";
  await postToChannel(message);
  return { delivered: message };
}

/** Fans a child mission's result back into its parent's hook. */
export async function reportToParent(token: string, report: unknown) {
  "use step";
  // Throws, and so retries, until the parent has created its hook.
  await resumeHook(token, report);
}
```

## Mission templates

A mission template is a constant source string plus the steps it may call. The bird survey mission asks a model for detections, fans out one expert review per detection, and aggregates the verdicts:

```typescript title="lib/missions.ts" lineNumbers
import {
  detectBirds,
  notify,
  reportToParent,
  requestExpertReview,
} from "@/workflows/mission-steps";

const BIRD_SURVEY_SOURCE = `
async function workflow(input) {
  "use workflow";
  const detections = await steps.llm({ image: input.image, count: input.count });

  const reviews = await Promise.all(
    detections.map(async (detection) => {
      const token = input.reviewTokenPrefix + ":" + detection.id;
      const review = createHook({ token });
      await steps.expertReview(detection, token);
      const verdict = await review;
      return { ...detection, confirmed: verdict.confirmed === true };
    })
  );

  const confirmed = reviews.filter((review) => review.confirmed).length;
  const result = { image: input.image, confirmed, reviews };
  await steps.notify(
    input.image + ": " + confirmed + " of " + reviews.length + " confirmed"
  );
  if (input.parentToken) {
    await steps.reportToParent(input.parentToken, result);
  }
  return result;
}
`;

export const MISSIONS = {
  birdSurvey: {
    source: BIRD_SURVEY_SOURCE,
    // Alias the source calls -> imported step function.
    steps: {
      llm: detectBirds, // [!code highlight]
      expertReview: requestExpertReview, // [!code highlight]
      notify,
      reportToParent,
    },
  },
};

export type MissionId = keyof typeof MISSIONS;

export function reviewTokenPrefix(missionId: string) {
  return `mission:${missionId}:review`;
}

export function reviewToken(missionId: string, detectionId: number) {
  return `${reviewTokenPrefix(missionId)}:${detectionId}`;
}
```

A few properties of the template are deliberate:

- **Every parameter arrives as `input`.** The image, the count, and the hook tokens are run input, never interpolated into the source. The source is fixed, so it is exactly the code that was reviewed, and every run of it shares one [workflow ID](/docs/advanced/dynamic-workflows#workflow-ids).
- **The step map holds imported functions.** The build stamps a `stepId` on each imported step function, and that ID binds `steps.llm` in the source to `detectBirds` in the deployment. The source can only call the aliases in this map; see [Security](#security) for what that does and does not guarantee.
- **Hook tokens are deterministic and unique.** Each review token is derived from a mission ID the server generates, so replay recreates the same hook and concurrent missions never share a token. See [custom tokens](/docs/foundations/hooks#custom-tokens-for-deterministic-hooks).
- **It is plain JavaScript.** Only `steps`, `createHook`, `sleep`, and the usual [workflow globals](/docs/api-reference/workflow-globals) are in scope. See [What the source can use](/docs/advanced/dynamic-workflows#what-the-source-can-use).

## Start a mission from a route handler

`start()` accepts the source directly, so a route handler can start a mission with no wrapper workflow. The route picks a template by ID; the request never carries source.

```typescript title="app/api/missions/route.ts" lineNumbers
import { start } from "workflow/api";
import { z } from "zod";
import { MISSIONS, reviewTokenPrefix } from "@/lib/missions";

const startRequest = z.object({
  mission: z.literal("birdSurvey"),
  image: z.string().min(1).max(200),
  count: z.number().int().min(1).max(20),
});

export async function POST(request: Request) {
  // Authenticate the caller first: a mission runs deployed steps.
  const parsed = startRequest.safeParse(await request.json());
  if (!parsed.success) {
    return Response.json({ error: parsed.error.message }, { status: 400 });
  }
  const { mission, image, count } = parsed.data;

  const missionId = crypto.randomUUID();
  const input = {
    image,
    count,
    reviewTokenPrefix: reviewTokenPrefix(missionId),
  };

  const { source, steps } = MISSIONS[mission];
  const run = await start(source, [input], { // [!code highlight]
    experimental_dynamic: { steps }, // [!code highlight]
  }); // [!code highlight]

  return Response.json({ runId: run.runId, missionId });
}
```

`start()` validates the source before it writes anything: a template with a syntax error, an `import`, or a missing `"use workflow"` directive throws here rather than failing on a queue delivery. See [Rules for the source](/docs/advanced/dynamic-workflows#rules-for-the-source).

## Resume a review

Each review waits on its own hook. The review route rebuilds the token from the mission ID and detection ID, confirms the hook belongs to the run, and resumes it:

```typescript title="app/api/missions/[runId]/reviews/route.ts" lineNumbers
import { getHookByToken, resumeHook } from "workflow/api";
import { HookNotFoundError } from "workflow/errors";
import { z } from "zod";
import { reviewToken } from "@/lib/missions";

declare function assertCanReview(request: Request, missionId: string): Promise<void>; // @setup

const reviewRequest = z.object({
  missionId: z.string().uuid(),
  detectionId: z.number().int().min(0),
  confirmed: z.boolean(),
});

export async function POST(
  request: Request,
  { params }: { params: Promise<{ runId: string }> }
) {
  const { runId } = await params;
  const parsed = reviewRequest.safeParse(await request.json());
  if (!parsed.success) {
    return Response.json({ error: parsed.error.message }, { status: 400 });
  }
  const { missionId, detectionId, confirmed } = parsed.data;

  // Knowing a token does not authorize the caller.
  await assertCanReview(request, missionId); // [!code highlight]

  try {
    const hook = await getHookByToken(reviewToken(missionId, detectionId));
    if (hook.runId !== runId) {
      return Response.json({ error: "No such review" }, { status: 404 });
    }
    await resumeHook(hook, { confirmed }); // [!code highlight]
    return Response.json({ ok: true });
  } catch (error) {
    if (HookNotFoundError.is(error)) {
      return Response.json({ error: "No pending review" }, { status: 404 });
    }
    throw error;
  }
}
```

A review that arrives before its hook exists, or after the mission has finished, gets a 404. See [Authorize before calling `resumeHook()`](/docs/foundations/hooks#authorize-before-calling-resumehook).

## Report mission status

A status route reads the run with [`getRun()`](/docs/api-reference/workflow-api/get-run). A dynamic run's result type is `unknown` to TypeScript, so pass the type you expect:

```typescript title="app/api/missions/[runId]/route.ts" lineNumbers
import { getRun } from "workflow/api";

interface BirdSurveyResult {
  image: string;
  confirmed: number;
  reviews: Array<{ id: number; species: string; confirmed: boolean }>;
}

export async function GET(
  _request: Request,
  { params }: { params: Promise<{ runId: string }> }
) {
  const { runId } = await params;
  const run = getRun<BirdSurveyResult>(runId);
  if (!(await run.exists)) {
    return Response.json({ error: "Mission not found" }, { status: 404 });
  }

  const status = await run.status;
  if (status === "completed") {
    return Response.json({ status, result: await run.returnValue });
  }
  return Response.json({ status });
}
```

## Variant: approval with a timeout

A mission can race a hook against a durable [`sleep()`](/docs/api-reference/workflow/sleep), so a request that nobody answers still finishes. Add it to `MISSIONS` next to the bird survey, and pass the token and the timeout as input:

```typescript title="lib/missions.ts" lineNumbers
import { notify } from "@/workflows/mission-steps";

const APPROVAL_SOURCE = `
async function workflow(input) {
  "use workflow";
  await steps.notify("Approval requested: " + input.subject);

  const approval = createHook({ token: input.approvalToken });
  const decision = await Promise.race([
    approval.then((payload) => ({
      approved: payload.approved === true,
      timedOut: false,
    })),
    sleep(input.timeout).then(() => ({ approved: false, timedOut: true })),
  ]);

  await steps.notify(
    input.subject + ": " + (decision.approved ? "approved" : "not approved")
  );
  return decision;
}
`;

declare const BIRD_SURVEY_MISSION: { source: string; steps: Record<string, any> }; // @setup
export const MISSIONS = {
  // birdSurvey: { ... },
  birdSurvey: BIRD_SURVEY_MISSION, // @setup
  approval: {
    source: APPROVAL_SOURCE,
    steps: { notify },
  },
};

export function approvalToken(missionId: string) {
  return `mission:${missionId}:approval`;
}
```

Start it the same way, with input such as `{ subject, approvalToken: approvalToken(missionId), timeout: "1d" }`. Resuming the token with `{ approved: true }` returns `{ approved: true, timedOut: false }`; if nobody resumes it within the timeout, the run returns `{ approved: false, timedOut: true }`. See [Timeouts](/cookbook/common-patterns/timeouts) for the general pattern.

## Fan out at scale

To run one mission per image across a large batch, start the missions from a static parent workflow and fan back in through hooks, as in [Child Workflows](/cookbook/advanced/child-workflows). Each child mission ends by calling `steps.reportToParent(input.parentToken, result)`, which resumes the hook its parent created for it.

```typescript title="workflows/bird-survey.ts" lineNumbers
import { createHook } from "workflow";
import { start } from "workflow/api";
import { MISSIONS, type MissionId } from "@/lib/missions";

interface BirdSurveyResult {
  image: string;
  confirmed: number;
}

export async function birdSurvey(surveyId: string, images: string[]) {
  "use workflow";

  const hooks = images.map((_, index) =>
    createHook<BirdSurveyResult>({ token: `survey:${surveyId}:mission:${index}` })
  );
  await Promise.all(
    images.map((image, index) =>
      startMission("birdSurvey", {
        image,
        count: 5,
        reviewTokenPrefix: `survey:${surveyId}:review:${index}`,
        parentToken: `survey:${surveyId}:mission:${index}`, // [!code highlight]
      })
    )
  );
  const results = await Promise.all(hooks); // [!code highlight]

  return {
    images: results.length,
    confirmed: results.reduce((total, result) => total + result.confirmed, 0),
    results,
  };
}

/** Starts one mission as a dynamic child run. */
async function startMission(mission: MissionId, input: Record<string, unknown>) {
  "use step";
  const { source, steps } = MISSIONS[mission];
  const run = await start(source, [input], { experimental_dynamic: { steps } });
  return { runId: run.runId };
}
```

`startMission` is a step, not workflow code: `start()` is a side effect, and the `steps` map holds function references that must not cross a step boundary as serialized data. The parent itself is a normal static workflow, so start it from a route with `start(birdSurvey, [surveyId, images])`, and bound the number of images there.

The child-workflows recipe covers the rest of the fan-out: [chunked spawning](/cookbook/advanced/child-workflows#fan-out-pattern-chunked-spawning) for hundreds of children, [partial failures](/cookbook/advanced/child-workflows#tolerating-partial-failures), and the parent's own event-log growth.

## Security

Dynamic source runs with the full privileges of your deployment's functions; the workflow sandbox is for determinism, not isolation. This recipe is safe because of how the source is chosen, not because of where it runs:

- **Templates are platform code.** They live in your repository and go through review like any other change. The start route selects one by ID and never accepts source in the request.
- **Parameters are input, not source.** Building source from request fields, even with escaping, turns every caller into a code author. Passing them as `input` keeps the executed code identical to the reviewed code.
- **Model output is data.** `detectBirds` returns detections for the template to iterate over. Do not ask a model to write the mission.
- **The step map is not a boundary.** A reviewed template that calls a missing alias fails its run, but the map does not stop source that is trying to reach other steps or the host. Review is the boundary.
- **Authorize every resume.** Hook tokens route a payload to a run; they do not prove who sent it.

See [Security](/docs/advanced/dynamic-workflows#security) on the concept page for the full model, including what encryption does and does not protect.

## Tips

- **Treat a template's bytes as its identity.** The workflow ID hashes the raw source and the step bindings, so reformatting a template, editing a comment, or rebinding an alias creates a new workflow and splits its runs in observability. Keep templates as constants and change them deliberately.
- **Bind only the steps a template calls.** On Vercel, the bindings count against the run's execution-context limit, and long step IDs cost more than long aliases. See [Rules for the source](/docs/advanced/dynamic-workflows#rules-for-the-source).
- **Cap what callers control.** Bound counts, batch sizes, and string lengths in the start route, since they decide how many steps and hooks a mission creates.
- **Test templates locally, then on a preview.** The Local World runs dynamic workflows, so `WORKFLOW_EXPERIMENTAL_DYNAMIC_WORKFLOWS=1 pnpm dev` checks a template's validation and behavior. It does not enforce Vercel's execution-context limit, so check a template with many bindings on a preview deployment too.

## Key APIs

- [`start()`](/docs/api-reference/workflow-api/start): Starts a run from workflow source with `experimental_dynamic.steps`.
- [`createHook()`](/docs/api-reference/workflow/create-hook): Waits for an external signal, such as a review, inside the source.
- [`sleep()`](/docs/api-reference/workflow/sleep): Durable timer, raced against a hook for timeouts.
- [`getHookByToken()`](/docs/api-reference/workflow-api/get-hook-by-token): Looks up a pending hook before resuming it.
- [`resumeHook()`](/docs/api-reference/workflow-api/resume-hook): Delivers a review or approval to the waiting run.
- [`getRun()`](/docs/api-reference/workflow-api/get-run): Reads a mission's status and result.
