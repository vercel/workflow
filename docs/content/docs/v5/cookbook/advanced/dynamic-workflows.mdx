A platform that imports customers' legacy CRM data usually needs nothing more than a field mapping. Then a customer arrives whose export only makes sense under their own conventions. Acme groups accounts by contract lineage, so a regional account must be loaded after the account it reports to. The same person appears once per region. Two account rows on one contract are one account, and when their owners disagree, a person has to choose.

An integration engineer, perhaps with an agent drafting it, writes those rules as a short JavaScript program over the platform's deployed migration steps. A reviewer approves it, and the platform runs it with [`start()`](/docs/api-reference/workflow-api/start) as a [dynamic workflow](/docs/advanced/dynamic-workflows). The program is published after the platform deployed, and running it needs no rebuild or redeploy. It survives pauses for approvals and restarts like any workflow, and it applies the same approved rules to every record.

<Callout type="warning">
Dynamic workflows are **experimental**. Before this recipe runs:

- The deployment must set `WORKFLOW_EXPERIMENTAL_DYNAMIC_WORKFLOWS=1`. Without it, `start()` throws.
- A dynamic run can only start on the deployment that calls `start()`.
- On Vercel, the project must have dynamic-workflow storage enabled. Without it, `start()` throws.

See [Enabling dynamic workflows](/docs/advanced/dynamic-workflows#enabling-dynamic-workflows) and [World support](/docs/advanced/dynamic-workflows#world-support) for the details.
</Callout>

## When to use this

- **Use static configuration for routine imports.** If a customer's import is "column `acct_name` goes to `name`", keep a static workflow that reads a mapping. It needs no review of code and has better types and errors.
- **Use a procedure when the rules are an algorithm.** Acme's grouping, identity, and dependency order take loops, maps, and a traversal. You could encode them in JSON, but then the platform owns an interpreter for that JSON.
- **Use an agent to write the procedure, not to run it.** A durable agent would reconsider every record. Here an agent can help draft the procedure, a person approves it, and the workflow executes exactly those rules for every record, every time.

<Callout type="error">
A procedure is trusted application code with your deployment's privileges, not a sandboxed customer script. Only run source approved under your application-code review process; a fixed catalog of steps is an integration contract, not a security boundary. See [Security](/docs/advanced/dynamic-workflows#security).
</Callout>

## The deployed catalog

The platform deploys a fixed set of migration steps once. Steps do the I/O: they read the legacy export and write to the destination. The procedure decides what to write and in what order, and reaches the steps only through `steps.<name>()`.

```typescript title="workflows/migration-steps.ts" lineNumbers
declare const legacyCrm: { page(dataset: string, cursor?: number): Promise<{ records: unknown[]; nextCursor?: number }> }; // @setup
declare const destinations: { lookup(r: any): Promise<any>; stage(r: any): Promise<any>; apply(r: any): Promise<any>; verify(r: any): Promise<any> }; // @setup
declare function notifyReviewer(r: any): Promise<void>; // @setup
declare function saveReport(r: any): Promise<string>; // @setup

/** One page of the customer's legacy export. */
export async function readSourcePage(request: { dataset: string; cursor?: number }) {
  "use step";
  return await legacyCrm.page(request.dataset, request.cursor);
}

/** Which of these keys the destination already has. */
export async function lookupDestination(request: { destinationId: string; keys: string[] }) {
  "use step";
  return await destinations.lookup(request);
}

/** Validates operations and returns an immutable plan with a content-derived `planId`. */
export async function stageChanges(request: {
  migrationId: string;
  destinationId: string;
  groupKey: string;
  operations: unknown[];
  dependsOn?: unknown[];
}) {
  "use step";
  return await destinations.stage(request);
}

/** Asks a reviewer to resume `token` with `{ approved, owner? }`. */
export async function requestApproval(request: { planId: string; token: string; summary: string }) {
  "use step";
  await notifyReviewer(request);
  return { planId: request.planId, token: request.token };
}

/** Applies a staged plan to the destination named in the plan. */
export async function applyChanges(request: { plan: unknown; idempotencyKey: string }) {
  "use step";
  return await destinations.apply(request);
}

/** Integrity invariants and the resulting records. */
export async function verifyChanges(request: { destinationId: string; migrationId: string; results: unknown[] }) {
  "use step";
  return await destinations.verify(request);
}

export async function publishReport(request: { migrationId: string; results: unknown }) {
  "use step";
  return { reportId: await saveReport(request) };
}
```

`legacyCrm` and `destinations` stand for your integration adapters. The destination adapter, not the procedure, owns the contract every procedure relies on:

- **Supported operations only:** `createAccount`, `createContact`, `linkContact`, `setParent`, `setOwner`, `markFinal`, `mergeAccount`, and `mergeContact`. There is no step that evaluates arbitrary code.
- **Referential integrity:** every parent and contact link must resolve when the plan is applied, to a record created earlier in the plan or by a plan listed in `dependsOn`.
- **Immutable plans:** `planId` is a hash of the plan's migration, destination, group, operations, and dependencies, and `applyChanges` takes the destination from the plan, so a caller cannot point an approved plan at another destination.
- **Conflicts block writes:** merging two accounts whose owners differ records a conflict on the plan, and `applyChanges` refuses a plan with conflicts.
- **Idempotency:** the key is `"apply:" + planId`. Repeating it returns the first result; reusing it for a different payload is rejected.

The steps are bound under their own names when a procedure starts:

```typescript title="lib/migration-catalog.ts" lineNumbers
import {
  applyChanges,
  lookupDestination,
  publishReport,
  readSourcePage,
  requestApproval,
  stageChanges,
  verifyChanges,
} from "@/workflows/migration-steps";

export const MIGRATION_CATALOG = {
  readSourcePage,
  lookupDestination,
  stageChanges,
  requestApproval,
  applyChanges,
  verifyChanges,
  publishReport,
};
```

## Procedure A: parent-first

This is Acme's procedure. It is a file in the integration team's repository, not part of the deployment. It migrates each account family as its own plan, all families at once, and only the family whose owners disagree waits for a person:

{/* @skip-typecheck: dynamic workflow source, evaluated with injected steps and createHook */}
```javascript title="procedures/acme-parent-first.js" lineNumbers
async function workflow(input) {
  "use workflow";
  const scope = { migrationId: input.migrationId, destinationId: input.destinationId };

  const rows = [];
  let cursor;
  do {
    const page = await steps.readSourcePage({ dataset: input.dataset, cursor });
    rows.push(...page.records);
    cursor = page.nextCursor;
  } while (cursor !== undefined);

  // This customer's rules: a family is every account under one contract root,
  // accounts on the same contract are one account, and a contact is one person
  // per normalized email within a family.
  const accounts = rows.filter((row) => row.kind === "account");
  const contacts = rows.filter((row) => row.kind === "contact");
  const families = new Map();
  for (const row of accounts) {
    const family = row.contract.split("/")[0];
    families.set(family, [...(families.get(family) || []), row]);
  }

  function familyOperations(members, owner) {
    // Parent-first: an account is written only after the account it reports to.
    const ordered = [];
    const visit = (row) => {
      if (ordered.includes(row)) return;
      const parent = members.find((other) => other.id === row.parent);
      if (parent) visit(parent);
      ordered.push(row);
    };
    members.forEach(visit);

    const ops = [];
    const survivors = new Map();
    const survivorOf = new Map();
    for (const row of ordered) {
      ops.push({ op: "createAccount", key: row.id, name: row.name, owner: row.owner, sources: [row.id] });
      if (row.parent) ops.push({ op: "setParent", account: row.id, parent: row.parent });
      const survivor = survivors.get(row.contract);
      if (!survivor) {
        survivors.set(row.contract, row.id);
        survivorOf.set(row.id, row.id);
        continue;
      }
      survivorOf.set(row.id, survivor);
      if (owner) {
        ops.push({ op: "setOwner", key: survivor, owner }, { op: "setOwner", key: row.id, owner });
      }
      ops.push({ op: "mergeAccount", from: row.id, into: survivor });
    }

    const people = new Map();
    for (const row of contacts) {
      if (!survivorOf.has(row.account)) continue;
      const email = row.email.trim().toLowerCase();
      const person = people.get(email) || { key: row.id, name: row.name, email, sources: [], accounts: [] };
      person.sources.push(row.id);
      person.accounts.push(survivorOf.get(row.account));
      people.set(email, person);
    }
    for (const person of people.values()) {
      ops.push({ op: "createContact", key: person.key, name: person.name, email: person.email, sources: person.sources });
      for (const account of new Set(person.accounts)) {
        ops.push({ op: "linkContact", contact: person.key, account });
      }
    }
    return ops;
  }

  async function migrateFamily(family, members) {
    const stage = (owner) =>
      steps.stageChanges({ ...scope, groupKey: family, operations: familyOperations(members, owner) });
    let plan = await stage();
    if (plan.conflicts.length > 0) {
      // Only this family waits for a person; the others carry on.
      const token = input.tokenPrefix + ":" + family;
      const review = createHook({ token });
      try {
        const owners = plan.conflicts.flatMap((conflict) => conflict.values);
        await steps.requestApproval({ planId: plan.planId, token, summary: family + ": choose an owner from " + owners.join(", ") });
        const decision = await review;
        if (!decision.approved) return { family, status: "skipped" };
        plan = await stage(decision.owner || owners[0]);
      } finally {
        review.dispose();
      }
    }
    const result = await steps.applyChanges({ plan, idempotencyKey: "apply:" + plan.planId });
    return { family, status: "applied", result };
  }

  const outcomes = await Promise.all([...families].map(([family, members]) => migrateFamily(family, members)));
  const verification = await steps.verifyChanges({
    ...scope,
    results: outcomes.filter((outcome) => outcome.result).map((outcome) => outcome.result),
  });
  const summary = outcomes.map(({ family, status }) => ({ family, status }));
  const report = await steps.publishReport({ migrationId: input.migrationId, results: { families: summary, verification } });
  return { families: summary, verification, report };
}
```

The procedure owns the customer's policy, and nothing in the catalog knows about it:

- **Families.** Accounts are grouped by the root of their contract number, so `C-100`, `C-100/E`, and `C-100/W` are one family. Each family becomes its own plan, and `Promise.all` runs them concurrently.
- **Parent-first order.** Within a family, an account is written only after the account it reports to. The destination checks that every parent resolves, so writing a child first would fail the plan.
- **One account per contract.** Two rows on the same contract become one account through `mergeAccount`. If their owners differ, the plan comes back with a conflict, and the procedure asks a person.
- **One person per email within a family.** Ada Park appears once per region with differently cased emails, and becomes one contact linked to both regions. `info@initech.com` appears in two families, so it stays two contacts.
- **Review before waiting.** The approval hook is created before `requestApproval` sends its token, so a fast reviewer can never miss it, and it is disposed once the review settles. A rejected family is skipped; the others are applied either way.

Every parameter, including the dataset, the destination, and the token prefix, arrives as `input`. The source is never templated, so what runs is exactly the file that was reviewed.

## Publish and start it

Nothing about this procedure existed when the platform deployed. After the procedure is reviewed and merged in the integration repository, a release job stores the file and its step names wherever the platform keeps procedures, keyed by a stable procedure ID such as `acme-parent-first`. A route then starts it on the running deployment:

```typescript title="app/api/migrations/route.ts" lineNumbers
import { start } from "workflow/api";
import { z } from "zod";
import { MIGRATION_CATALOG } from "@/lib/migration-catalog";

declare const procedures: { latest(id: string): Promise<{ source: string; steps: Record<string, string> } | null> }; // @setup
declare function assertOperator(request: Request): Promise<void>; // @setup

const startRequest = z.object({
  procedureId: z.string(),
  dataset: z.string(),
  destinationId: z.string(),
});

export async function POST(request: Request) {
  await assertOperator(request);
  const parsed = startRequest.safeParse(await request.json());
  if (!parsed.success) {
    return Response.json({ error: parsed.error.message }, { status: 400 });
  }
  const procedure = await procedures.latest(parsed.data.procedureId);
  if (!procedure) {
    return Response.json({ error: "Unknown procedure" }, { status: 404 });
  }

  // Bind each name the procedure calls to the imported step function.
  const steps = Object.fromEntries(
    Object.entries(procedure.steps).map(([alias, name]) => [
      alias,
      MIGRATION_CATALOG[name as keyof typeof MIGRATION_CATALOG],
    ])
  );

  const id = crypto.randomUUID();
  const migrationId = `migration-${id}`;
  const run = await start(procedure.source, [{ // [!code highlight]
    dataset: parsed.data.dataset,
    destinationId: parsed.data.destinationId,
    migrationId,
    tokenPrefix: `migration:${id}`,
  }], { experimental_dynamic: { steps } }); // [!code highlight]

  return Response.json({ runId: run.runId, migrationId });
}
```

The step map holds the **imported** step functions: the build stamps a `stepId` on each one, and that ID is what binds `steps.applyChanges` in the source to this deployment's step. See [Operating it](#operating-it) for what to check before starting a stored procedure.

The whole sequence is:

1. Deploy the catalog and these routes once.
2. Write and review a procedure, then publish it to the store.
3. `POST /api/migrations` with the procedure ID, the dataset, and the destination.
4. A reviewer answers any approval it requests.
5. Read the result with [`getRun()`](/docs/api-reference/workflow-api/get-run); the run's return value holds the verification and the report ID.

## Review an owner conflict

Initech's two rows share contract `C-300` but list different owners, so only that family waits. Its token is the run's `tokenPrefix` plus the family. The review route resumes it after authorizing the reviewer:

```typescript title="app/api/migrations/[runId]/reviews/route.ts" lineNumbers
import { getHookByToken, resumeHook } from "workflow/api";
import { HookNotFoundError } from "workflow/errors";
import { z } from "zod";

declare function assertCanReview(request: Request, migrationId: string): Promise<void>; // @setup

const reviewRequest = z.object({
  migrationId: z.string().startsWith("migration-"),
  family: z.string(),
  approved: z.boolean(),
  owner: z.string().optional(),
});

export async function POST(
  request: Request,
  { params }: { params: Promise<{ runId: string }> }
) {
  const { runId } = await params;
  const parsed = reviewRequest.safeParse(await request.json());
  if (!parsed.success) {
    return Response.json({ error: parsed.error.message }, { status: 400 });
  }
  const { migrationId, family, approved, owner } = parsed.data;
  // Knowing a token does not authorize the caller.
  await assertCanReview(request, migrationId); // [!code highlight]

  const token = `migration:${migrationId.slice("migration-".length)}:${family}`;
  try {
    const hook = await getHookByToken(token);
    if (hook.runId !== runId) {
      return Response.json({ error: "No such review" }, { status: 404 });
    }
    await resumeHook(hook, { approved, owner }); // [!code highlight]
    return Response.json({ ok: true });
  } catch (error) {
    if (HookNotFoundError.is(error)) {
      return Response.json({ error: "No pending review" }, { status: 404 });
    }
    throw error;
  }
}
```

A review for a family that never conflicted, or one that arrives after the review settled, gets a 404: that hook never existed, or the procedure already disposed it. See [Authorize before calling `resumeHook()`](/docs/foundations/hooks#authorize-before-calling-resumehook).

## What survives a pause, and what changed

While Initech waits, the run is suspended on its hook, using no compute, and the other two families are already applied: Acme's three accounts with Ada linked to both regions, and Globex. A restart in between does not matter, and neither does a new deploy: the run stays on the deployment that started it, and when the review arrives it replays its stored procedure and recorded step results instead of re-reading or re-writing anything.

After the reviewer picks `sam` as Initech's owner, the destination holds:

| Account | Parent | Owner | From legacy rows |
| --- | --- | --- | --- |
| Acme Holdings | none | dana | `acct-acme` |
| Acme East | Acme Holdings | dana | `acct-acme-east` |
| Acme West | Acme Holdings | dana | `acct-acme-west` |
| Globex | none | lee | `acct-globex` |
| Initech | none | sam | `acct-initech`, `acct-initech-ltd` |

| Contact | Linked to | From legacy rows |
| --- | --- | --- |
| Ada Park, `ada@acme.com` | Acme East, Acme West | `ct-ada-east`, `ct-ada-west` |
| Initech front desk, `info@initech.com` | Initech | `ct-info-initech` |
| Globex reseller desk, `info@initech.com` | Globex | `ct-info-globex` |

`verifyChanges` reports no dangling links, no provisional accounts, and no duplicate contacts. A field mapping could not produce this: it would create six accounts and four contacts, merge nothing, and either link the two `info@initech.com` rows together or keep Ada twice.

## Procedure B: provisional first

Another customer team prefers to see everything land before anything is reconciled. Procedure B runs over the same catalog and is published later, without a deploy. It is structured differently: instead of building each family carefully and pausing only the ambiguous one, it writes every row as it is, then stages one consolidation over all of it, and asks for one review of the whole change:

{/* @skip-typecheck: excerpt of dynamic workflow source */}
```javascript title="procedures/acme-provisional-first.js (excerpt)" lineNumbers
  // 1. Land every row as written: provisional, flat, one record per row.
  const load = await steps.stageChanges({
    ...scope,
    groupKey: "load",
    operations: [
      ...accounts.map((row) => ({ op: "createAccount", key: row.id, name: row.name, owner: row.owner, status: "provisional", sources: [row.id] })),
      ...contacts.flatMap((row) => [
        { op: "createContact", key: row.id, name: row.name, email: row.email.trim().toLowerCase(), sources: [row.id] },
        { op: "linkContact", contact: row.id, account: row.account },
      ]),
    ],
  });
  const loaded = await steps.applyChanges({ plan: load, idempotencyKey: "apply:" + load.planId });

  // 2. Reconcile the landed records with this customer's rules, as one change:
  //    setParent for every child, mergeAccount for rows on the same contract,
  //    mergeContact for one person per email within a family, markFinal for
  //    every surviving account.
  function consolidation(owner) { /* ... */ }
  const stage = (owner) =>
    steps.stageChanges({ ...scope, groupKey: "consolidation", operations: consolidation(owner), dependsOn: [load] });
  let plan = await stage();

  // 3. One review for the whole consolidation, not one per family.
  const token = input.tokenPrefix + ":consolidation";
  const review = createHook({ token });
  let decision;
  try {
    const owners = plan.conflicts.flatMap((conflict) => conflict.values);
    await steps.requestApproval({ planId: plan.planId, token, summary: plan.operations.length + " changes; owners to choose from: " + owners.join(", ") });
    decision = await review;
    if (decision.approved && plan.conflicts.length > 0) plan = await stage(decision.owner || owners[0]);
  } finally {
    review.dispose();
  }
```

The two procedures converge on the same records shown above, but they get there differently:

| | Procedure A: parent-first | Procedure B: provisional first |
| --- | --- | --- |
| First writes | Final records, one family at a time | Every row, provisional and flat |
| What waits for a person | Only the family whose owners disagree | The single consolidation of everything |
| Integrity during the run | Parents exist before children | Hierarchy and merges arrive in one plan that depends on the load |
| If the review is rejected | That family is skipped; the others are final | Records stay provisional, and `verifyChanges` reports them |

Neither is the right migration algorithm in general. They encode two customers' conventions, which is why each is a procedure rather than a platform feature.

## Many families

A procedure that runs every family in one run keeps the whole migration in one event log. For an export with thousands of families, start one run per family, or per batch of families, from a static parent workflow, and fan back in through hooks as in [Child Workflows](/cookbook/advanced/child-workflows). Each child is the same procedure with a narrower `input`.

## Operating it

The sections above leave out how procedures are stored and checked. None of this changes the API, but a platform that runs procedures for customers needs it.

### Procedure revisions

Store procedures as **immutable revisions** under a stable procedure ID: the exact source, the step names it binds, the catalog version it was reviewed against, and the approval record. Publish adds a revision; nothing edits one in place. Record the revision a run started from next to its run ID.

Keep the procedure ID separate from the [workflow ID](/docs/advanced/dynamic-workflows#workflow-ids). The SDK derives the workflow ID from a hash of the raw source bytes and the step bindings, so reformatting a procedure or editing a comment gives its runs a new workflow ID; the procedure ID stays stable across revisions.

### Checks at publish and start

Restrict publishing to operators, and at publish check what your platform owns: the approval record exists, every bound name is in the catalog, the catalog version is one this deployment serves, and the source is under 128 KB. Check again when a run starts, because the store can change in between:

```typescript title="lib/bind-revision.ts" lineNumbers
import { FatalError } from "workflow";
import { MIGRATION_CATALOG } from "@/lib/migration-catalog";

declare function sha256Hex(text: string): Promise<string>; // @setup

interface ProcedureRevision {
  procedureId: string;
  revision: number;
  source: string;
  sourceSha256: string;
  steps: Record<string, string>;
  catalogVersion: string;
  approval: { approvedBy: string; approvedAt: string; reviewUrl: string };
}

const CATALOG_VERSION = "crm-migration@1";

export async function bindRevision(revision: ProcedureRevision) {
  const label = `${revision.procedureId}@${revision.revision}`;
  if (!revision.approval?.approvedBy) {
    throw new FatalError(`Procedure ${label} has no approval record`);
  }
  if ((await sha256Hex(revision.source)) !== revision.sourceSha256) {
    throw new FatalError(`Procedure ${label} does not match its recorded hash`);
  }
  if (revision.catalogVersion !== CATALOG_VERSION) {
    throw new FatalError(`Procedure ${label} targets catalog ${revision.catalogVersion}`);
  }
  const steps: Record<string, (typeof MIGRATION_CATALOG)[keyof typeof MIGRATION_CATALOG]> = {};
  for (const alias of Object.keys(revision.steps)) {
    const name = revision.steps[alias];
    if (!Object.hasOwn(MIGRATION_CATALOG, name)) {
      throw new FatalError(`Procedure ${label} binds unknown step "${name}"`);
    }
    steps[alias] = MIGRATION_CATALOG[name as keyof typeof MIGRATION_CATALOG];
  }
  return steps;
}
```

Be precise about what these checks prove:

- **They are not a review.** Nothing here can tell whether a procedure does what its approver thinks it does. Syntax validation in `start()` is not a review either.
- **The hash detects accidents, not tampering.** It is stored next to the source it describes, so it catches a source that changed without it, such as a partial write or a hand edit, but not a writer who changes both or invents an approval record. `approvedBy` is a field the publisher supplied.
- **Trust comes from who can publish and who can write to the store.** To verify provenance at start independently of the store, sign each revision at publish with a key the store's writers do not hold, and check the signature here.

The checks throw [`FatalError`](/docs/api-reference/workflow/fatal-error) so that a refused revision fails at once instead of retrying when a step calls them.

### Runs in flight

A dynamic run stores its compiled code when it starts, and every replay runs that stored code:

- **In-flight runs are neither upgraded nor revoked.** Publishing a new revision changes what the next start runs. To stop a run, [cancel it](/docs/api-reference/workflow-api/get-run#cancel-a-run).
- **A run needs its deployment until it finishes.** A dynamic run executes only on the deployment that started it, against that deployment's steps. Keep a deployment available while its migrations wait on reviews, and bump the catalog version when a step changes in a way an existing procedure would notice.

### Limits

- **Source size.** At most 128 KB of source per procedure.
- **Execution context.** On Vercel, a run's execution context is limited to **2,048 bytes of JSON**, and the procedure's plaintext metadata counts against it: the source hash, the export name, and every bound name with its full step ID. Treat any count of bindings as an estimate; a start that exceeds the limit throws before a run is created. The Local World does not enforce this limit, so try a procedure with many bindings on a preview deployment.

See [Rules for the source](/docs/advanced/dynamic-workflows#rules-for-the-source) for the full list.

## Testing it

The e2e tests behind this recipe run both procedures against a synthetic `acme-legacy` dataset and a **pure simulated destination**: each plan's records are derived from the plan and the plans it depends on, and `verifyChanges` reconciles the results it is given. That shows the workflow's guarantees, including replay of recorded step results across a pause. It does not show destination-side deduplication when a write's outcome is unknown, which needs a destination that stores idempotency keys; test that against your real adapter.

## Key APIs

- [`start()`](/docs/api-reference/workflow-api/start): Starts a run from workflow source with `experimental_dynamic.steps`.
- [`createHook()`](/docs/api-reference/workflow/create-hook): Waits for a review inside the procedure.
- [`getHookByToken()`](/docs/api-reference/workflow-api/get-hook-by-token): Looks up a pending review before resuming it.
- [`resumeHook()`](/docs/api-reference/workflow-api/resume-hook): Delivers a reviewer's decision to the waiting run.
- [`getRun()`](/docs/api-reference/workflow-api/get-run): Reads a migration's status and result.
