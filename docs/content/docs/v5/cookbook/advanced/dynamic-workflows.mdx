Use this pattern when the orchestration a platform runs has to change after deploy, but every side effect it performs does not. The deployment ships a fixed catalog of steps and a small runner. Operators then publish reviewed **missions**, short JavaScript workflows over that catalog, to a store. The runner loads a mission and starts it with [`start()`](/docs/api-reference/workflow-api/start) as a [dynamic workflow](/docs/advanced/dynamic-workflows). Publishing a new mission needs no rebuild or redeploy.

<Callout type="warning">
Dynamic workflows are **experimental**. Before this recipe runs:

- The deployment must set `WORKFLOW_EXPERIMENTAL_DYNAMIC_WORKFLOWS=1`. Without it, `start()` throws.
- A dynamic run can only start on the deployment that calls `start()`.
- On Vercel, the project must have dynamic-workflow storage enabled. Without it, `start()` throws.

See [Enabling dynamic workflows](/docs/advanced/dynamic-workflows#enabling-dynamic-workflows) and [World support](/docs/advanced/dynamic-workflows#world-support) for the details.
</Callout>

## How it fits together

1. **Deploy once.** The deployment contains the step catalog, the runner, and the publish, start, and review routes. It contains no missions.
2. **Publish mission A.** An operator publishes a reviewed revision of a mission that sends every bird detection to an expert. The store keeps it.
3. **Publish mission B.** Later, an operator publishes a second mission with a different shape: it accepts confident detections on its own and sends only the rest for review. Nothing is rebuilt.
4. **Start either mission** on the same, unchanged deployment. The start route loads the stored revision and runs it.

If the set of workflows is known at build time, write normal workflow functions and pick one in code instead. They have better types and errors, and no source to store or review separately.

## The step catalog

The catalog is a workflow file of ordinary step functions, deployed with the app. Dynamic source cannot define steps, so everything a mission does outside of orchestration happens here.

```typescript title="workflows/mission-steps.ts" lineNumbers
import { resumeHook } from "workflow/api";

export interface BirdDetection {
  id: number;
  species: string;
  confidence: number;
}

declare function callVisionModel(image: string, maxDetections: number): Promise<BirdDetection[]>; // @setup
declare function pageReviewer(detection: BirdDetection, token: string): Promise<void>; // @setup
declare function postToChannel(message: string): Promise<void>; // @setup

export async function detectBirds(request: { image: string; count: number }) {
  "use step";
  return await callVisionModel(request.image, request.count);
}

export async function requestExpertReview(detection: BirdDetection, token: string) {
  "use step";
  await pageReviewer(detection, token);
  return { detectionId: detection.id, token };
}

export async function notify(message: string) {
  "use step";
  await postToChannel(message);
  return { delivered: message };
}

/** Fans a child mission's result back into its parent's hook. */
export async function reportToParent(token: string, report: unknown) {
  "use step";
  // Throws, and so retries, until the parent has created its hook.
  await resumeHook(token, report);
}
```

The runner names the catalog by step name and gives it a version. Bump the version whenever a step changes in a way an existing mission would notice, such as a new argument shape or a different return value.

```typescript title="lib/mission-catalog.ts" lineNumbers
import {
  detectBirds,
  notify,
  reportToParent,
  requestExpertReview,
} from "@/workflows/mission-steps";

export const MISSION_CATALOG = {
  detectBirds,
  requestExpertReview,
  notify,
  reportToParent,
};

export const MISSION_CATALOG_VERSION = "birds@1";

export type CatalogStepName = keyof typeof MISSION_CATALOG;
```

## Mission revisions

The store holds **immutable revisions**. A stable, app-level mission ID such as `triage` names the mission; each publish adds a revision under it, and nothing edits a revision in place. A revision records exactly what was approved:

```typescript title="lib/mission-store.ts" lineNumbers
import type { CatalogStepName } from "@/lib/mission-catalog";

export interface MissionRevision {
  missionId: string;
  revision: number;
  /** The exact approved bytes. */
  source: string;
  sourceSha256: string;
  /** Alias the source calls -> catalog step name. */
  steps: Record<string, CatalogStepName>;
  /** The catalog version the source was reviewed against. */
  catalogVersion: string;
  approval: { approvedBy: string; approvedAt: string; reviewUrl: string };
}

/** Any durable store works: a database table, a KV namespace, a bucket. */
export interface MissionStore {
  latest(missionId: string): Promise<MissionRevision | null>;
  get(missionId: string, revision: number): Promise<MissionRevision | null>;
  /** Appends the next revision; never overwrites one. */
  append(revision: Omit<MissionRevision, "revision">): Promise<MissionRevision>;
}

export async function sha256Hex(text: string) {
  const digest = await crypto.subtle.digest("SHA-256", new TextEncoder().encode(text));
  return Array.from(new Uint8Array(digest), (byte) => byte.toString(16).padStart(2, "0")).join("");
}
```

Keep the mission ID separate from the workflow ID. The SDK derives the [workflow ID](/docs/advanced/dynamic-workflows#workflow-ids) from a hash of the raw source bytes and the step bindings, so reformatting a mission, editing a comment, or rebinding an alias gives its runs a new workflow ID. The mission ID is what stays stable across revisions.

## The two missions

Missions are plain JavaScript: a top-level `async function workflow(input)` that opens with `"use workflow"` and reaches the catalog only through `steps`. `createHook`, `sleep`, and the usual [workflow globals](/docs/api-reference/workflow-globals) are in scope; see [What the source can use](/docs/advanced/dynamic-workflows#what-the-source-can-use).

Mission A sends every detection to an expert and waits on one hook per detection:

{/* @skip-typecheck: dynamic workflow source, evaluated with injected steps and createHook */}
```javascript title="missions/review-all.js" lineNumbers
async function workflow(input) {
  "use workflow";
  const detections = await steps.llm({ image: input.image, count: input.count });

  const reviews = await Promise.all(
    detections.map(async (detection) => {
      const token = input.reviewTokenPrefix + ":" + detection.id;
      const review = createHook({ token });
      await steps.expertReview(detection, token);
      const verdict = await review;
      return { ...detection, confirmed: verdict.confirmed === true, reviewedBy: "expert" };
    })
  );

  const confirmed = reviews.filter((review) => review.confirmed).length;
  const result = { image: input.image, confirmed, reviews };
  await steps.notify(input.image + ": " + confirmed + " of " + reviews.length + " confirmed");
  if (input.parentToken) {
    await steps.reportToParent(input.parentToken, result);
  }
  return result;
}
```

Mission B, published later, accepts detections at or above `input.autoAcceptAbove` without a review, and gives each remaining review until `input.reviewTimeout` before counting it as unconfirmed:

{/* @skip-typecheck: dynamic workflow source, evaluated with injected steps, createHook, and sleep */}
```javascript title="missions/triage.js" lineNumbers
async function workflow(input) {
  "use workflow";
  const detections = await steps.llm({ image: input.image, count: input.count });

  const reviews = await Promise.all(
    detections.map(async (detection) => {
      if (detection.confidence >= input.autoAcceptAbove) { // [!code highlight]
        return { ...detection, confirmed: true, reviewedBy: "auto" }; // [!code highlight]
      } // [!code highlight]
      const token = input.reviewTokenPrefix + ":" + detection.id;
      const review = createHook({ token });
      await steps.expertReview(detection, token);
      const verdict = await Promise.race([ // [!code highlight]
        review, // [!code highlight]
        sleep(input.reviewTimeout).then(() => null), // [!code highlight]
      ]); // [!code highlight]
      if (verdict === null) {
        return { ...detection, confirmed: false, reviewedBy: "timeout" };
      }
      return { ...detection, confirmed: verdict.confirmed === true, reviewedBy: "expert" };
    })
  );

  const confirmed = reviews.filter((review) => review.confirmed).length;
  const result = { image: input.image, confirmed, reviews };
  await steps.notify(input.image + ": " + confirmed + " of " + reviews.length + " confirmed");
  if (input.parentToken) {
    await steps.reportToParent(input.parentToken, result);
  }
  return result;
}
```

Both missions bind the same aliases: `llm` to `detectBirds`, `expertReview` to `requestExpertReview`, `notify`, and `reportToParent`. Every parameter, including the threshold, the timeout, and the hook tokens, arrives as `input`. The stored source is never templated, so the code that runs is byte for byte the code that was reviewed. Hook tokens are derived from a mission-run ID the server generates, so replay recreates the same hooks and concurrent runs never share a token; see [custom tokens](/docs/foundations/hooks#custom-tokens-for-deterministic-hooks).

## Publish a revision

Publishing is a privileged operator action, not part of the public API. A typical setup keeps missions in a reviewed repository and lets its CI job call this route after a change merges:

```typescript title="app/api/admin/missions/route.ts" lineNumbers
import { z } from "zod";
import { MISSION_CATALOG, MISSION_CATALOG_VERSION } from "@/lib/mission-catalog";
import { sha256Hex, type MissionStore } from "@/lib/mission-store";

declare const missionStore: MissionStore; // @setup
declare function assertOperator(request: Request): Promise<void>; // @setup

const publishRequest = z.object({
  missionId: z.string().regex(/^[a-z][a-z0-9-]{0,62}$/),
  source: z.string().max(128 * 1024),
  steps: z.record(z.string(), z.string()),
  catalogVersion: z.string(),
  approval: z.object({
    approvedBy: z.string().min(1),
    approvedAt: z.string().datetime(),
    reviewUrl: z.string().url(),
  }),
});

export async function POST(request: Request) {
  await assertOperator(request); // [!code highlight]

  const parsed = publishRequest.safeParse(await request.json());
  if (!parsed.success) {
    return Response.json({ error: parsed.error.message }, { status: 400 });
  }
  const { steps, catalogVersion, ...mission } = parsed.data;

  if (catalogVersion !== MISSION_CATALOG_VERSION) {
    return Response.json(
      { error: `This deployment serves catalog ${MISSION_CATALOG_VERSION}` },
      { status: 409 }
    );
  }
  for (const name of Object.values(steps)) {
    if (!Object.hasOwn(MISSION_CATALOG, name)) {
      return Response.json({ error: `Unknown catalog step "${name}"` }, { status: 400 });
    }
  }

  const revision = await missionStore.append({
    ...mission,
    steps: steps as Record<string, keyof typeof MISSION_CATALOG>,
    catalogVersion,
    sourceSha256: await sha256Hex(mission.source),
  });
  return Response.json({ missionId: revision.missionId, revision: revision.revision });
}
```

These checks confirm the revision is well formed and fits this deployment's catalog. They are not a review: nothing here can tell whether a mission does what its approver thinks it does. The review is the approval recorded with it. The SDK validates the source shape (the `workflow` declaration, the directive, no imports) when `start()` is called; there is no separate validation API, so a pipeline that wants that check before approval can start the mission once on a preview deployment.

## Start a mission

The start route loads the latest revision, checks it again, and starts it. Checking at start as well as at publish catches a record that was edited after approval and a revision published against a catalog this deployment no longer serves. The checks throw [`FatalError`](/docs/api-reference/workflow/fatal-error) so that, when a step calls them (as in [Fan out at scale](#fan-out-at-scale)), a refused revision fails at once instead of retrying.

```typescript title="lib/start-mission.ts" lineNumbers
import { FatalError } from "workflow";
import { start } from "workflow/api";
import { MISSION_CATALOG, MISSION_CATALOG_VERSION } from "@/lib/mission-catalog";
import { sha256Hex, type MissionRevision } from "@/lib/mission-store";

export async function bindMissionRevision(revision: MissionRevision) {
  const label = `${revision.missionId}@${revision.revision}`;
  if (!revision.approval?.approvedBy) {
    throw new FatalError(`Mission ${label} has no approval record`);
  }
  if ((await sha256Hex(revision.source)) !== revision.sourceSha256) {
    throw new FatalError(`Mission ${label} does not match its approved source`);
  }
  if (revision.catalogVersion !== MISSION_CATALOG_VERSION) {
    throw new FatalError(`Mission ${label} targets catalog ${revision.catalogVersion}`);
  }
  const steps: Record<string, (typeof MISSION_CATALOG)[keyof typeof MISSION_CATALOG]> = {};
  for (const alias of Object.keys(revision.steps)) {
    const name = revision.steps[alias];
    if (!Object.hasOwn(MISSION_CATALOG, name)) {
      throw new FatalError(`Mission ${label} binds unknown step "${name}"`);
    }
    steps[alias] = MISSION_CATALOG[name]; // [!code highlight]
  }
  return steps;
}

export async function startMissionRevision(
  revision: MissionRevision,
  input: Record<string, unknown>
) {
  const steps = await bindMissionRevision(revision);
  return await start(revision.source, [input], { // [!code highlight]
    experimental_dynamic: { steps }, // [!code highlight]
  }); // [!code highlight]
}
```

The step map holds the **imported** step functions. The build stamps a `stepId` on each one, and that ID is what binds `steps.llm` in the source to `detectBirds` in this deployment.

```typescript title="app/api/missions/route.ts" lineNumbers
import { z } from "zod";
import type { MissionStore } from "@/lib/mission-store";
import { startMissionRevision } from "@/lib/start-mission";

declare const missionStore: MissionStore; // @setup

const startRequest = z.object({
  missionId: z.string(),
  image: z.string().min(1).max(200),
  count: z.number().int().min(1).max(20),
});

export async function POST(request: Request) {
  // Authenticate the caller first: a mission runs deployed steps.
  const parsed = startRequest.safeParse(await request.json());
  if (!parsed.success) {
    return Response.json({ error: parsed.error.message }, { status: 400 });
  }
  const { missionId, image, count } = parsed.data;

  const revision = await missionStore.latest(missionId);
  if (!revision) {
    return Response.json({ error: "Unknown mission" }, { status: 404 });
  }

  const missionRunId = crypto.randomUUID();
  const run = await startMissionRevision(revision, {
    image,
    count,
    reviewTokenPrefix: `mission-run:${missionRunId}:review`,
    // Read only by missions that use them.
    autoAcceptAbove: 0.9,
    reviewTimeout: "1d",
  });

  return Response.json({
    runId: run.runId,
    missionRunId,
    revision: revision.revision,
  });
}
```

Record the revision a run started from alongside its run ID, so every result can be traced to the exact approved source.

## Resume a review

Each review waits on its own hook. The review route rebuilds the token from the mission-run ID and the detection ID, confirms the hook belongs to the run, and resumes it:

```typescript title="app/api/missions/[runId]/reviews/route.ts" lineNumbers
import { getHookByToken, resumeHook } from "workflow/api";
import { HookNotFoundError } from "workflow/errors";
import { z } from "zod";

declare function assertCanReview(request: Request, missionRunId: string): Promise<void>; // @setup

const reviewRequest = z.object({
  missionRunId: z.string().uuid(),
  detectionId: z.number().int().min(0),
  confirmed: z.boolean(),
});

export async function POST(
  request: Request,
  { params }: { params: Promise<{ runId: string }> }
) {
  const { runId } = await params;
  const parsed = reviewRequest.safeParse(await request.json());
  if (!parsed.success) {
    return Response.json({ error: parsed.error.message }, { status: 400 });
  }
  const { missionRunId, detectionId, confirmed } = parsed.data;

  // Knowing a token does not authorize the caller.
  await assertCanReview(request, missionRunId); // [!code highlight]

  try {
    const hook = await getHookByToken(`mission-run:${missionRunId}:review:${detectionId}`);
    if (hook.runId !== runId) {
      return Response.json({ error: "No such review" }, { status: 404 });
    }
    await resumeHook(hook, { confirmed }); // [!code highlight]
    return Response.json({ ok: true });
  } catch (error) {
    if (HookNotFoundError.is(error)) {
      return Response.json({ error: "No pending review" }, { status: 404 });
    }
    throw error;
  }
}
```

A review for a detection mission B accepted on its own, or one that arrives after its timeout, gets a 404: that hook never existed or is already gone. See [Authorize before calling `resumeHook()`](/docs/foundations/hooks#authorize-before-calling-resumehook).

To report status, read the run with [`getRun()`](/docs/api-reference/workflow-api/get-run). A dynamic run's result type is `unknown` to TypeScript, so pass the type you expect, as in `getRun<MissionResult>(runId)`.

## Fan out at scale

To run a mission once per image across a large batch, start the runs from a static parent workflow and fan back in through hooks, as in [Child Workflows](/cookbook/advanced/child-workflows). Each mission ends with `steps.reportToParent(input.parentToken, result)` when it was given a parent token, which resumes the hook the parent created for it.

```typescript title="workflows/bird-survey.ts" lineNumbers
import { createHook } from "workflow";
import type { MissionRevision } from "@/lib/mission-store";
import { startMissionRevision } from "@/lib/start-mission";

interface MissionResult {
  image: string;
  confirmed: number;
}

export async function birdSurvey(revision: MissionRevision, surveyId: string, images: string[]) {
  "use workflow";

  const hooks = images.map((_, index) =>
    createHook<MissionResult>({ token: `survey:${surveyId}:mission:${index}` })
  );
  await Promise.all(
    images.map((image, index) =>
      startMission(revision, {
        image,
        count: 5,
        reviewTokenPrefix: `survey:${surveyId}:review:${index}`,
        parentToken: `survey:${surveyId}:mission:${index}`, // [!code highlight]
      })
    )
  );
  const results = await Promise.all(hooks); // [!code highlight]

  return {
    images: results.length,
    confirmed: results.reduce((total, result) => total + result.confirmed, 0),
    results,
  };
}

async function startMission(revision: MissionRevision, input: Record<string, unknown>) {
  "use step";
  const run = await startMissionRevision(revision, input);
  return { runId: run.runId };
}
```

`startMission` is a step, not workflow code: `start()` is a side effect, and the step map holds function references that must not cross a step boundary as serialized data. Load the revision in the route that starts `birdSurvey`, and pass it in, so every child runs the same revision. The child-workflows recipe covers the rest of the fan-out: [chunked spawning](/cookbook/advanced/child-workflows#fan-out-pattern-chunked-spawning) for hundreds of children, [partial failures](/cookbook/advanced/child-workflows#tolerating-partial-failures), and the parent's own event-log growth.

## Runs in flight

A dynamic run stores its compiled code when it starts, and every replay runs that stored code. Publishing a new revision changes what the *next* start runs:

- **In-flight runs are neither upgraded nor revoked.** A run of mission A revision 1 finishes on revision 1, even after revision 2 is published or the record is deleted. To stop one, [cancel the run](/docs/api-reference/workflow-api/get-run#cancel-a-run).
- **A run needs its deployment until it finishes.** A dynamic run executes only on the deployment that started it, against that deployment's steps. Keep a deployment available while its long-running missions wait on reviews or timers, and keep its catalog steps compatible with what those missions call.

## Limits

- **Source size.** At most 128 KB of source per mission.
- **Execution context.** On Vercel, a run's execution context is limited to **2,048 bytes of JSON**, and the mission's plaintext metadata counts against it: the source hash, the export name, and every alias with its full step ID. Step IDs are derived from the step's file path and function name, so a catalog in a deeply nested file fits fewer aliases than one near the root. Treat any alias count as an estimate; a start that exceeds the limit throws before a run is created.
- **Local and Vercel differ.** The Local World does not enforce the execution-context limit, so start a mission with many bindings on a preview deployment before approving it.

See [Rules for the source](/docs/advanced/dynamic-workflows#rules-for-the-source) for the full list.

## Security

Dynamic workflows execute trusted application code, including code authored by operators or drafted by a model and approved under your application-code review process. Do not execute end-user scripts, or unreviewed model-generated source influenced by untrusted requests, retrieved content, or tool outputs. A fixed step catalog, syntax validation, and a dedicated project do not make that source safe.

- **The source has the deployment's privileges.** The workflow sandbox is for determinism, not isolation. Mission source can read `process.env`, reach host globals, call the World with the deployment's credentials (which reach other runs' hooks and streams), and alter state in a warm instance that later requests reuse.
- **The step map is not a boundary.** A mission that calls an alias it was not given fails its run, but the map does not stop source that is trying to reach other steps or the host. Review is the boundary.
- **A dedicated project is defense in depth.** Running missions from their own Vercel project, with only the environment variables and access the catalog needs, limits what a mistake in reviewed code can reach. It does not make unreviewed source safe to run.
- **Guard the publish path like a deploy.** Anyone who can publish a revision can run code with the deployment's privileges. Restrict the publish route to operators, and protect the store's write access the same way.
- **Parameters are input, not source.** Building source from request fields, even with escaping, turns every caller into a code author.
- **Authorize every resume.** Hook tokens route a payload to a run; they do not prove who sent it.

See [Security](/docs/advanced/dynamic-workflows#security) on the concept page for the full model, including what encryption does and does not protect.

## Key APIs

- [`start()`](/docs/api-reference/workflow-api/start): Starts a run from workflow source with `experimental_dynamic.steps`.
- [`createHook()`](/docs/api-reference/workflow/create-hook): Waits for an external signal, such as a review, inside the source.
- [`sleep()`](/docs/api-reference/workflow/sleep): Durable timer, raced against a hook for timeouts.
- [`getHookByToken()`](/docs/api-reference/workflow-api/get-hook-by-token): Looks up a pending hook before resuming it.
- [`resumeHook()`](/docs/api-reference/workflow-api/resume-hook): Delivers a review to the waiting run.
- [`getRun()`](/docs/api-reference/workflow-api/get-run): Reads a mission run's status and result.
