After you define a workflow function, use the `start()` function <LanguageContent value="ts" as="span">from `workflow/api`</LanguageContent> to trigger it. The function enqueues a new workflow run and returns a `Run` object for tracking its progress.

## The `start()` function

<LanguageContent value="ts">

The [`start()`](/docs/api-reference/workflow-api/start) function programmatically triggers workflow executions from runtime contexts such as API routes, Server Actions, or other server-side code. In v5, you can also call `start()` inside a workflow function to spawn a child run or continue work in a new run.

```typescript lineNumbers
import { start } from "workflow/api";
import { handleUserSignup } from "./workflows/user-signup";

export async function POST(request: Request) {
  const { email } = await request.json();

  // Start the workflow
  const run = await start(handleUserSignup, [email]); // [!code highlight]

  return Response.json({
    message: "Workflow started",
    runId: run.runId
  });
}
```

</LanguageContent>
<LanguageContent value="py">

The `start()` function programmatically triggers workflow executions from API routes or other server-side code.

```python lineNumbers
from app.workflows.user_signup import handle_user_signup
from vercel import workflow

@app.post("/api/signup")
async def signup(body: SignupBody):
    # Start the workflow
    run = await workflow.start(handle_user_signup, body.email)  # [!code highlight]

    return {
        "message": "Workflow started",
        "run_id": run.run_id,
    }
```

</LanguageContent>

**Key points:**

- `start()` returns immediately after enqueuing the workflow. It doesn't wait for completion
- The first argument is your workflow function
- <LanguageContent value="ts" as="span">The second argument is an array of arguments to pass to the workflow (optional if the workflow takes no arguments)</LanguageContent><LanguageContent value="py" as="span">Remaining positional and keyword arguments are passed to the workflow</LanguageContent>
- All arguments must be [serializable](/docs/foundations/serialization)
- On Worlds with a regional dimension, the optional `region` option pins the new run's storage, queuing, and streams to a specific region. See [Multi-region on the Vercel World](/worlds/vercel#multi-region)

</LanguageContent>

## The `Run` object

When you call `start()`, it returns a `Run` object that provides access to the workflow's status and results.

<LanguageContent value="ts">

```typescript lineNumbers
import { start } from "workflow/api";
import { processOrder } from "./workflows/process-order";

const run = await start(processOrder, [/* orderId */]);

// The run object has properties you can await
console.log("Run ID:", run.runId);

// Check the workflow status
const status = await run.status; // "running" | "completed" | "failed"

// Get the workflow's return value (blocks until completion)
const result = await run.returnValue;
```

</LanguageContent>
<LanguageContent value="py">

```python lineNumbers
from app.workflows.process_order import process_order
from vercel import workflow

run = await workflow.start(process_order, order_id)

print("Run ID:", run.run_id)

# Check the workflow status
status = await run.status()  # "pending" | "running" | "completed" | ...

# Get the workflow's return value (waits until completion)
result = await run.return_value()
```

</LanguageContent>

<LanguageContent value="ts">

**Key properties:**

- `runId`: Unique identifier for this workflow run
- `status`: Current status of the workflow (async)
- `returnValue`: The value returned by the workflow function (async, blocks until completion)
- `readable`: `ReadableStream` for streaming updates from the workflow

</LanguageContent>
<LanguageContent value="py">

**Key properties and methods:**

- `run_id`: Unique identifier for this workflow run
- `status()`: Current workflow status
- `return_value()`: Wait for and return the workflow result
- `readable()`: Async iterator for streaming updates from the workflow

</LanguageContent>

<Callout type="info">
<LanguageContent value="ts" as="p">Most `Run` properties are async getters that return promises. `await` them to get their values. For a complete list of properties and methods, see the API reference below.</LanguageContent>
<LanguageContent value="py" as="p">Python exposes asynchronous run operations as methods. Call and await them, for example `await run.status()`.</LanguageContent>
</Callout>

## Common patterns

### Starting workflows from workflow functions

<LanguageContent value="ts">

You can also call `start()` directly inside workflow functions to spawn child workflows. For choosing between this and awaiting a workflow function directly, see [Workflow Composition](/cookbook/common-patterns/workflow-composition).

```typescript lineNumbers
import { start } from "workflow/api";
import { childWorkflow } from "./workflows/child";

export async function parentWorkflow(inputValue: number) {
  "use workflow";

  const childRun = await start(childWorkflow, [inputValue]); // [!code highlight]

  // childRun is a full Run object. Use it like normal.
  const childResult = await childRun.returnValue;
  return { childRunId: childRun.runId, childResult };
}
```

When you call `start()` inside a workflow function, it automatically executes through an internal step to maintain deterministic replay. The returned `Run` object works as it does outside workflows. Properties such as `.runId`, `.status`, and `.returnValue`, and methods such as `.cancel()`, are all available. Each property access or method call executes as a separate step.

<Callout type="info">
Inside workflow functions, each `Run` property access (e.g., `run.status`, `run.returnValue`) triggers a workflow step. This means each access is recorded in the event log and replayed deterministically.
</Callout>

<Callout type="warn">
Awaiting `returnValue` polls the child run every second, and the polling step holds its worker slot open until the child finishes. Size worker-based Worlds to cover the peak number of these polls in flight. If the child workflow is long-running, spawn it without awaiting `returnValue` and have it resume a [hook](/docs/foundations/hooks) when it completes. See the [`startAndWait()` pattern](/cookbook/advanced/child-workflows).
</Callout>

</LanguageContent>
<LanguageContent value="py">

Python workflow bodies run without World access. To spawn a child workflow, call `start()` in a step and return the child's run ID. If the parent must wait for the result, do that in another step:

```python lineNumbers
from app.workflow import wf
from app.workflows.child import child_workflow
from vercel import workflow

@wf.step
async def start_child(input_value: int) -> str:
    run = await workflow.start(child_workflow, input_value)  # [!code highlight]
    return run.run_id

@wf.step
async def wait_for_child(run_id: str):
    return await workflow.Run(run_id).return_value()

@wf.workflow
async def parent_workflow(input_value: int):
    child_run_id = await start_child(input_value)
    child_result = await wait_for_child(child_run_id)
    return {"child_run_id": child_run_id, "child_result": child_result}
```

<Callout type="warn">
`return_value()` polls the child run and keeps the waiting step's worker slot occupied until the child finishes. For long-lived children, start the child without waiting and use a [hook](/docs/foundations/hooks) to notify the parent when it completes.
</Callout>

</LanguageContent>

### Fire and forget

Start a workflow and immediately return to let it execute in the background:

<LanguageContent value="ts">

```typescript lineNumbers
import { start } from "workflow/api";
import { sendNotifications } from "./workflows/notifications";

export async function POST(request: Request) {
  // Start workflow and don't wait for it
  const run = await start(sendNotifications, [userId]);

  // Return immediately
  return Response.json({
    message: "Notifications queued",
    runId: run.runId
  });
}
```

</LanguageContent>
<LanguageContent value="py">

```python lineNumbers
from app.workflows.notifications import send_notifications
from vercel import workflow

@app.post("/api/notifications")
async def queue_notifications(user_id: str):
    run = await workflow.start(send_notifications, user_id)

    return {
        "message": "Notifications queued",
        "run_id": run.run_id,
    }
```

</LanguageContent>

### Wait for completion

If you need to wait for the workflow to complete before responding:

<LanguageContent value="ts">

```typescript lineNumbers
import { start } from "workflow/api";
import { generateReport } from "./workflows/reports";

export async function POST(request: Request) {
  const run = await start(generateReport, [reportId]);

  // Wait for the workflow to complete
  const report = await run.returnValue; // [!code highlight]

  return Response.json({ report });
}
```

</LanguageContent>
<LanguageContent value="py">

```python lineNumbers
from app.workflows.reports import generate_report
from vercel import workflow

@app.post("/api/reports")
async def create_report(report_id: str):
    run = await workflow.start(generate_report, report_id)

    report = await run.return_value()  # [!code highlight]
    return {"report": report}
```

</LanguageContent>

<Callout type="warn">
Waiting for <LanguageContent value="ts" as="code">returnValue</LanguageContent><LanguageContent value="py" as="code">return_value()</LanguageContent> can cause your API route to time out if the workflow takes a long time.
</Callout>

### Stream updates to client

Stream updates from your workflow as it executes without waiting for completion:

<LanguageContent value="ts">

```typescript lineNumbers
import { start } from "workflow/api";
import { generateAIContent } from "./workflows/ai-generation";

export async function POST(request: Request) {
  const { prompt } = await request.json();

  // Start the workflow
  const run = await start(generateAIContent, [prompt]);

  // Get the readable stream (can also use run.readable as shorthand)
  const stream = run.getReadable(); // [!code highlight]

  // Return the stream immediately
  return new Response(stream, {
    headers: {
      "Content-Type": "application/octet-stream",
    },
  });
}
```

</LanguageContent>
<LanguageContent value="py">

```python lineNumbers
from starlette.responses import StreamingResponse

from app.workflows.ai_generation import generate_ai_content
from vercel import workflow

@app.post("/api/generate")
async def generate(prompt: str):
    run = await workflow.start(generate_ai_content, prompt)

    return StreamingResponse(
        run.readable_bytes(),  # [!code highlight]
        media_type="application/octet-stream",
    )
```

</LanguageContent>

Steps can write to the run's stream:

<LanguageContent value="ts">

```typescript lineNumbers
import { getWritable } from "workflow";

export async function generateAIContent(prompt: string) {
  "use workflow";

  const writable = getWritable(); // [!code highlight]

  await streamContentToClient(writable, prompt);

  return { status: "complete" };
}

async function streamContentToClient(
  writable: WritableStream,
  prompt: string
) {
  "use step";

  const writer = writable.getWriter();

  // Stream updates as they become available
  for (let i = 0; i < 10; i++) {
    const chunk = new TextEncoder().encode(`Update ${i}\n`);
    await writer.write(chunk);
  }

  writer.releaseLock();
}
```

</LanguageContent>
<LanguageContent value="py">

```python lineNumbers
from app.workflow import wf
from vercel.workflow import get_writable

@wf.step
async def stream_content_to_client(prompt: str):
    writable = get_writable()  # [!code highlight]

    for index in range(10):
        await writable.write(f"Update {index}\n".encode())

    await writable.close()

@wf.workflow
async def generate_ai_content(prompt: str):
    await stream_content_to_client(prompt)
    return {"status": "complete"}
```

</LanguageContent>

<Callout type="info">
Use streams to show users real-time progress from AI workflows or intermediate results from long-running processes.
</Callout>

**Learn more**: [Streaming in workflows](/docs/foundations/streaming)

### Check status later

You can recreate a workflow run handle later from its ID:

<LanguageContent value="ts">

```typescript lineNumbers
import { getRun } from "workflow/api";

export async function GET(request: Request) {
  const url = new URL(request.url);
  const runId = url.searchParams.get("runId");

  // Retrieve the existing run
  const run = getRun(runId); // [!code highlight]

  // Check its status
  const status = await run.status;

  if (status === "completed") {
    const result = await run.returnValue;
    return Response.json({ result });
  }

  return Response.json({ status });
}
```

</LanguageContent>
<LanguageContent value="py">

```python lineNumbers
from vercel import workflow

@app.get("/api/runs/{run_id}")
async def get_run_status(run_id: str):
    run = workflow.Run(run_id)  # [!code highlight]
    status = await run.status()

    if status == "completed":
        result = await run.return_value()
        return {"result": result}

    return {"status": status}
```

</LanguageContent>

### Recursive and repeating workflows

A workflow can start a new instance of itself. This pattern prevents a single long-running workflow from accumulating too many events. Large event logs are slower to replay, more expensive to store, and harder to inspect in the UI. Breaking work into smaller runs that chain together keeps each run lean.

<LanguageContent value="ts">

```typescript lineNumbers
import { start } from "workflow/api";
declare function fetchBatch(cursor?: string): Promise<{ items: string[]; nextCursor?: string }>; // @setup
declare function processBatch(items: string[]): Promise<void>; // @setup

export async function processQueue(cursor?: string) {
  "use workflow";

  const { items, nextCursor } = await fetchBatch(cursor);
  await processBatch(items);

  if (nextCursor) {
    // Continue processing in a new workflow run
    await start(processQueue, [nextCursor]); // [!code highlight]
  }
}
```

</LanguageContent>
<LanguageContent value="py">

```python lineNumbers
from app.workflow import wf
from vercel import workflow

@wf.workflow
async def process_queue(cursor: str | None = None):
    items, next_cursor = await fetch_batch(cursor)
    await process_batch(items)

    if next_cursor:
        # Continue processing in a new workflow run
        await continue_queue(next_cursor)  # [!code highlight]

@wf.step
async def continue_queue(cursor: str) -> str:
    run = await workflow.start(process_queue, cursor)
    return run.run_id
```

</LanguageContent>

This pattern also enables **repeating cron-like workflows**. A workflow can complete its work, sleep, and then schedule a new instance of itself. This creates an indefinite chain without allowing any single run to grow too large:

<LanguageContent value="ts">

```typescript lineNumbers
import { sleep } from "workflow";
import { start } from "workflow/api";
declare function refreshMetrics(): Promise<void>; // @setup

export async function syncDashboard() {
  "use workflow";

  await refreshMetrics();
  await sleep("1h");

  // Schedule the next run
  await start(syncDashboard); // [!code highlight]
}
```

</LanguageContent>
<LanguageContent value="py">

```python lineNumbers
from app.workflow import wf
from vercel import workflow

@wf.workflow
async def sync_dashboard():
    await refresh_metrics()
    await workflow.sleep("1h")

    # Schedule the next run through a step
    await schedule_next_sync()  # [!code highlight]

@wf.step
async def schedule_next_sync() -> str:
    run = await workflow.start(sync_dashboard)
    return run.run_id
```

</LanguageContent>

#### Starting against the latest deployment

<LanguageContent value="ts">

By default a chained run starts on the same deployment as its parent. For workflows that chain over long periods, pass [`deploymentId: "latest"`](/docs/api-reference/workflow-api/start#using-deploymentid-latest) so the next run picks up new code. [Versioning](/docs/foundations/versioning#self-upgrading-workflows) covers this pattern in full, including how the serialized state acts as the migration boundary between versions.

</LanguageContent>
<LanguageContent value="py">

A Python child run starts on the deployment executing its `start()` step, which is the parent's pinned deployment. The Python SDK does not currently expose a deployment selector for self-upgrading chains.

</LanguageContent>
