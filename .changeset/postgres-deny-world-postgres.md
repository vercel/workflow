Deliver the Workflow SDK's messages in process and refuse the flow route over HTTP (`queueAuthMode: 'deny'`). A Graphile Worker runner starts only in a process that registered the app's flow route with the World (`registerWorkflowHandler()` from `workflow/runtime`, which the framework integrations call when the app starts); every other process (the CLI, the web UI, a script calling `start()`) only enqueues. The World owns its delivery handler and no longer depends on `@workflow/world-local`; the `WORKFLOW_LOCAL_QUEUE_MAX_VISIBILITY` clamp and the Local World's Vercel-deployment warning no longer apply to it. The loopback wait and port probe before the runner are gone. What to do: adopt the startup hook the Postgres docs describe for your framework (Next.js and SvelteKit import the generated worker module; Astro starts through the emitted `dist/server/workflow-worker.mjs`; Nitro and Nest register the route themselves). A hook that only calls `world.start()` runs no worker on this release, leaves runs `pending`, and gets a warning once; for separate worker machines, deploy a copy of the app that serves no web traffic; drain the processes on the previous release before upgrading, since their HTTP deliveries are refused and retried against the attempt limit, or set `WORKFLOW_QUEUE_AUTH=off` on the new release for the overlap. `WORKFLOW_POSTGRES_HEADERS_TIMEOUT_MS` is the deadline an in-process delivery has to respond; `WORKFLOW_POSTGRES_BODY_TIMEOUT_MS` only applies to a consumer's own HTTP route. Request-only framework APIs (Next.js `headers()`, `cookies()`, `after()`, `revalidatePath()`) do not work inside steps.
