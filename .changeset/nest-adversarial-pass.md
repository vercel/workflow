---
"@workflow/nest": minor
---

Harden the NestJS integration against the framework features a real application uses.

- **Fastify applications now boot.** Fastify derives a HEAD route from every GET route, so registering the flow route's GET handler before its HEAD handler made route registration throw `Method 'HEAD' already declared for route '/.well-known/workflow/v1/flow'` and reject `app.init()` — the whole application failed to start, not just the workflow routes. The handlers are declared in the order Fastify needs, and an integration test boots an app on both platforms.
- **Queue deliveries are no longer capped at 100 KB.** The queue carries run inputs, step inputs and step outputs in the request body, and Express's parser — which NestJS installs by default — rejects anything larger with `413` before a controller sees it, so a workflow passing a modest amount of data around stopped making progress with only a retry loop to show for it. `WorkflowModule` now keeps the application's body parsers away from `.well-known/workflow/v1`, and nothing else; the new `bypassBodyParser` option turns it off. This also delivers signed webhook bodies byte-for-byte without `{ rawBody: true }`. On Fastify, where the body limit is enforced per instance rather than per route, a limit low enough to reject deliveries is reported at startup instead.
- **`app.enableVersioning()` no longer moves the workflow routes.** URI versioning relocated them to `/v1/.well-known/workflow/v1/...` while the SDK kept generating callback URLs at the unversioned path, so every delivery 404'd. The controller is registered `VERSION_NEUTRAL`.
- **`setGlobalPrefix(prefix, { exclude })` is honoured.** An exclusion covering the workflow routes leaves them at the origin root; the prefix is no longer adopted for generated URLs, and an exclusion that covers only one of the two routes is reported.
- **New `isWorkflowRequest(context)` export.** A global guard runs for the workflow routes too, so an application that authenticates every request rejected every queue delivery and webhook with `403`. Guards can now let them through: `if (isWorkflowRequest(context)) return true`. `isWorkflowRoutePath()` and `WORKFLOW_ROUTE_PREFIX` are exported alongside it.
- **The local-dev steps bundle no longer imports TypeScript.** An ESM project whose step imported a plain local helper produced `import ... from "./helper.ts"`, which Node cannot load below 22.18 — and above it, type stripping still rejects the enums and parameter properties a NestJS codebase is full of. Every workflow request answered `503 Unknown file extension ".ts"`. Those dependencies are bundled now. CommonJS projects are unchanged.
- **The Vercel app function is bundled for the runtime it is deployed on.** The esbuild target was pinned to `node22` regardless of `--runtime`, so `--runtime nodejs20.x` could emit syntax the deployed Node cannot parse. `import.meta` is also given a working value instead of esbuild's empty object, which previously made `createRequire(import.meta.url)` throw at cold start in an ESM NestJS app.
- **`--external <pkgs>` for dependencies the bundler cannot follow**, such as a database driver reached through an ORM. The build error now names the flag, and native addons the bundle statically requires are reported rather than silently externalized into a function that cannot load them.
- **The flow route's Build Output rewrite is anchored**, so a path merely containing `/.well-known/workflow/v1/flow` is no longer routed into the workflow function.
- **A second copy of `@nestjs/core` is reported.** NestJS's core providers are injected by class, so two copies give two tokens, `@Optional()` yields `undefined`, and prefix handling and the body-parser bypass both stop working with no other symptom.
