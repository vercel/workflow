"@workflow/builders": patch
"@workflow/nest": patch
"@workflow/vitest": patch
---

Stop workflow discovery from losing imports in silence, which shipped builds that registered fewer workflows than the app could start.

- Follow TypeScript's `.js`-to-`.ts` import rewriting. A `.ts` file using NodeNext module resolution writes `./x.js` for a sibling that only exists as `./x.ts`, which every bundler in the toolchain resolves and discovery took literally: the module was never scanned and the workflow it declared never registered, with a successful build and a runtime `WorkflowNotRegisteredError` as the only signal. `.js`/`.jsx`/`.mjs`/`.cjs` specifiers now fall back to their `.ts`/`.tsx`/`.mts`/`.cts` counterparts, for relative paths and deep package imports alike. The written extension is still tried first, so a project shipping both `x.js` and `x.ts` resolves to the same file it did before.
- Report, rather than drop, an import that resolves to nothing when the file that wrote it declares `"use workflow"`, `"use step"`, or a serde class. Those imports decide what the build registers, so a production build now prints which file and which specifier went nowhere instead of leaving the gap to surface as `WorkflowNotRegisteredError`/`StepNotRegisteredError` at runtime. An import that resolves to something discovery does not follow is never reported: an existing asset, a type-only import backed by a `.d.ts`/`.d.mts`/`.d.cts`, a package that is not installed, a bare specifier that only matched a catch-all `"*"` tsconfig alias, or import-looking text inside a template literal. Development and watch builds stay quiet, where writing an import before creating its target is a normal editing state.
- Stop reading template-literal text as imports. `extractImportSpecifiers` masked comments but not template text, so a code sample inside a prompt string — ordinary in an agent workflow — was followed as an import. That was already over-discovery; with the report above it also warned about correct builds.
- Fail a production build when the workflow manifest cannot be created, instead of warning and reporting success. The manifest is what records which workflows a deployment registered, so a build that cannot write one cannot be verified. This covers the optional diagnostics copy too, which now fails the build even when `manifest.json` itself was written.
- Classify builders that run inside an edit or test loop as development, so the two behaviours above do not apply to them. `@workflow/nest` rebuilds at application startup — every `nest start --watch` restart — and `@workflow/vitest` rebuilds per test run under `NODE_ENV=test`; neither watches nor sets `NODE_ENV=development`, so both were being treated as builds ahead of a deploy. A new `development` builder option carries this, and `workflow-nest build` stays strict because it genuinely does run ahead of a deploy.
